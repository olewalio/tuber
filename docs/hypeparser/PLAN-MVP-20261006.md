### 1.6. Что дал глубокий анализ Tuber (06.10.2026)

Отчёт: `docs/DEEP-ANALYSIS-TUBER-20261006.md`. Факты, прямо влияющие на этот план:

- **Поиска через сессию в проекте нет** (нет `SearchTimeline`), дискавери держится на
  Nitter-поиске — а из 12 зеркал в боевых метриках реально работают 1–2
  (`nitter.jaydenha.uk` 53 273 запроса из 193 626 в журнале транспорта). Внешний канал
  поиска нужен не «для новой фичи», а чтобы у поиска вообще был независимый путь.
- **Канал может быть активным и невидимым**: `fxtwitter` дал 8 848 постов, но в журнале
  `transport_request` — 0 строк. Новый канал поиска обязан писать в журнал, иначе повторяем дефект.
- **Сессия X — самая нагруженная часть транспорта**: 166 353 из 280 248 снимков метрик X (59%),
  501 запрос за сутки, лимит 4 запроса/60 с, блок при 403 на 24 часа. Аккаунт twscrape нельзя
  расходовать «как получится» — нужен отдельный потолок и учёт в том же журнале.
- **Просмотры есть лишь у 65,5% постов X** (ограничение канала, не сбоя записи). Значит
  интерфейс обязан показывать «просмотров нет», а не ноль, и не выдавать такие посты за нулевой
  коэффициент.
- **Реестр источников разбалансирован**: 384 `active`, 410 `candidate`, 323 `rejected`.
  Авторы, найденные поиском, логично попадают в `candidate` с пометкой источника.
- **Рост базы не ограничен**: `metric_snapshot` 1,10 млн строк за 27 дней (~41 тыс/сутки),
  ретенции нет, база 2,00 ГиБ при `freelist` = 0. Посты поиска добавят объём — пометка
  `source_kind='search'` нужна ещё и для будущей политики прореживания.
- **Эксплуатация**: все 36 заданий Tuber живут в кроне Hermes, системный crontab и systemd
  свободны; есть регламентный рестарт гейтвея около 02:00 (он даёт статусы `unknown` в
  планировщике — при приёмке не путать с поломкой новой задачи). Воркер поиска — отдельный
  systemd-юнит.
- **В проекте уже 2 красных теста** (`tests/test_report_compact.py`, хрупкая проверка по
  подстроке). При Фазе 2 они останутся красными — это не регрессия от нашего кода.

## 3. Решения приняты владельцем-делегатом 07.10.2026

Владелец распорядился «подумать хорошо и решить самому». Решения ниже приняты и обоснованы
фактами, собранными на узле 07.10.2026; каждый вариант проверялся, а не выбирался по вкусу.

| № | Вопрос | Решение | Почему именно так (факты) |
|---|--------|---------|---------------------------|
| 1 | Куда вешать страницу | Приложение на `127.0.0.1:8730`, наружу — nginx-вхост на **443 с TLS** (Let's Encrypt), имя `<server_host>.sslip.io`; basic-auth, `X-Robots-Tag: noindex`, ограничение частоты | На Main **нет ни одного домена**: `proprate.xyz` и `<owner-domain>` резолвятся на eduard (<other_host>), `aiofficegame.com` — за Cloudflare, `api.proprate.xyz` не существует. Конфиг `prop-rate` в nginx — наследие. Слушает только :80, **443 свободен**, certbot/letsencrypt отсутствуют. Поддомен требует действия владельца в DNS — отложено; открытый HTTP с basic-auth недопустим (пароль защищает наш X-бюджет, а идёт в открытом виде). `sslip.io` даёт валидный TLS без правки DNS. `server_name` — отдельная переменная: переход на реальный поддомен = одна строка + перевыпуск. Если ACME не пройдёт — самоподписанный сертификат на 8443 вместо пароля по HTTP |
| 2 | Куда пишутся посты поиска | **Свои таблицы `x_search*`, в `content`/`metric_snapshot`/`content_latest` не пишем вообще** | `metric_snapshot` растёт на ~41 тыс. строк/сутки **без ретенции**, база 2,00 ГиБ, `freelist`=0. Критерий приёмки №10 требует, чтобы посты поиска не попадали в общие отчёты; изоляция таблиц даёт это **по построению**, а «пометка + 12 фильтров» — по договорённости, которую можно забыть в любом из отчётов. Авторов из поиска в реестр `source` не заводим: иначе чужие тысячи аккаунтов попадут в контуры сбора (это отдельное решение, не побочный эффект). Подписчики живут в `x_search_post` (`subs`, `subs_at`) с правилом 24 ч |
| 3 | Аккаунт для twscrape | Тот же аккаунт из `config/x_session.json`, но поиск — **отдельный вид трафика** `kind='search'` в существующем журнале `transport_request` со своим потолком | Куки `auth_token`+`ct0`+`guest_id`+`twid` подходят twscrape без шага логина (проверено по исходникам: `add_account_cookies` требует ровно `auth_token` и `ct0`). За 24 ч боевой сбор израсходовал **535** запросов из суточного потолка 1000 (окно 50/900 с, темп 4/60 с, точка 200/сут, лента 800/сут) — запас есть, но приоритет всегда у боевого сбора. Потолок поиска: темп ≤ 1 запрос/5 с, окно ≤ 20/600 с, сутки ≤ 100 запросов, и поиск **не стартует**, если за последний час боевых `x_session`-запросов больше 60. Второй аккаунт — только при первом признаке карантина (пустая выдача или 403) |
| 4 | Потолок одной задачи | На ветку: **12 страниц ИЛИ 300 постов ИЛИ 8 минут**; на задачу (две ветки): **20 страниц ИЛИ 500 постов ИЛИ 12 минут**. Упор → статус `incomplete`, прогресс сохранён, продолжение кнопкой «Обновить» | Latest по слову «AI» бесконечен, задача без потолка никогда не станет «готовой». При нашем темпе (1 запрос/5 с) и ~20 постах на странице 12 страниц ≈ 240 постов и ~60 с — потолки согласованы между собой. Главный ограничитель — суточные 100 запросов из решения №3: он перебивает всё, задача сверх него честно сообщает «лимит на сегодня исчерпан» |

Итог по бюджету: 535 боевых + ≤100 поисковых = ≤635 из 1000 суточных — запас 36 %.

Итог: **поиск работает**. 86 постов за 45 с, 4 страницы (21–22 поста каждая), 0 отказов,

Что дал прогон, кроме «да»: счётчик просмотров **отстаёт** (у постов возрастом секунды
`viewCount` пуст — 1 из 20), выдача Latest **включает ответы**, страница это 21–22 поста, а один
полный прогон стоит 4 запроса из 100 суточных. Все три находки разведены по фазам ниже.

### Фаза 1. ТЗ-55 в стиле репозитория (0,5 дня)

Файл `docs/TZ-55-hypeparser-search.md`: схема новых таблиц, поведение воркера, API страницы,
правила кэша (подписчики 24 ч, выдача 5 мин), правила готовности, критерии приёмки, порядок
проверки на копии боевой базы. Следующий свободный номер ТЗ — 55.

### Фаза 2. Ядро поиска (1,5–2 дня, весь код через jCode)

1. Таблицы в общей базе:
   - `x_search` — задача: `query`, `langs`, `period`, `window_start`, `window_end`, `status`
     (`queued|running|ready|incomplete|failed`), `created_at`, `finished_at`, `note`;
   - `x_search_branch` — ветка RU/EN: `search_id`, `lang`, `cursor`, `page_no`, `position`,
     `status`, `posts_found`, `last_page_at` (позиция пишется после сохранения страницы —
     отсюда возобновляемость после сбоя);
   - `x_search_post` — связь задачи с постами: `search_id`, `content_id`, `branch`, `position`;
   - `x_search_cache` — готовая выдача: `key_hash` (запрос + языки + фильтры + период, без
     сортировки), `search_id`, `collected_at`, `expires_at`.
2. Коллектор в модуле X: страницы Latest по ветке → таблицы `x_search_post` (текст, автор,
   дата, просмотры, подписчики, лайки, ответы, коэффициент) — **в
   `content`/`metric_snapshot`/`content_latest` не пишем ничего** (решение №2 §3: изоляция по
   построению, критерий приёмки 10). Транспорт — twscrape через брокер (`broker.py`), учёт в
   существующем журнале `transport_request` новым видом `kind='search'` со своим суточным
   потолком (решение №3 §3: ≤100 запросов/сут, темп ≤1/5 с): тогда «общая очередь аккаунта с
   учётом лимитов» получается из уже работающего механизма, а инвариант «сеть только через
   брокер» не ломается.
3. Подписчики из ответа с постом — через существующий `set_follower_snapshot`
   (`x/store.py`) со временем замера; логика «моложе 24 часов → берём из базы» общая с
   задачей followers.
4. Коэффициент = `x_search_post.view_count / x_search_post.subs` (процент = ×100); при `subs=0`
   или отсутствии подписчиков — «недоступен», как требует задание. Строку без просмотров
   **не считаем нулём** (спайк: счётчик отстаёт, у свежих постов пусто) — такие строки получают
   пометку «просмотров ещё нет» и в сортировке по коэффициенту уходят вниз.
5. Фильтр выдачи: по умолчанию `-filter:replies` (спайк: Latest возвращает много @-реплаев);
   отдельный флаг задачи «включая ответы».
6. Файл аккаунтов twscrape — в закрытом каталоге с правами `600` (не в `/tmp`, как в спайке:
   он хранит куки открытым текстом).
7. Детектор зацикленного курсора: N одинаковых курсоров или id подряд → ветка помечается
   неполной, прогресс сохраняется.

Критерий приёмки: прогон на **копии** боевой базы; сверка «до/после» по числу строк;
тесты на кэш, на возобновление, на детектор цикла; ноль записей мимо брокера.

### Фаза 3. Веб-слой (1 день)

FastAPI или Flask + одна страница: поле запроса, период, галочки RU/EN, «Найти», строка
состояния, сортировка, таблица результатов (текст, автор, дата и возраст, просмотры,
подписчики, лайки, ответы, коэффициент, процент). Прогресс — опрос раз в секунду.
Два режима сортировки (спайк: у свежих постов просмотров ещё нет, поэтому один режим
нечестен): «свежие» — по времени, коэффициент показываем где он есть; «по коэффициенту» —
по возрастанию отношения, строки без просмотров не считаются нулём и уходят вниз с пометкой.
Галочка «включая ответы» (по умолчанию выключена — `-filter:replies`).
Кнопка «Обновить» обходит кэш готовой выдачи; повторный тот же поиск — из кэша 5 минут;
закрытие страницы задачу не отменяет (её ведёт воркер, не веб-запрос).

### Фаза 4. Публикация и наблюдение (0,5 дня)

systemd-юнит воркера, nginx-локейшн, basic-auth, предохранители (потолок задачи, суточный
потолок аккаунта), сторож: если за сутки не было успешной задачи или ветка висит в
`running` дольше потолка — сообщение владельцу.

### Фаза 5. Второй этап (вне MVP)

Фоновое наблюдение по сохранённым темам и уведомления — по расширению спеки, отдельным ТЗ.

## 5. Критерии приёмки MVP (чеклист по заданию)

1. Запрос по теме возвращает посты за выбранный период, обе ветки языка.
2. Коэффициент и процент показаны у каждого поста; сортировка по коэффициенту, просмотрам,
   дате, лайкам, ответам работает по всей выдаче.
3. Повторный тот же поиск в течение 5 минут отдаётся из базы; границы окна и время сбора
   показаны.
4. «Обновить» запускает новый поиск, кэш авторов при этом сохраняется.
5. RU → RU+EN догружает только EN за тот же период.
6. Закрытие страницы не отменяет задачу; повторный вход подключается к идущему поиску.
7. Сбой, лимит или зацикленный курсор → выдача помечена неполной, прогресс сохранён,
   продолжение после восстановления.
8. Подписчиков нет или 0 → коэффициент показан как недоступный.
9. Репост объединён с оригиналом, цитата считается по своему автору.
10. Посты поиска помечены и не попадают в общие отчёты Tuber.
11. Сессия X не выходит за пределы сервера и не попадает в Git.
12. Приёмка выполнена на копии боевой базы, боевая не тронута.

## 6. Риски и предохранители

| Риск | Предохранитель |
|------|----------------|
| Карантин или бан аккаунта X | один аккаунт на старте, осторожный темп, потолок задач, готовность завести второй |
| Условия использования X для неофициального сбора | зафиксировать осознанное решение владельца до боевого запуска |
| Шум в общей базе | пометка `source_kind='search'`, исключение из отчётов |
| Незавершаемая задача (Latest по слову «AI» бесконечен) | жёсткий потолок: 12 страниц / 300 постов / 8 минут на ветку |
| Зацикливание курсора | детектор повторов → статус «неполная выдача», не тихое зависание |
| asyncio против синхронного sqlite | воркер — отдельный процесс со своим event loop и одним соединением на запись |
| Открытый доступ к поиску по X-данным | TLS (решение №1 §3) + basic-auth + `noindex` + ограничение частоты; порт приложения — только `127.0.0.1` |
| Порт 443 закрыт провайдером снаружи | проверить доступ снаружи до приёмки; запасной путь — 8443 с тем же сертификатом |
| Новый канал поиска окажется вне журнала | обязательное журналирование `kind='search'` + приёмочная проверка «в `transport_request` есть строки нового канала» (урок `fxtwitter`) |
| Просмотров у поста нет (65,5% покрытия в X) | в выдаче честное «просмотров нет», коэффициент помечен как недоступный, такие посты не считаются нулём |

## 7. Что в MVP не входит

Фоновое наблюдение тем и уведомления (Фаза 5), перевод запроса между языками, ручной
перевод текстов постов, экспорт выдачи, публикация результатов куда-либо.

## 9. Бриф для jCode на Фазу 0 (спайк)

Задача: доказать или опровергнуть, что поиск X доступен с нашего аккаунта и отдаёт
просмотры и подписчиков. Скрипт — отдельный файл в `/root/tuber/scripts/x/spike_twscrape.py`,
ничего в боевом коде не менять, в боевую базу не писать.

Шаги: поставить twscrape в отдельный venv; добавить аккаунт куками из
`/root/tuber/config/x_session.json` (`pool.add_account_cookies`); выполнить
`api.search("(AI OR \"artificial intelligence\") lang:en", limit=100)` и то же для `lang:ru`;
для каждого поста собрать `id`, `user.username`, `viewCount`, `user.followersCount`,
`likeCount`, `replyCount`, дату; посчитать коэффициент; напечатать таблицу первых 20 строк
и сводку: сколько постов получено, у скольких есть `viewCount`, у скольких есть подписчики,
на какой странице пришёл отказ, код отказа.

Результат: файл `/root/tuber/docs/hypeparser/SPIKE-twscrape-<дата>.md` с таблицей фактов и
однозначным выводом «можно / можно с ограничением X страниц / нельзя».
