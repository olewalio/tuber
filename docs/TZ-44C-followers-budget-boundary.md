# ТЗ-44C: обход подписчиков не ломается на границе бюджета окна

Дата: 21.09.2026. Ветка: `master`. Один коммит, см. `git log -1`.

## Что было (факт 21.09.2026)

`python3 -m tuber x followers --limit 400` по реестру X (216 активных/кандидатов)
обновил 34 подписчика, затем упёрся в потолок окна (50 запросов / 900 с) и
завершился кодом **1**; в `run_log` — «бюджет окна исчерпан … откат на Nitter».
Каждая следующая попытка считалась «отказом транспорта», хотя это штатный
предохранитель. Обход 216 аккаунтов при потолке окна 50 за прогон физически
невозможен — нужен пейджинг.

## Изменения

1. **`tuber/platforms/x/session.py`**: добавлен подкласс
   `XSessionWindowCap(XSessionRateLimited)`; `_check_budget()` при исчерпании
   ОКНА поднимает его (раньше — общий `XSessionRateLimited`, неотличимый от 429).
   `XSessionDailyCap` уже был. Наследование сохраняет совместимость: старые
   вызывающие ловят `XSessionRateLimited` как прежде.
2. **`tuber/platforms/x/cli.py`, `cmd_followers`**:
   * бюджет окна/суток → счётчик **отложено**, не **отказов**; выход из цикла;
   * в Nitter за подписчиками не ходим вовсе (подписчиков он не отдаёт);
   * итог одной строкой: `подписчики X: обновлено N, отложено M (бюджет окна,
     продолжение после HH:MM:SS UTC), отказов K`;
   * коды возврата: **0** — боевых отказов нет (даже если часть отложена),
     **1** — настоящий отказ (сеть/429/401/403/ответ без профиля),
     **2** — сессия недоступна. Обоснование: 401/403 в ТЗ отнесены к отказам
     («сеть, 401/403/429, ответ без профиля»), поэтому `SessionBlocked` = код 1;
     «сессия недоступна» — отдельный случай отсутствия сессии (код 2).
3. **`scripts/x/tuber_x_followers.sh`** (обёртка ТЗ-44B правится, не переписана):
   * план расширен строкой `pending` — остаток по фактическому состоянию реестра
     (`subs_at IS NULL`), а не счётчик попыток;
   * пока `pending > 0`, обёртка зовёт CLI порциями по остатку окна, спит до
     времени из строки CLI «продолжение после … UTC» (фолбэк — `window_free_at`
     из плана) и повторяет;
   * потолок времени прогона — `RUN_TIME_CAP_MIN=100` минут (env
     `TUBER_X_FOLLOWERS_TIME_CAP_MIN` / `TUBER_X_FOLLOWERS_TIME_CAP_SEC`), сон
     ограничен остатком бюджета времени; по достижении — остановка;
   * итог одной строкой в журнал: `followers done: обновлено=… отложено=…
     отказов=… порций=… время=…s`; наружу сводка — только когда прогон неполный
     (норма молчит, ТЗ-7), при настоящем отказе — только ALERT.
4. **`scripts/x/install_hermes_cron.sh`**: задание `tuber_x_followers.sh`
   (`10 2 * * *`) добавлено в `LAUNCHERS` и `JOBS`. Это закрывает уже висевший
   разрыв D-01: задание было зарегистрировано в планировщике, но не объявлено в
   установщике (тест `test_schedule_sync` это поймал). Тесты установщика
   (`test_tz7`, `test_tz9`, `test_tz11`) обновлены на 13 шимов.

## Проверки

* ПОСЛЕ: **375 passed, 2 xfailed** (+7 новых).

### 2. Реальный прогон по копии боевой базы

Копия снята через sqlite backup API (WAL-консистентно). Окно искусственно
урезано, чтобы показать честную остановку: `TUBER_X_SESSION_WINDOW_CAP=5`,
`TUBER_X_SESSION_WINDOW_SEC=60` (иначе ждать 900 с), `MIN_INTERVAL=1`,
`RATE_MAX=10`.

Прогон 1: `TUBER_DB=<copy> python3 -m tuber x followers --limit 400`

```
подписчики X: обновлено 5, отложено 211 (бюджет окна, продолжение после 12:41:25 UTC), отказов 0
```

Фактический код возврата: **0** (обновлено 5, остальные отложены).

### 3. Продолжение при освобождении окна

Дождались `12:41:25 UTC` и запустили тот же вызов на той же копии:

```
подписчики X: обновлено 5, отложено 211 (бюджет окна, продолжение после 12:42:29 UTC), отказов 0
```

Код возврата: **0**. Обход продолжился с того же места (алфавитно, без повторов):

| прогон | хэндлы |
|---|---|
| 1 | barackobama, bcherny, beshkenadze, bestblogsdev, bitsalumni |
| 2 | bodryachog, botnewsnetwork, bullhooves, bytemohit, bznotes |

Копия базы: `subs_at IS NOT NULL` 34 → 44, `subs_at IS NULL` 182 → 172
(+10 новых снимков за оба прогона).

Отдельно продемонстрирован пейджинг обёртки на копии с
`TUBER_X_FOLLOWERS_LIMIT=8`: три порции (`--limit 3`, `2`, `3`) с ожиданием окна,
итог в журнале — `followers done: обновлено=8 отложено=0 отказов=0 порций=3
время=116s`.

### 4. Боевая `data/tuber.db` не тронута

mtime до и после совпадает: `1789994260`, `2026-09-21 15:37:40.697843817 +0300`
(прогоны шли только по копии). Все проверки — на копии, боевая база не писалась.

## Что не сделано и почему

* Бюджет окна внутри CLI не ожидается: ожидание/пейджинг вынесены в обёртку
  (ТЗ-44C п.5), CLI останавливается и сообщает время продолжения.
* Остаток считается по `subs_at IS NULL` (как предписано ТЗ); повседневное
  обновление уже снятых подписчиков остаётся на ротации `subs_at ASC` и в
  объём этого ТЗ не входит.
* Потолок времени 100 минут проверен юнит-тестом (обёртка останавливается), а не
  100-минутным боевым прогоном: полный обход 216 аккаунтов при демонстрационном
  окне 5/60 с занял бы ~43 минуты, что дороже и ничего нового не проверяет.
