# Сквозные сюжеты: связывание сюжетов между платформами

Дата замера: 17.09.2026 (вторая волна, «качество сквозных сюжетов»). База: **копии
боевой** в `/root/tz5/` (в боевую `/root/tuber/data/tuber.db` исполнитель не
писал). Код: `tuber/analysis/cross_stories.py`, команда
`python3 -m tuber x cross-stories --db <копия>`. Разметка и замер:
`docs/cross-story-labels.jsonl` (старая, 47 пар), `docs/cross-story-labels-240.jsonl`
(новая, 64 пары), `scripts/x_cross_story_eval.py`.

## 1. Проблема

Движок сюжетов X (`tuber/platforms/x/stories.py`, `platform='x'`) — эталон и в
этой задаче не менялся. Сквозные сюжеты (материал одного события с РАЗНЫХ
платформ) строит `tuber/analysis/cross_stories.py`, и первая версия (коммит
`254b40a`) переносила правило X один-в-один. Замер дал precision 0.19 при recall
1.00 на 47 размеченных парах — движок работал, но склеивал разное. Живой прогон
владельца вынужденно шёл на завышенном `--text-min 0.60` (2 сюжета из 16).

Задача второй волны — устранить **причины**, а не поднять порог.

## 2. Причины ложных склеек и что именно устранено

| № | Причина (подтверждено замером) | Что сделано |
|---|---|---|
| 1 | **Насыщение сущностного вклада.** `STORY_ENTITY_IDF_NORM=3.0` делает `ent_part=1.0` почти для любой общей сущности, поэтому ОДНОЙ сущности достаточно для склейки. | В `cross_stories` сущность больше не добавляет к баллу константу. «Значимые» общие сущности (не «гиганты», df ≤ `CROSS_ANCHOR_MAX_DF`) открывают лишь более слабый текстовый порог и только при **≥2 независимых** совпадениях (`CROSS_ENT_MIN=2`). |
| 2 | **Транзитивные склейки.** Средняя связь (UPGMA) тянула цепочку A~B~C при A≁C. | Слияние разрешено, только если ВСЕ кросс-платформенные пары между группами уже приняты (критерий «кросс-платформенного клика», `_cluster`). Пары внутри одной платформы не проверяются, поэтому «три перепоста одного твита» собираются, а цепочка через среднее звено — нет. |
| 3 | **Языковый перекос IDF + асимметричный containment.** IDF считался по англоязычному X-контексту, а близость нормировалась на КОРОТКИЙ пост. Для нелатинских текстов (корейский/китайский режет `_WORD_RE`) и коротких заголовков YouTube это давало `text_part≈1.0` на одном общем слове: пара «Qwen model on apple silicon» ↔ «Yandex weights» имела containment 0.49 при косинусе 0.02. | IDF токенов считается по ВСЕМУ корпусу окна (все языки). Мера — симметричная **TF-IDF-косинусная** (`(1+ln tf)·idf`): ни короткий, ни длинный документ не «раздувает» близость; TF не даёт одному общему слову перевесить повторяющееся событийное содержимое. |

Якорная сущность (для порождения пар) сохраняется: «гиганты» калибруются на
X-контексте (там список стабилен: `anthropic, claude, google, meta, nvidia,
openai`), а частота якоря нормируется абсолютным df ≤ 50 (устойчиво к размеру
корпуса, в отличие от доли).

**Порог.** `--text-min` (default `CROSS_TEXT_MIN=0.30`) не менялся ни по имени, ни
по значению — но теперь применяется к косинусу. Рекомендованный для боевой выдачи
порог — **0.15** (обоснование в §4).

## 3. Старая разметка (47 пар) — контроль, не стало хуже

| конфигурация | сюжетов | precision | recall | F1 |
|---|---|---|---|---|
| до правки (коммит 254b40a, containment) | 16 | 0.19 | 1.00 | 0.32 |
| после, default `--text-min 0.30` | 9 | 0.80 | 0.444 | 0.571 |
| после, `--text-min 0.15` | 14 | 0.67 | 0.667 | 0.667 |

Вывод: на контрольной разметке F1 вырос с 0.32 до 0.57–0.67; хуже не стало.

## 4. Новая независимая разметка (приёмка)

`docs/cross-story-labels-240.jsonl` — **64 пары, окно 240 ч** (не 72 ч, как в
старой!), `now = 2026-09-17T13:38:00Z`, копия `/root/tz5/new240.db`. Каждая пара
размечена вручную с однострочным обоснованием и ссылками-референсами участников
(`a_ref`/`b_ref`, платформа:external_id) — владелец может перепроверить кликом.

**Отличия от старой выборки:** другое окно (240 ч против 72 ч), другая эпоха
содержимого (сентябрьские релизы: ChatGPT Images 2.5, Mistral Series D, AuK
Tencent, отчёт Anthropic о misuse), 64 пары против 47, пересечение по парам —
нулевое.

Выборка построена без подгонки: в неё вошли ВСЕ пары-кандидаты окна с
нетривиальной близостью (`text_min ≥ 0.10`, «правдоподобная область», 49 пар) плюс
15 случайных пар ниже порога. Итог: 35 `same` / 29 `different`.

| конфигурация | сюжетов | precision | recall | F1 |
|---|---|---|---|---|
| default `--text-min 0.30` | 6 | 1.000 | 0.171 | 0.293 |
| `--text-min 0.13` | 17 | 0.815 | 0.629 | 0.710 |
| **`--text-min 0.15` (рекомендация)** | 12 | **0.875** | **0.600** | **0.712** |

**Планка precision ≥ 0.60 при recall ≥ 0.30 достигнута** на рекомендованном
пороге 0.15. На неизменном default 0.30 порог по recall НЕ взят (0.171): правило
намеренно precision-first. Почему default не понижен — см. §6.

### Контроль переобучения (design/test по событиям)

Чтобы порог не был подобран по самой приёмке, новая разметка разбита по СВЯЗНЫМ
компонентам событий (seed 7): design — 43 пары (25 same), отложенный test — 21
пара (10 same). Порог выбирался на design, метрики считались на test:

| половина | precision | recall | F1 |
|---|---|---|---|
| design (порог выбран здесь) | 0.812 | 0.520 | 0.634 |
| **test (отложенная, `--text-min 0.15`)** | **1.000** | **0.800** | **0.889** |

На отложенной части планка также взята (1.00/0.80).

**Честный потолок.** Остаток ошибок — семантический, а не пороговый: сводки и
дайджесты, упоминающие событие в ряду других, а также «разные новости об одной
модели» (Qwen/Grok/DeepMind) лексически неотличимы от «одного события по разным
источникам». Поэтому precision выше 0.9 и recall выше ~0.8 одновременно на этом
материале недостижимы без семантической модели. Что мешает — в §6.

## 5. Ресурсы, целостность, воспроизводимость

* Окно 72 ч: **5.4 с**, **173 МБ** RSS (лимит 60 с / 1 ГБ).
* Окно 240 ч: **14.9 с**, **545 МБ** RSS.
* X не сломан: `story WHERE platform='x'` = **75 сюжетов / 275 участников**,
  множество `(external_id, role, handle)` до и после сквозного прогона идентично.
* Идемпотентность: повторный прогон даёт те же id и состав (`identical: True`).
* Боевая база: `PRAGMA quick_check = ok`. Исполнитель в неё не писал (все прогоны
  на копиях `/root/tz5/`); в боевой `story`/`story_member` без изменений.
* Тесты: полный прогон — **1050 passed, 1 xfailed** (плюс два
  ПРЕДСУЩЕСТВУЮЩИХ падения `tests/*/test_schedule_sync.py` из-за расхождения
  живого реестра планировщика с установщиком — воспроизводятся на чистом коммите
  `254b40a`). Новые тесты механизмов: цепочка A~B~C при A≁C, короткий пост с одним
  общим словом, одна общая сущность.

## 6. Рекомендация и почему default не менялся

Для боевой выдачи рекомендуется **`--text-min 0.15`** (precision 0.875, recall
0.600 на новой разметке; на отложенной половине 1.00/0.80). Значение default
`CROSS_TEXT_MIN` оставлено **0.30 без изменений** — по жёсткому условию ТЗ
(«запрещено менять default text_min»); порог задаётся явно в задании расписания.

Что осталось и что мешает: склейка «событие, упомянутое в дайджесте» и различение
«одна модель — разные новости» требуют семантики; лексических признаков для этого
недостаточно (замер: распределения косинуса у `same` и `different` перекрываются в
полосе 0.13–0.22). Дальнейший рост recall без потери precision — только за счёт
модели (эмбеддинги/LLM-судья), вне рамок этой правки.

## 7. Воспроизведение

```bash
# 1. копии боевой базы (боевую не трогать)
cp /root/tuber/data/tuber.db /root/tz5/my_copy.db
# 2. сквозные сюжеты (X-сюжеты не трогаются)
python3 -m tuber x --db /root/tz5/my_copy.db cross-stories --text-min 0.15
# 3. отчёт: блок 4 непустой
python3 -m tuber report --db /root/tz5/my_copy.db --days 10
# 4. замер на старой разметке (контроль) и новой (приёмка)
python3 scripts/x_cross_story_eval.py --db /root/tz5/my_copy.db \
    --labels docs/cross-story-labels.jsonl
python3 scripts/x_cross_story_eval.py --db /root/tz5/new240.db \
    --labels docs/cross-story-labels-240.jsonl
```
