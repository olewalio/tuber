Реализация: коммит `f2ac029`.

## Что сделано

1. **Связь очередь ↔ реестр (D-55).** Новый модуль
   `tuber/platforms/telegram/linking.py`: канонический ключ хендла
   (`@X` / `t.me/x` / `https://t.me/x` / `x/s` → `x`) и второй ключ `tg_id`
   (`source.external_id` ↔ `candidate.external_id`/`meta_json`). Промоушен
   реестра закрывает найденную строку очереди (`status='promoted'`,
   `promoted_at`, `promoted_by`) либо заводит её (`found_via='registry_promote'`).
   Импорт (`bridge.import_candidates`) и `queue promote`
   (`_reuse_registry_identity`) дедуплицируют по каноническому ключу.
   Идемпотентно: повторный прогон не плодит строк.
2. **Расчёт `vr` при промоушене (D-54).** `promote.compute_vr` считает
   виральность по фактическим постам: медиана просмотров
   (`content.meta_json.views`, запасные `metric_snapshot`/`content_latest`) /
   подписчики × 100. Колонка `source.vr` (заполнялась только при импорте
   `UNIVERSE.csv`) больше не читается. «vr неизвестен» — явное состояние с
   отдельной строкой отчёта.
3. **Калибровка порога.** `PROMOTE_MIN_VR = 15.0` — нижний квартиль
   распределения `vr` по кандидатам с `posts ≥ 20` и `antifraud = 0`
   (Q1 ≈ 14, медиана ≈ 27). Константа и обоснование — в
   `tuber/platforms/telegram/config.py`. Вырождение: если на выборке ≥ 50
   повышаются ВСЕ подряд, боевой прогон отменяется (`rc=3`).
4. **Миля по расписанию.** `scripts/common/tuber_queue_review.sh` (крон 07:50)
   после `queue review` выполняет `tg promote`; `--allow-production` доходит до
   КАЖДОЙ подкоманды; при норме обёртка молчит, при сбое печатает одну ALERT и
   завершается ненулевым кодом.
