Единственный владелец квоты — `channels.ChannelRouter` (`channels.py:1-18`); прямой сетевой вызов только в `broker.raw_http_get` (`broker.py:503`), инвариант подтверждён тестом `tests/x/test_no_direct_network.py`.

**Важно:** `fxtwitter` идёт через `broker.raw_http_get` (single network exit сохранён, `fxtwitter.py:44-51`), но `raw_http_get` **не пишет** в `transport_request` — журналирование живёт только в `NitterBroker._http_get/_run_job` и классах `channels.py`. Итог: канал `fxtwitter` **полностью отсутствует в журнале транспорта** — 0 строк с хостом `api.fxtwitter.com`, при этом его след есть в 8 848 постах (`content.meta_json`, напр. `text_src='fxtwitter'`). Темп держится только константой `FX_MIN_INTERVAL_SEC` внутри `collect.refetch_fulltext_by_id`.

  - `x.com` — 14 725
  - `https://nitter.netbub.com` — 1 347, `https://nitter.kareem.one` — 988 (аварийные/чужие)
  - `syndication.twitter.com` — 33

### 2.3 Журнал `transport_request` и бюджет

- Все запросы (успех и отказ) пишутся в `transport_request` через временное представление `requests` + INSTEAD OF-триггер (`store.py:1370-1399`, `store.py:602-608`). **Пишущая обёртка глотает исключения** (`channels.py:96-103` — `except Exception: pass`) — журнал может терять записи молча. **Канал `fxtwitter` в журнал не пишется вообще** (см. 2.1).
- Общий бюджет сессии X считается **по журналу**, а не по памяти процесса (`session.py:279`, `store.py:685-716`), поэтому он общий для всех процессов-кронов. Гейты: окно `X_SESSION_WINDOW_CAP=50 / X_SESSION_WINDOW_SEC=900`; суточные потолки с раздельным учётом: общий `X_SESSION_DAILY_CAP=1000`, ленты `X_SESSION_FED_DAILY_CAP=800`, точечные задачи `X_SESSION_POINT_DAILY_CAP=200` (`config.py:523-537`).
- У брокера Nitter — свой суточный потолок `DAILY_REQUEST_CAP` на инстанс (`broker.py:683-699`).

## 5. Слабые места и дефекты

1. **N+1 в обогащении.** `enrich.enrich_batch` идёт циклом `for row in rows: router.enrich_tweet(tid)` — **один HTTP-запрос `cdn_tweet` на каждый пост** (`enrich.py:247-250`). Батч до `ENRICH_BATCH=400` постов = до 400 последовательных запросов. Ускорения через `TweetResultsByRestIds` (пакетный GraphQL) в этом пути нет.
2. **Канал `fxtwitter` вне журнала транспорта.** Он ходит через `broker.raw_http_get` (инвариант единственного выхода сохранён), но `raw_http_get` не журналирует: 0 строк `api.fxtwitter.com` в `transport_request`, тогда как след канала — в 8 848 постах. Целый активный канал невидим для наблюдаемости и общего бюджета.
3. **Тихие обрывы (fail-silent).** Несколько мест проглатывают любые исключения: `channels._record_request` (`channels.py:96-103`, `except Exception: pass`) — журнал `transport_request` может недосчитывать; `collect._try_ssr`/`_fetch_ssr` (`collect.py:363-391`) — отказ резерва не виден; `broker._try_session_feed` (`broker.py:943-946`) — отказ сессии превращается в тихий фолбэк на Nitter.
4. **Аварийный резерв `x_ssr` — узкое горло.** Потолок `XSSR_MAX_PER_RUN=50` на прогон; за последние 24 ч резерв израсходовал ровно 50 запросов — то есть по факту резерв был основным каналом минимум для 50 аккаунтов, при том что «безлимитный» он только на бумаге.
5. **Расхождение кода и комментариев о лентах сессии.** `config.py:538-544` утверждает, что ленты через сессию — ОСНОВНОЙ канал (дефолт `X_SESSION_FEDS_ENABLED="1"`), а docstring `broker.py:897-901` заявляет, что они «по умолчанию ВЫКЛЮЧЕНЫ (…=0)». Фактическое поведение — включены. Комментарий устарел → риск неверной диагностики.
6. **Одна личная учётка X = единая точка отказа.** Сессия, лимиты (4 зап/60 с), блок при 403 (24 ч) и суточные потолки завязаны на один `x_session.json`. Блокировка учётки отбрасывает весь точечный транспорт (followers/метрики) на мёртвый Nitter-пул.
7. **Ретраи не бесконечны, но тише всего ломается путь метрик.** CDN: 3 повтора 60/120/240 с (`config.py:271`, `channels.py:224-245`); при `rate_limited` батч обогащения **обрывается на середине** (`enrich.py:274-276`, `break`) — остаток пачки молча откладывается.
8. **`last_seen_at` у постов X не ведётся вообще** (100% NULL) — использовать поле как «капчур-тайм» нельзя, свежесть фиксируется только по `first_seen_at`/`metric_snapshot.captured_at`.
9. **Nitter-пул деградирован по построению:** из 12 инстансов в боевых метриках реально работают 1-2 (`nitter.jaydenha.uk` 53 273 против `kareem.one` 988), остальное — история (см. `session.py:5-7`). Значит основной сбор по факту держится на одном зеркале.

## 6. Выводы

1. Платформа X — крупнейшая по числу постов после YouTube/Telegram, но **самая сложная по транспорту**: данные идут минимум через 6 разных каналов (`nitter_rss`, `nitter_search`, `cdn_tweet`, `synd_timeline`, `x_ssr`, `x_session`/`fxtwitter`).
2. Доказательство сложности: 193 626 записей `transport_request`, распределены между 7 хостами (`cdn.syndication.twimg.com` 119 530; `nitter.jaydenha.uk` 53 273; `x.com` 14 725; …); при этом **8-й активный канал `fxtwitter` в журнал не попадает вообще** (0 строк `api.fxtwitter.com` при 8 848 постах со следом канала) — это прямой дефект наблюдаемости.
3. **Сессия X — уже не «точка», а рабочая лошадка точечных задач:** источник 166 353 из 280 248 снимков метрик X (59%), 501 запрос за 24 ч.
4. Поиск через сессию **не реализован** (нет `SearchTimeline`) — дискавери остаётся на Nitter-поиске, то есть на самом хрупком канале.
5. Данные X **свежие**: `MAX(published_at)=2026-10-06 19:00:17`, `MAX(metric captured_at)=2026-10-06 19:25:48`; приток ~1 807 постов/сутки, ~10 936 снимков метрик/сутки.
6. Покрытие метриками почти полное по постам (99.92% имеют ≥1 снимок), но **просмотры есть лишь у 65.5%** (30 163 из 46 056) — видимо, ограничение канала/даты, а не сбой записи (58.8% снимков с `views`).
7. Качество ключевых полей высокое: NULL по `published_at/links/mentions/url` = 0%; потери только в `text` (~0.40%), `author_handle` (0.23%), `lang` (0.24%).
8. Реестр X разбалансирован: 384 `active` против 410 `candidate` и 323 `rejected`; 909 из 1 267 источников — тир C (редкий обход), реальное ядро — ~352 (тиры A+B).
9. Главный технический долг раздела: **N+1 в `enrich.enrich_batch`** (1 запрос на пост) и **fail-silent обработка ошибок** в журналировании и фолбэках — оба занижают наблюдаемость и создают скрытые задержки.
10. Единая личная учётка X + полуживой Nitter-пул + 100%-NULL `last_seen_at` — три системных ограничения, определяющих потолок надёжности платформы X.
