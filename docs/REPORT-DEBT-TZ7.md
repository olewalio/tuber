## 1. Задача 0 (P0). Команда сквозных сюжетов падала в конце (закрыто)

### 1.1 Причина

`tuber/platforms/x/cli.py` (`cmd_cross_stories`) вызывал старый
**четырёхаргументный** хелпер `unified_report.content_url(platform, external_id,
url, handle)`. После ТЗ-6 хелпер живёт в `tuber/core/urls.py` и принимает **три**
аргумента, а из `tuber/analysis/report.py` был удалён. Живой прогон 17.09.2026
(журнал `/root/.hermes/logs/tuber_x_cross_stories.log`) показал:

```
  сюжет 237 xconf=5 участников=5 платформы=telegram, youtube
AttributeError: module 'tuber.analysis.report' has no attribute 'content_url'
--- код возврата: 1
```

Из-за кода 1 шим отправил владельцу ложную тревогу, хотя сюжеты посчитались.

### 1.2 Что сделано

1. **Единый хелпер с правилом приоритета.** В `tuber/core/urls.py` добавлен
   `material_url(db_url, platform, external_id, handle)`: если `content.url`
   непуст — печатается он; если пуст — синтез через `content_url(...)`; если и
   для синтеза не хватает компонентов — `None` (выдача печатает «нет ссылки»,
   выдуманных ссылок нет).
2. **CLI-путь починен**: `cmd_cross_stories` больше не зовёт удалённый хелпер,
   а использует `urls.material_url(m["url"], m["platform"], m["external_id"],
   handle)`.
3. **Все оставшиеся места синтеза ссылок приведены к единому хелперу** (задача 0.1):
   * `tuber/platforms/x/cli.py` — сквозные сюжеты (главный дефект);
   * `tuber/platforms/x/report.py` — сводный отчёт X: представление `posts`
     теперь отдаёт `content.url`, все блоки печатают его с приоритетом, синтез —
     через `urls.content_url` (прежняя заглушка `handle='i'` устранена);
   * `tuber/platforms/youtube/report.py` — `_video_url` делегирует в общий хелпер;
   * `tuber/platforms/telegram/scoring.py` — `post_url` делегирует в общий хелпер;
   * `tuber/platforms/x/store.py` — в TEMP-представление `posts` добавлена
     колонка `url` из `content.url`.

## 2. Задача 1. D-47: добор метрик YouTube `--fill-gap` (закрытие начато)

### 2.1 Настоящая причина (уточнение формулировки D-47)

`yt viral-refresh` запускается и идемпотентен: пересчёт ~5,3 с, число
посчитанных не меняет, md5 базы меняется только из-за `computed_at`. Дефицит не
в «не запускали», а в том, что **архивные видео не получают метрик**: план
снимков строится по возрастным корзинам (`_fresh_bucket`), и видео старше
`MAX_TRACK_DAYS` (30 суток) из плана выпадает навсегда. Второй оси не появляется
— композитный индекс (минимум две оси) не строится.

### 2.2 Замер исходного состояния (боевая база, read-only; пересчёт на копии)

| Метрика | Значение |
|---------|----------|
| `score` YouTube | 96 116 строк |
| видео с осью виральности | 37 320 |
| `viral_index` посчитан | **15 255** |
| NULL (меньше двух осей) | **22 065** |
| из них: 0 осей | **8 495** |
| из них: 1 ось | **13 570** |
| состав 1-осевой группы | целиком ось `packaging` (упаковка) |
| легаси-эталон `/root/tuber-os/data/tuber.db` | те же 15 255 — перенос ничего не потерял |

### 2.3 Реализация (`yt snapshots --fill-gap N`)

* `--fill-gap N` (N — максимум видео за прогон, `N=0` — выключено);
* кандидаты — видео с меньшим двух осями виральности; приоритет: **одна ось →
  ноль осей**, внутри группы **свежие первыми** (`content.published_at` по
  убыванию), тайбрейк по `video_id`;
* обычный план по корзинам **не меняется** — добор добавляется поверх
  (`bucket_of.setdefault(...)`); слот добора — суточный (`d`, `SOURCE_DAILY`);
* в сводку пишется расчёт числа запросов `videos.list` (пачки по 50) и остаток
  суточной квоты (`YouTubeClient.quota_remaining`);
* частичный сбой батча прогон не роняет (как и в обычном режиме);
* расписание **не изменено** (решение о суточном бюджете — за владельцем).

### 2.4 Живой прогон на копии боевой базы, N=200

```
$ tuber yt --db /tmp/tz7db47b.db snapshots --fill-gap 200
Замеры: по плану 1267, добор архивных 200 (запрошено 200), снято 1407,
батчей 30, сбойных батчей 0, запросов videos.list 30 (остаток квоты 39115).

```

Из 30 запросов на добор приходится **4** (200 / 50), остальные 26 — обычный
план. Затем `yt seo --score-refresh --force` и `yt viral-refresh`. Итог:

| Метрика | До добора | После добора |
|---------|-----------|--------------|
| `indexed` | 15 255 | **15 495** (+240) |
| видео с ≥2 осями | 15 255 | **15 495** |
| 1 ось | 13 570 | 13 330 (−240) |
| 0 осей | 8 495 | 8 495 (без изменений) |
| добранные, получившие ≥2 оси | — | **194 из 200** |

(+240 = 194 добора + 46 от сдвига медиан каналов; 1 видео потеряло вторую ось.)

**0-осевая группа добором не лечится** (отдельный сэмпл 199 свежих 0-осевых
видео дал **0** новых осей). Причина: у этих видео нет базы сравнения канала —
ось «упаковка» требует медианы канала, лайки/комментарии тоже нормируются на
медиану; метрики у них при этом есть (у 5 157 из 8 495 лайки > 0). Это отдельная
задача наполнения базы каналов, поэтому D-47 остаётся открытым.

### 2.5 Рекомендация по суточному бюджету

Квота — не узкое место: 50 видео = 1 unit, весь остаток 13 570 1-осевых ≈ 272
units против порога 8 000 units/сутки на проект. Обычный план расходует ~26
запросов за прогон. **Рекомендуется `--fill-gap 1000` в сутки** (20 units):
при ~97% успеха это закрывает 13 570 1-осевых за ~14 дней и не трогает обычный
план и search-квоту. Для 8 495 0-осевых нужен отдельный подход (база сравнения
каналов). Точное решение — за владельцем после приёмки.

### 2.6 Тесты добора

первыми, лимит N), расчёт числа запросов, отсутствие изменений при `N=0`
(`viral.compute` не вызывается), слот/источник добора, повторный прогон без
