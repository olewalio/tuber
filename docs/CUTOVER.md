# CUTOVER — переключение на единую базу (ТЗ-5)

Коротко: что переключается, что остаётся и как откатиться. Переключение кронов
выполняет **владелец**: реестр заданий планировщика Hermes
(`/root/.hermes/cron/jobs.json`) установщик не трогает.

**Состояние на 17.09.2026:** переключение ВЫПОЛНЕНО внешним контуром. Шимы
монорепо установлены (21, ни один не указывает на legacy), боевая единая база
пересобрана из замороженных снимков, оба новых задания зарегистрированы
(реестр `jobs.json` 99 → 101). Факты, замеры и уроки — ниже и в
`docs/REPORT-TZ5.md` §0a, `docs/acceptance-log-tz5.txt` записи [13]…[18].

## Что переключается

1. **Расписание — одно.** Единственный источник списка заданий —
   `scripts/install_hermes_cron.sh` (блоки `JOBS` / `NEW_JOBS` / `LAUNCHERS`).
   Он пишет шимы в `~/.hermes/scripts/` (обычные файлы, не симлинки), имена и
   времена 19 уже зарегистрированных заданий сохранены как были. Каждый шим
   делегирует в обёртку монорепо (`scripts/x|telegram|youtube|common`), а та
   вызывает `python3 -m tuber yt|x|tg …` либо общие `tuber db backup` /
   `tuber report`.
2. **База — одна.** Все три платформы читают и пишут `data/tuber.db`.
3. **Бэкап — один.** Задание `tuber_db_backup.sh` (новое, регистрирует
   владелец) делает суточный бэкап единой базы и `PRAGMA integrity_check` с
   записью результата в журнал `backup.log` того каталога, куда лёг бэкап
   (по умолчанию `data/backups/`; каталог появляется после первого прогона —
   `ls -lt /root/tuber/data/backups/ 2>/dev/null | head`).
4. **Выдача — одна.** Задание `tuber_report.sh` (новое) собирает объединённый
   отчёт по трём платформам из одной базы. Владельцу планировщик доставляет
   компактную сводку (`tuber report --compact`, ≤3500 байт: заголовок, пункты
   каждой платформы с полными ссылками, сквозной сюжет строкой, подвал со
   счётчиком скрытых и путём к полному файлу). Места делятся справедливо:
   каждому разделу с данными — минимум 1 пункт, остаток бюджета round-robin.
   Полный отчёт по-прежнему ложится файлом в `reports/` и целиком идёт в журнал.
5. **Фиды моста** живут в `data/exchange/` монорепо. Каталог и файлы создаёт
   первая же обработка мостов (`tuber yt candidates-import` /
   `tuber tg bridge import`), поэтому проверять их надо командой, а не по имени
   файла: `ls -l /root/tuber/data/exchange/ 2>/dev/null`.

## Порядок переключения (владелец)

Копию реестра планировщика снимать **ПЕРВЫМ шагом** — ДО
`install_hermes_cron.sh`, иначе откатывать будет нечего. Имя снятой копии
записать в раздел «Копии реестра планировщика» этого документа.

```bash
cd /root/tuber

# 1. ПЕРВЫМ делом — свежая копия реестра планировщика (боевой jobs.json не правим):
cp /root/.hermes/cron/jobs.json \
   /root/.hermes/cron/jobs.json.bak-cutover-$(date +%Y%m%d-%H%M%S)
ls -lt /root/.hermes/cron/jobs.json.bak-* | head   # какие копии реально есть

bash scripts/install_hermes_cron.sh --dry-run    # 2. список «до»
bash scripts/install_hermes_cron.sh              # 3. записать шимы монорепо
python3 -m tuber doctor                          # схема/интерпретатор/база
bash scripts/cutover_prepare.sh --dry-run        # 4. план пересборки базы
bash scripts/cutover_prepare.sh                  # 5. страховка + пересборка из снимков legacy
```

6. Зарегистрировать в планировщике **новые** задания (блок
   «ТРЕБУЕТСЯ РЕГИСТРАЦИЯ ВЛАДЕЛЬЦЕМ» из вывода установщика):
   - `tuber_db_backup.sh` — `0 5 * * *`;
   - `tuber_report.sh` — `0 8 * * *`.
7. Выключить кроны старых проектов (tuber-os / tuber-x / tuber-telegram) —
   это и есть точка «старые проекты перестали собирать данные».
8. Сверить: `pytest -q tests/test_schedule_sync.py` — зелёный.

## Уроки фактического переключения (17.09.2026)

Пересборка боевой базы выполнена внешним контуром. Два урока, которые надо
учесть в процедуре (шаг 5 «страховка + пересборка из снимков legacy»):

1. **Длинные шаги пересборки запускать в транзиентном systemd-юните**
   (`systemd-run --unit=tz5-cutover …`), а не прямо в контуре гейтвея.
   Факт: первый прогон `cutover_prepare.sh` был прерван **рестартом гейтвея**
   (процесс жил в его контуре), база осталась недособранной. Повторный прогон в
   транзиентном юните `tz5-cutover.service` завершился штатно. Юнит
   транзиентный — после завершения его в `systemctl` уже нет, поэтому факт
   фиксируется в журнале прогона, а не в `systemctl status`.
2. **Откат не понадобился.** Все шаги из разделов «Что остаётся» и «Как
   откатиться» выполнены не были: legacy-базы не восстанавливались, реестр
   `jobs.json` не откатывался, шимы legacy-проектов не переустанавливались.
   Проверки этих разделов делались только на существование путей и копий (см.
   `docs/acceptance-log-tz5.txt` [9]); фактического отката не было.

## Копии реестра планировщика

Реестр `/root/.hermes/cron/jobs.json` принадлежит планировщику; его правит
только владелец. Перед переключением владелец снимает копию (шаг 1 выше) и
вписывает её имя сюда.

Копия переключения от 17.09.2026 (99 заданий, снята владельцем):

    /root/.hermes/cron/jobs.json.bak-cutover-20260917-103941

Установщик шимов `jobs.json` не менял: 99 заданий до и после установки, ноль
добавленных и ноль удалённых (сверка по имени/расписанию/скрипту со снимком
`/root/tz5/cron_before.json`). Затем владелец зарегистрировал два новых задания
монорепо, поэтому **боевой реестр содержит 101 задание** (`tuber_db_backup.sh`
`0 5 * * *`, `tuber_report.sh` `0 8 * * *`). Копия для отката при этом хранит
исходные 99 заданий.

Какие копии реально лежат — не угадывать по имени, а посмотреть:

    ls -lt /root/.hermes/cron/jobs.json.bak-* | head

## Что остаётся (страховка, 2 недели)

- Старые проекты `/root/tuber-os`, `/root/tuber-x`, `/root/tuber-telegram` и их
  боевые базы — **не удаляются**, лежат как есть.
- Замороженные снимки legacy этапа переключения — каталог
  `data/cutover_snapshots/` (создаёт `cutover_prepare.sh`); проверить:
  `ls -lt /root/tuber/data/cutover_snapshots/ 2>/dev/null | head`.

  `ls -lt /root/tuber/data/backups/ 2>/dev/null | head`.

## Как откатиться

Откат возвращает старые кроны и старую выдачу (окно страховки — 2 недели).
Процедура воспроизводимая: имена копий не угадываются, а берутся из `ls`.
**Перед откатом обязательна проверка выбранной копии.**

```bash
# 1. Посмотреть, какие копии реестра реально есть (свежие сверху):
ls -lt /root/.hermes/cron/jobs.json.bak-* | head

# 2. Выбрать копию (подставить реальное имя из вывода выше) и проверить её:
BAK=/root/.hermes/cron/jobs.json.bak-cutover-20260917-103941
test -e "$BAK" && echo "есть: $BAK" || echo "НЕТ файла: $BAK — откат не делать"
python3 -c "import json;d=json.load(open('$BAK'));print('заданий:',len(d.get('jobs',d)))"
# ожидаем ровно 99 заданий; если файла нет или заданий не 99 — СТОП, откат не делать.

# 3. Вернуть реестр заданий Hermes (имена/скрипты старых проектов):
cp "$BAK" /root/.hermes/cron/jobs.json

# 4. Вернуть шимы старых проектов их установщиками:
bash /root/tuber-os/scripts/install_hermes_cron.sh
bash /root/tuber-x/scripts/install_hermes_cron.sh
bash /root/tuber-telegram/scripts/install_hermes_cron.sh

# 5. Старые базы не тронуты — коллекторы продолжают писать в них.
```

Если откат нужен только для единой базы, восстановите её из страховочной
копии, которую `tuber db backup` кладёт в `data/backups/` (каталог появляется
после `cutover_prepare.sh`; список — `ls -lt /root/tuber/data/backups/ 2>/dev/null | head`).
