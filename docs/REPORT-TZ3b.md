## 1. D-27 — тайбрейк в отчёте X: воспроизведение порядка legacy

### 1.1. Причина расхождения

`_primary_post`/`_story_claim` выбирали «первый/лучший пост сюжета» сортировкой
**только по времени**:

```sql
... FROM story_posts sp JOIN posts p ON p.tweet_id=sp.tweet_id
WHERE sp.story_id=? ORDER BY p.published_at_utc ASC LIMIT 1
```

У сюжета 87 два поста @Cointelegraph имеют **одну и ту же секунду**
(`published_at_utc = 2026-09-15T13:25:00`):

| tweet_id | роль в legacy `story_posts` | `content_id` в ядре |
|---|---|---|
| `2099851980843925762` | `primary` | 34519 |
| `2099851981557035395` | `echo` | 34517 |

При равном ключе выбор диктует план запроса.

### 1.2. План legacy и ключ, дающий его результат

`EXPLAIN QUERY PLAN` legacy (замороженная копия, SQLite 3.53.1):

```
|--SEARCH sp USING COVERING INDEX sqlite_autoindex_story_posts_1 (story_id=?)
|--SEARCH p USING INDEX sqlite_autoindex_posts_1 (tweet_id=?)
|--SEARCH a USING INTEGER PRIMARY KEY (rowid=?) LEFT-JOIN
`--USE TEMP B-TREE FOR ORDER BY
```

`story_posts` в legacy объявлена как `PRIMARY KEY (story_id, tweet_id)`, поэтому
скан по `story_id` идёт по автоиндексу `(story_id, tweet_id)` — **в порядке
`tweet_id` ASC**. Сортировка по времени получает строки уже в этом порядке и
(устойчиво) отдаёт первым кандидата с меньшим `tweet_id`:
`2099851980843925762` (лексикографически `'...084...' < '...155...'`).

Это не «похоже на DESC» и не догадка: правило — **тайбрейк по `tweet_id` ASC**,
и оно совпадает с тем, что уже делает кластеризация X:
`stories.cluster_posts`/`assign_roles` сортируют
`(published_at_utc, str(tweet_id))` (`stories.py:256/297/346/430`). То есть
назначение роли `primary` и «первый пост» отчёта были согласованы в legacy, а в
адаптере разъехались: ядро читает `story_member` по `(story_id, content_id)`, а
`content_id` — это **порядок вставки в `content`** (порядок миграции), не
семантический.

### 1.3. Что сделано

Тайбрейк объявлен явно в новом коде (legacy не менялся):

* `tuber/platforms/x/report.py` — `_FIRST_POST_ORDER = " ORDER BY
  p.published_at_utc ASC, p.tweet_id ASC LIMIT 1"` для `_primary_post` и
  `_story_claim`;
* `tuber/platforms/x/stories.py` — тот же вторичный ключ в выборке окна сюжетов
  и в чтении `story_posts`.

Явный ключ делает выбор **воспроизводимым** и не зависящим от плана запроса и
порядка строк; результат при этом — тот же, что у legacy.

### 1.4. Проверка

Методика — `scripts/acceptance/x_compare_reports.py` на замороженных копиях
(`/tmp/v-x.db` и единая база, пересобранная из `/tmp/v-os.db`, `/tmp/v-tg.db`):

* отчёт legacy — 62 строки, отчёт монорепо — 62 строки, `diff` пуст
  (**0 строк расхождения**);
* **3 прогона на каждую сторону — одинаковый md5** (`637acb68…`, 6/6 прогонов);
* `parity` X — 17 правил, `+0`;
* скорость отчёта: legacy 0.12–0.13 с, монорепо 0.17 с, отношение **1.36–1.40×**
  (< 2×).

Полный вывод — `docs/x/acceptance-log-tz3b.txt`.

Регресс-тест: `tests/x/test_report_tiebreak.py` (3 теста). Вставляет в сюжет два
кандидата с равным временем **в порядке, при котором без тайбрейка побеждает
неверный**, и проверяет: выбран меньший `tweet_id`; зачин сюжета (`_story_claim`)
— его же; результат не зависит от порядка вставки. Проверено: при удалении
`p.tweet_id ASC` из `_FIRST_POST_ORDER` **все 3 теста падают**.

## 2. D-24 — `run_log` без платформы

### 2.1. Диагностика

Ядровая `run_log` привязана к `run`, у которого `platform` есть. Но код X пишет
в журнал и **вне прогона** (`run_id IS NULL`: предупреждения брокера о 429,
потолках квоты, cooldown). Принадлежность таких строк можно было вывести только
«по допущению» («в `run_log` пишет только X»), а правило parity
`JOIN run … platform='x'` их вообще не считало. Первая третья платформа сделала
бы сверку недостоверной.

Проверка родственных таблиц:

| Таблица | `platform` | Вердикт |
|---|---|---|
| `run` | есть | ок |
| `metrics_daily` | есть (PK `day, platform`) | ок |
| `classify_daily` | есть (PK `day, platform`) | ок |
| `report_text` | нет | **дефекта нет**: ключ `text_hash`, текст платформо-независим |
| `run_log` | **не было** | **чинилось здесь** |

### 2.2. Что сделано

* Аддитивная колонка `run_log.platform` (+ индекс `idx_run_log_platform`),
  `SCHEMA_VERSION` 3 → **4**. Пишут её: ядерная `storage.log_run(…, platform=…)`,
  миграция (`platform='x'`/`'telegram'`), адаптер X (`store.log_run` и триггер
  представления).
* Представление X `run_log` переведено на `WHERE platform='x'` — без допущения
  о `run_id IS NULL`.
* Правила parity `x.run_log`/`tg.run_log` — на колонку:
  `SELECT COUNT(*) FROM run_log WHERE platform='x'` (JOIN run убран).

### 2.3. Идемпотентный бэкфилл

`tuber.core.schema.backfill_run_log_platform` (вызывается из `migrate_schema`):

1. **по `run_id`** → `run.platform` (строки внутри прогона);
2. **по провенансу `legacy_map`** → для строк **без связи** (`run_id IS NULL`):
   `legacy_map(legacy_table='run_log').legacy_db` знает исходную legacy-базу
   (`x`/`tg`/`os`). Это **точнее догадки по времени**: строка могла быть
   записана между прогонами;
3. **остаток** честно остаётся `NULL` и возвращается числом `remaining` —
   платформа не выдумывается.

Числа:

| База | Строк | по `run_id` | по `legacy_map` | остаток NULL |
|---|---|---|---|---|
| копия боевой `data/tuber.db` (v1) | 7 630 | 7 630 | 0 | **0** |
| пересобранная из `/tmp/v-*.db` | 8 136 | 8 136 | 0 | **0** |

(в пересобранной: `x` 1 611 + `telegram` 6 525). Повторный `migrate` — **0
изменений** на каждом шаге.

### 2.4. Доказательство, что допущение убрано

На копии пересобранной базы добавлены по одной внепрогонной строке (`run_id
NULL`) для X и Telegram:

| Правило | X | Telegram |
|---|---|---|
| старое (`JOIN run`) | 1 611 | 6 525 |
| новое (`platform=`) | **1 612** | **6 526** |

Старое правило обе внепрогонные строки не видит; новое видит их явно.

### 2.5. Скорость и планы

```
ядро  main.run_log WHERE platform='x':
  SEARCH main.run_log USING COVERING INDEX idx_run_log_platform (platform=?)
представление X run_log (COUNT):
  SEARCH rl USING COVERING INDEX idx_run_log_platform (platform=?)
```

`MATERIALIZE` нет ни в одном плане (тест проверяет это автоматически).

### 2.6. Тесты

* `tests/core/test_run_log_platform.py` (7): колонка/индекс + `required_columns`,
  бэкфилл по `run_id`, бэкфилл строк без связи по `legacy_map`, идемпотентность,
  0 NULL после миграции синтетического набора, правила parity без `JOIN run`,
  `EXPLAIN` без `MATERIALIZE`.
* `tests/x/test_run_log_platform.py` (2): адаптер пишет `platform='x'`;
  представление X не показывает строку чужой платформы.
* `tests/migration/test_migration.py` — обновлено ожидание результата
  `migrate_schema` (добавлен ключ `run_log_platform`).

## 3. Красный legacy-тест → известный дефект

`tests/x/test_story_pairs.py::test_required_different_pairs_not_glued` падает:

```
AssertionError: 2099679599542382696 и 2099793800147390574 склеены, а это разные события
  assert 4 != 4
```

Это **не регрессия переноса**: то же сообщение, те же id, то же место
(`test_story_pairs.py:101`) воспроизводится в legacy `/root/tuber-x`. Тест
помечен `@pytest.mark.xfail(strict=True, …)` с причиной и ссылкой на новый долг
**D-31** в `TECH-DEBT.md`:

* `pytest -q` снова зелёный (907 passed, 1 xfailed);
* падение видно как **известный дефект** (`XFAIL` с причиной в `-rx`), а не как
  норма;
* `strict=True`: как только пару разъединят, тест станет `XPASS` и **потребует
  снять пометку**, а не «незаметно позеленеет».

Суть дефекта и что чинить — в `TECH-DEBT.md` § D-31 (правило
`stories.cluster_posts`/`_pair_score`: у пары общий сильный признак, которого не
хватает для разделения; подгонять правило под обязательную пару запрещено —
это ломает `test_new_rule_beats_old_rule`).

## 7. Найденное попутно (не входило в ТЗ)

**Разные версии SQLite в окружении.** `/usr/bin/python3` (3.12.3, SQLite
**3.45.1**) не создаёт TEMP-триггеры адаптера X с `INSERT INTO main.…` в теле —
`sqlite3.OperationalError: qualified table names are not allowed on INSERT,
UPDATE, and DELETE statements within triggers`. `python3` из venv
(`/usr/local/lib/hermes-agent/venv/bin/python3`, SQLite **3.53.1**) их создаёт, и
именно им гоняются тесты и приёмка. Вся работа велась `python3` (venv).
Рекомендация: закрепить интерпретатор в обёртках/расписании (ТЗ-5), иначе
запуск «голым» `/usr/bin/python3` уронит X-контур на первом же соединении.
Это не регрессия ТЗ-3b и не чинилось (вне объёма).
