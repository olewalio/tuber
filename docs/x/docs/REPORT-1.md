## 3. Что не получилось и почему

### 3.1. Противоречие в Р2 по постам без разобранной даты

ТЗ одновременно требует:
* `published_at_utc TEXT NOT NULL` и инвариант «не пустой, не `1970-*`, не будущее > 2 ч»;
* «при неудаче статус `unknown` и пост НЕ попадает выборки отчёта».

Пост со статусом `unknown` не может иметь непустую валидную дату, значит строку в `posts`
вставить нельзя. Р9 запрещает записывать «сегодня» вместо даты.

Решение (выбрано сознательно): **пост с неразобранной датой не пишется в `posts`
и не попадает в `published_src`**; он считается в счётчике прогона `skipped_no_date` и
показывается в отчёте `collect`. Так инвариант Р2 держится жёстко (П5 = 100%), а неверная
дата не выдумывается. Побочный эффект: `published_src='unknown'` в БД в норме не встречается.
Проверка полноты Р6.1 такие посты тоже не считает «новыми id» (иначе П4 был бы вечно красным).

На фикстуре: 8 item → 7 записано, 1 отброшен по дате. На живых данных за сутки: отброшено 0.

### 3.2. Р4.3.2 недостижим внутри ТЗ-1

Порог «≥ 2 разных авторов из доверенного ядра упоминали хендл» требует, чтобы доверенное
ядро (tier A/B, `status='active'`) уже существовало. Наполняет ядро дискавери из **ТЗ-2**,
которого в этой работе нет. Поэтому на живых данных все проверки дают
`cooccurrence_lt_2` — это не дефект кода, а следствие порядка этапов.

Факт (`registry verify nasa`, живой прогон):

```
@nasa: ОТКЛОНЁН — cooccurrence_lt_2
  items=20 авторов_ядра=0 (-)
  постов/сутки=4.28 cv=1.99 ссылки=0.38 ретвиты=0.37 дубли=0.0
    OK  items_ge_15      OK  posts_per_day_in_range   OK  link_ratio_ok
    OK  cv_ok            OK  dup_ratio_ok              OK  rt_ratio_ok
    FAIL cooccurrence_ge_2
```

Пять порогов из шести на живом аккаунте проходят, шестой ждёт ТЗ-2. Реализация Р4.3
проверяется в тестах (`test_registry_validate.py`, по одному тесту на каждый отказ,
включая co-occurrence, посчитанный по `posts.mentions` и `posts.orig_handle`).

### 3.3. `collect` обходит и `candidate`

Р5 говорит «обход по тирам», Р4.2 оставляет добавленный хендл в статусе `candidate`.
Если обходить только `active`, приёмка П3 (`registry add nasa` → `collect`) физически
не даёт постов, а измерять кандидата для Р4.3 нечем. Обход идёт по
`status IN ('active','candidate')`; `dead`/`blocked`/`rejected` не обходятся.
`verdict` `rejected` (как у `nasa` после `registry verify`) исключает аккаунт из обхода — см. лог.

### 3.4. Коллизия health-эндпоинта и аккаунта `nasa`

Р3.4 предписывает health через `GET /nasa/rss`. Это ровно тот же URL, что лента аккаунта
`@nasa`. В коде коллизии нет (health идёт отдельным путём с `kind='health'`), но в
тестовой заглушке транспорта этот путь перехватывается как health, поэтому тесты
используют хендлы, отличные от `nasa`.

### 3.5. Окружение: сломанный сторонний pytest-плагин

`python3 -m pytest` падал **до сбора тестов** из-за несовместимого плагина
`pytest_ethereum` (пакет web3, `ImportError: cannot import name 'ContractName' from
'eth_typing'`). К проекту он отношения не имеет. Добавлен `pytest.ini` с
`addopts = -p no:pytest_ethereum`; ничего вне `/root/tuber-x` не менялось (Р9).

### 3.6. Один 429 на живом health-запросе (транзиент)

В первом же прогоне health к `nitter.kareem.one` вернул 429. Обработано по Р3.5:
cooldown инстанса, автоматический переход на `nitter.jaydenha.uk`, сбор выполнен без
потерь. 429 возникает и на health-запросе, поэтому обработка 429/403 добавлена и в
`check_instance`, а не только в обход. За меренный период (25 запросов) доля 429 = 0%.

### 3.7. Приоритеты: preemption не реализован

Р3.7 («при перегрузке сначала обслуживаются старшие») реализован приоритетной очередью:
планировщик всегда выбирает готовую задачу с наименьшим приоритетным номером
(`critical > collect > discover > backfill`), а неготовые по времени задачи не блокируют
готовые младшие. Уже **начатый** запрос не вытесняется (нет отмены in-flight HTTP);
с учётом того, что прогоны по крону последовательны, практического эффекта это не имеет.
Проверяется тестом `test_priority_order`.

## 4. Поведение, зафиксированное на живых данных

* Заголовок курсора приходит именно как `min-id` в нижнем регистре; `?cursor=<min-id>`
  отдаёт страницу назад. Проверено: 3 страницы `@nasa` = 20+14+20 = 54 item, 0 пересечений.
* `x-nitter-backend: red` пишется в `instances.version`.
* Item в ленте: `title, dc:creator, description, pubDate, guid, link` — метрик
  вовлечённости нет, как и зафиксировано в методологии §2.
* Ретвит: `title` = `RT by @<владелец ленты>: ...`, `dc:creator` = автор оригинала.
  Разбор подтверждён на живых лентах `@OpenAI` и `@GoogleDeepMind`.
* 152 поста, распределение: `is_retweet=27`, `is_quote=2`, `is_reply=19`,
  `media: photo=102, video=35, gif=0`, посты со ссылками = 36, разных `owner_handle` = 2,
  разных `orig_handle` = 14.
* Снежфлейк-фолбэк на живых данных не потребовался (все 152 даты пришли валидным
  `pubDate`); фолбэк и отбраковка 1970/будущего проверены фикстурой и тестами.
* Расход: 152 поста за 25 запросов ≈ 6 постов на запрос. При суточном потолке
  18 000 запросов на инстанс это ≫ потенциального объёма ТЗ-1 (200 аккаунтов TIER-A
  = 4 800 зап/сутки), то есть потолок не является узким местом на этом этапе.

## 5. Рекомендации

1. **ТЗ-2 обязателен перед боем**: без доверенного ядра реестр не растёт (Р4.3.2 всегда
   ложь), и `collect` будет обходить только вручную добавленные кандидаты.
2. **Зафиксировать трактовку §3.1** в методологии: «пост без восстановимой даты не
   хранится, а считается в `skipped_no_date`». Если заказчик хочет видеть такие посты,
   нужно разрешить `published_at_utc IS NULL` и отфильтровывать их в выборках отчёта.
3. **Понизить потолок прироста active** с 50/сутки для первых недель: качество
   валидатора на живых данных ещё не проверено (пороги взяты из методологии §6).
4. **Не поднимать частоту обхода** до перевода CryptoGraph на брокер: лимит канала
   общий (методология §4). Текущий расход 0.09% — запас есть, но демон CryptoGraph
   реестром 3181 аккаунта продолжает долбить `kareem.one`.
5. **Поставить сторожей в расписание** (Р11 этапов): обход без крона = тихий простой
   27.08–14.09.2026 с потерей 96% постов.
6. Мониторить `metrics_daily.valid_date_ratio`: если он упадёт ниже 1.0 после включения
   сбора, значит в лентах появились битые `pubDate` и снежфлейк-фолбэк не справляется
   (возможен мусорный `guid`).
