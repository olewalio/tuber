## Найденные проблемы и наблюдения

1. **Молчаливый сбор тира A был реальной миной.** Старое `TIER="${1:-A}"` при
   запуске из планировщика без аргументов собирало бы тир A вместо B/C — тихая
   порча данных. Теперь это ошибка с кодом 2.
2. **Дублирующее расписание.** Установщик сознательно не пишет в crontab и не
   создаёт заданий: регистрацию выполняет заказчик. Иначе можно получить два
   параллельных сбора по одному и тому же тиру.
3. **Тревога сторожа.** В системном crontab почты нет — раньше строки `ALERT`
   уходили в никуда. В Hermes они доставляются в Telegram; в документе это
   зафиксировано как ограничение способа 7-а.
4. **Живая БД меняется посторонним процессом (важно для приёмки).** Во время
   первого прогона приёмки снимок рабочей БД «ДО/ПОСЛЕ» разошёлся
   (`classified` 275→315). Причину установили по `ps`: независимый процесс
   (`bash -lic … txz_chain_prod.log`, PID 1238593) в это время выполнял боевую
   цепочку `classify → scores → report` прямо на рабочей БД. Приёмка к этому
   непричастна: она пишет только в копию и в журналы. Чтобы сравнение было
   честным, инструмент до и после работы **ждёт окно тишины** (пока отпечаток
   рабочей БД перестанет меняться); в тихом окне снимки совпали, строка — ДА.
   Это же наблюдение подтверждает: регистрацию заданий должен координировать
   заказчик, чтобы не плодить конкурентов за одну БД.
5. **`tuber_x_health.sh` пишет в БД** (`run_log`/`runs`) — поэтому в приёмке он
   запускался с `TUBER_X_DB=<копия>`. На рабочей БД его запускать безопасно: он
   пишет только служебные записи, постов не меняет.
