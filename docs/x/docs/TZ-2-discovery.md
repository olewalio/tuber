# ТЗ-2 — Tuber-x: дискавери и рост реестра

Предусловие: ТЗ-1 (`docs/TZ-1-core.md`) выполнен и принят. Работать в `/root/tuber-x`,
использовать брокер и схемы из ТЗ-1. Никаких прямых запросов в Nitter мимо брокера.

## Р1. Ядро запросов (таксономия дискавери)

Файл `tuber_x/seeds.py` — словарь рубрик по методологии §8. Для каждой рубрики:

```
{
  'рубрика': 'вайб-кодинг',
  'queries_ru': [...],   # 2–4 запроса на русском
  'queries_en': [...],   # 2–4 запроса на английском
  'priority': 1..3,       # 1 — самые ценные
  'quota_per_day': N      # бюджет запросов в сутки на рубрику
}
```

Требования:

Р1.1. Рубрики: релизы моделей · агенты и автоматизация · вайб-кодинг · инструменты
разработчика · инфраструктура и железо · инвестиции и раунды · регулирование ·
исследования и бенчмарки · кейсы внедрения · скандалы и риски.

Р1.2. Операторы X, использовать разрешённые и проверенные (работают в RSS):

```
since:<дата> until:<дата>   окно по времени
min_faves:N min_retweets:N  порог (осторожно: молча режет выборку)
lang:ru lang:en             язык
-filter:replies             без ответов
filter:media                НЕ ИСПОЛЬЗОВАТЬ (в замере отдаёт устаревшее)
from:<handle>               лента аккаунта через поиск
```

Р1.3. Суммарный дневной бюджет дискавери — не более 120 запросов (методология §10).
Проверка бюджета перед прогоном, при исчерпании — прогон пропускается с записью в `run_log`.

Р1.4. Русские запросы обязаны присутствовать во всех рубриках (русский срез — требование
продукта); при этом английские дают основной объём.

## Р2. Цикл дискавери (`discover.py`)

Р2.1. Порядок: рубрики по приоритету, внутри — запросы по кругу, по одному запросу за раз.

Р2.2. Для каждого запроса: `fetch_search(query, cursor=...)` из брокера. Если у запроса есть
сохранённый курсор и остался бюджет — допускается вторая страница (не более 2 страниц на
запрос за прогон).

Р2.3. Из постов извлекаются кандидаты четырёх видов, с пометкой происхождения:

| Вид | Откуда берётся | `found_via` |
|---|---|---|
| автор поста | `owner_handle` | `author:<рубрика>` |
| автор оригинала при ретвите/цитате | `orig_handle` | `orig:<рубрика>` |
| упомянутый | `mentions[]` | `mention:<рубрика>` |
| автор ссылки | домен/хендл из `links[]`, если это `x.com/<handle>` | `link:<рубрика>` |

Р2.4. Запись кандидата в таблицу `candidates`: при первом появлении `seen_count=1`,
`distinct_sources=1`; при повторном — `seen_count += 1`, `last_seen_at` обновляется,
`distinct_sources` увеличивается, если источник (аккаунт-наблюдатель + вид находки) новый.

Р2.5. Отбрасывание на входе: невалидный хендл, служебные (`search`, `explore`, `i`, `home`),
уже в `accounts`, в стоп-листе `tuber_x/blocklist.py` (заводится пустым, пополняется
вручную и по отклонениям).

Р2.6. Дедупликация кандидатов — по `handle` (PK). Один и тот же хендл из разных рубрик
даёт рост `distinct_sources`, а не вторую запись.

## Р2-БИС. Bootstrap: пока доверенное ядро пусто (обязательно)

**Дефект, найденный на живых данных 15.09.2026.** Процедура Р4.3 ТЗ-1 требует «≥ 2 разных
авторов доверенного ядра упоминали хендл», а доверенное ядро — это `accounts.status='active'`
(`tuber_x/registry.py:220,234`). Новый аккаунт получает `active` только через ту же проверку
(`registry.py:336`). Итог: при пустом ядре **каждый** кандидат отклоняется и ядро не может
появиться никогда. Факт: `python3 -m tuber_x.cli registry verify nasa` → `FAIL cooccurrence_ge_2`;
в БД `accounts` ноль строк со статусом `active` (`nasa` — `rejected`, `cointelegraph` — `candidate`).

**Решение: трёхступенчатый статус.**

| Статус | Как получается | Что разрешено |
|--------|----------------|---------------|
| `candidate` | найден дискавери, стоит в очереди | ничего, кроме повторных проверок |
| `provisional` | прошёл **пять** порогов Р4.3, кроме `cooccurrence_ge_2` | сбор постов (тир C), участие в графе упоминаний |
| `active` | (а) 2 упоминания от ядра **или** (б) ≥ 14 дней непрерывного сбора при `ai_density ≥ 0.5` и нуле нарушений качества | тир A/B, полный вес в скоринге |

Р2-БИС.1. Упоминание засчитывается от аккаунта `active`, **и** от `provisional`, если у того
уже ≥ 10 собранных постов и `ai_density ≥ 0.5`. Это и есть разрыв замкнутого круга.

Р2-БИС.2. Фаза bootstrap: пока `count(active) < 20`, переход `provisional → active`
разрешается только по пути (б) — 14 дней. После 20 активных путь (б) требует ещё и
отсутствия `reject_reason` за последние 30 дней.

Р2-БИС.3. Ограничители против накрутки графа: не более 300 `provisional` одновременно;
самоупоминания не считаются; повторные упоминания от одного автора считаются один раз;
кандидаты с шаблоном спама (см. Р3) в граф не попадают.

Р2-БИС.4. Каждое решение о смене статуса пишется в `run_log` с указанием пути промоушена
(`by=core_mentions|by_tenure`) и фактических чисел порога — чтобы промоушен был проверяем.

**Замеры дискавери, на которых строятся пороги (15.09.2026, живые запросы к `nitter.kareem.one`):**
5 поисковых запросов по ИИ-темам → 96 постов → **91 уникальный автор** (18,2 автора на запрос),
курсор `min-id` присутствует на всех запросах, отказов 0, время ответа 1,4–2,3 с.
Скрипт замера: `/tmp/xx_probeG_discovery.py`.

## Р3. Скоринг очереди кандидатов (в `registry.py`)

```
приоритет = distinct_sources
          + 3 × (встречался у аккаунтов TIER-A)
          + 2 × (рубрика приоритета 1)
          + 1 × (найден среди авторов, а не только в упоминаниях)
          − 2 × (совпадение с шаблоном спама: handle из цифр, длина ≥ 13 с длинной цифровой частью)
```

Р3.1. Верификацию проходят верхние `--max-verify` кандидатов (по умолчанию 30 в сутки).

Р3.2. Верификация = процедура Р4.3 ТЗ-1 (шесть порогов). Результат: `active` или `rejected`
с причиной; отказ пишется в `blocklist` только для причин `bad_handle`, `not_found`,
`bot_pattern`, `duplicate_content` — чтобы не проверять их повторно каждый день.

Р3.3. Потолок прироста 50 `active` в сутки (ТЗ-1 Р4.4) остаётся в силе; лишние остаются
в очереди с приоритетом.

Р3.4. Для принятых аккаунтов назначить тир:
`A` — если `ai_density ≥ 0.7` и постов/сутки ≥ 1 и не более 200 таких мест;
`B` — если `ai_density ≥ 0.5`, до 1000 мест; остальные — `C`.

## Р4. Измерение тематической плотности

Р4.1. Для каждого нового аккаунта `ai_density` считается по его последним 20 постам
(одна лента, уже получена при верификации) — доля постов, отнесённых классификатором
к ИИ-теме. До появления классификатора (ТЗ-3) допускается предварительная оценка
по ключевым индикаторам, с обязательной пометкой `ai_density_src='heuristic'` и
пересчётом после ТЗ-3.

Р4.2. Признаки для эвристики (по одному баллу): наличие в тексте `ai`, `llm`, `gpt`,
`agent`, `model`, `prompt`, `нейросет`, `ии`, `модель`, `агент`, `промпт`; ссылки на
`arxiv.org`, `huggingface.co`, `github.com`, `openai.com`, `anthropic.com`, `deepmind`,
`ai.google`, `techcrunch.com`. Это временная мера, она НЕ является классификатором
(семантическое решение остаётся за моделью, ТЗ-3).

## Р5. Отчёт о росте реестра (`cli discover --report`)

## Р6. Тесты (pytest, сеть подменена фикстурами `tests/fixtures/search_*.xml`)

1. `test_extract_candidates` — из фикстуры поиска извлекаются автор, автор оригинала,
   упоминания и ссылки; `found_via` расставлен верно.
2. `test_candidates_dedup` — повторная находка увеличивает `seen_count` и
   `distinct_sources`, но не создаёт вторую запись.
3. `test_blocklist` — служебные и отклонённые хендлы не попадают в реестр.
4. `test_priority_score` — приоритет растёт от TIER-A-источника и рубрики 1, падает от
   спам-шаблона (минимум 3 проверки с конкретными числами).
5. `test_verify_thresholds` — шесть порогов ТЗ-1 проверяются на границах.
6. `test_daily_growth_cap` — при 60 валидных кандидатах `active` становится не больше 50.
7. `test_discovery_budget` — при исчерпанном бюджете прогон завершается без запросов и
   пишет причину в `run_log`.

## Р7. Приёмка (живые данные)

| # | Проверка | Команда | Порог |

| П2 | Извлечение из живого поиска | SQL: `distinct_sources > 1` | ≥ 10 кандидатов с 2+ источниками |
| П3 | Верификация **без ядра** (bootstrap) | `cli registry verify --max-verify 10` | ≥ 5 аккаунтов в статусе `provisional` с заполненными признаками, отказов по `cooccurrence_ge_2` при этом **ноль** (порог не применяется до появления ядра) |
| П4 | Русские запросы дают результат | `cli discover --lang ru --budget 6` | ≥ 10 русскоязычных кандидатов (проверяется по текстам постов) |
| П5 | Потолок роста | SQL по `accounts` за сутки | ≤ 50 новых `active` (плюс ≤ 300 `provisional` одновременно) |
| П6 | Тесты | `pytest tests -q` | все зелёные |
| П7 | Отчёт о росте | `cli discover --report` | печатает все разделы Р5, цифры непустые |

| П9 | Промоушен путём «б» | `cli registry promote --simulate-tenure --days 14` — **только на копии БД** (проверено 15.09.2026: прогон по рабочей базе сделал ядро фиктивным) | ≥ 1 аккаунт с непрерывным сбором становится `active` **в копии**, в `run_log` `by=tenure`; рабочая БД не меняется |
| П10 | Ни один кандидат не отклонён только из-за пустого ядра | SQL по `run_log` за прогон | 0 отказов с причиной `cooccurrence_lt_2` при `count(active)+count(provisional) = 0` |
| П11 | Приёмка не пишет в рабочую базу | до и после всего прогона приёмки: `SELECT status, COUNT(*) FROM accounts GROUP BY status` | набор статусов не изменился; в частности `active = 0`, пока ядро не набрано реальными данными |
| П12 | Аккаунт без единого собранного поста не повышается | тест на фикстуре: `provisional` с `posts_collected = 0` → промоушен по тенуру | отказано, в `run_log` запись об отказе «нет собранных постов» |

**Правило приёмки (ТЗ-2-ФИКС).** Приёмочные проверки, меняющие статусы, выполняются ТОЛЬКО
на копии БД. Рабочая база после приёмки обязана иметь `active = 0`, пока ядро не набрано
реальными данными; рабочую базу во время приёмки разрешено только читать.

## Р8. Запрещено

- Искать людей напрямую (`f=users` запрещён на уровне Nitter, отдаёт 400).
- Обходить блок-лист «ручными» правками БД: пополнять только через `blocklist.py`.
- Принимать аккаунт в реестр без записи причины находки.
- Повышать дневной бюджет дискавери без замера расхода (`cli budget`).
- **Выполнять приёмочные проверки, меняющие статусы, на рабочей базе.** Любая симуляция
  (`--simulate-tenure` и подобные) идёт на копии файла БД; рабочая база во время приёмки —
  только для чтения. Причина: 15.09.2026 прогон приёмки по рабочей базе повысил 14 аккаунтов
  в `active` с отмотанной на 14 дней назад датой и `posts_collected = 0` — доверенное ядро
  реестра стало фиктивным, и от него уже считались бы упоминания остальных кандидатов.
- **Повышать аккаунт в `active` при `posts_collected = 0`.** Ядро — это аккаунты с реальной
  историей сбора, а не записи в таблице.
