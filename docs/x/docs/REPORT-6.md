  Это единственный изменённый существующий тест: его исходное утверждение

## Задача 2. Обёртки classify и report + ключ модели

Добавлены `scripts/tuber_x_classify.sh` и `scripts/tuber_x_report.sh`:

* `classify`: один прогон `cli classify`. **Дневной потолок `CLASSIFY_DAILY_CAP`
  (400 постов/сутки) соблюдает сам CLI**: без явного `--limit` берётся ровно

* `report`: `cli report` — файл `reports/YYYY-MM-DD.md` + наполнение
  `report_texts`. Отчёт обязан отработать каждый день (см. задачу 3).
* Обе обёртки берут `DEEPSEEK_API_KEY` только из окружения; если переменной нет
  — подгружают из `/root/.hermes/.env`, **не печатая значение** (ни в stdout, ни
  в журнал). Никаких ключей в коде.
* В норме обёртки молчат в stdout: вывод уходит в
  `/root/.hermes/logs/tuber_x_{classify,report}.log`; код возврата 0.
* `scripts/tuber_x_scores.sh` уточнён: перед `scores` запускает `stories`
  (кластеризация — обязательный вход отчёта).
* `health` по-прежнему печатает только строки `ALERT`.

### Найденная поломка (важно)

Шаг `stories` в ежедневной цепочке **падал**: `cli stories` после печати
таблицы обращался к `summary["dry_run"]`, которого в сводке `stories.run` не
было, и завершался `KeyError: 'dry_run'` (код 1). Это ломало `scores`-обёртку и,
значит, отчёт. Исправлено:

* `stories.run(..., dry_run=False)` теперь возвращает ключ `dry_run` и при
  `dry_run=True` считает сюжеты, **не записывая** их в БД;
* `cli cmd_stories` передаёт `dry_run=args.dry_run`.

Новые тесты: `test_stories_cli_does_not_crash_and_reports_dry_run`,
`test_stories_dry_run_writes_nothing`.

## Задача 5. Аудит путей отката/записи в рабочую БД

Что искали: `restore`, «откат», `snapshot`, `copy2` на `config.DB_PATH`,
копирование поверх рабочей БД, `.restore(`, `sqlite3 ... .restore`, `cp/mv` на
рабочую БД, скрипты с именем `*restore*`/`*откат*`.

**Найдено в репозитории:** опасных путей **нет** (0). Единственная операция
копирования с участием рабочей БД — `shutil.copy2(config.DB_PATH, <временный
путь>)` в `cli._simulate_tenure_on_copy`; источник только читается, приёмник —
временный каталог, и есть проверка `realpath(copy) == prod`. Приёмочные
инструменты (`acceptance_tz3/4/5/6`) копируют рабочую БД в `/tmp` через backup
API и пишут только туда. Скриптов восстановления из снимка в репозитории нет.

**Что сделано:**

* добавлены `db.production_path()`, `db.is_production_db(path)`,
  `db.ensure_not_production_db(path, action)` — общий предохранитель «не писать в
  рабочую БД»; применён в `_simulate_tenure_on_copy` (дополнительно к прежней
  проверке);
* добавлен `tools/audit_writeback.py` — сканер репозитория на опасные шаблоны;
  текущий результат: `опасных=0`, `читающих копий=1`, просканировано 72 файла;
* новые тесты: `test_db_guard_refuses_production_path`,
  `test_audit_finds_no_writeback_or_rollback_paths`,
  `test_repo_has_no_restore_scripts`.

**Причина инцидента 15.09.2026 (484 → 152).** Это был **не** скрипт репозитория.
Историю восстановили по журналам сессий: в сессии (`session_sloth`,
15.09.2026 ~10:46) агент вручную «restore the prod DB to its original state»,
то есть внешней командой скопировал снимок поверх живой базы, затёр живой сбор.
Артефакты этого ручного отката лежали в `/root/.jcode/scratch/`:

* `prod_snapshot_before_restore.db` (+`-wal`/`-shm`) — 1 462 272 байта, 484 поста,
  18 прогонов, `sha256 effd37600064b4f1db90a4c7a9c77fad5b9a4b5d7a61620521cae5132df5078a`;
* ad-hoc мониторинговые скрипты `prod_monitor.py`, `envprobe.py` вокруг рабочей БД.

Эти лежалые артефакты отката (источник будущего «снимок поверх живой базы»)
**удалены**. Рабочая БД при этом не трогалась и осталась цела (484 поста).

## Что не получилось / ограничения

1. **`report_texts` в приёмке = 0 строк.** Механизм перевода работает (это
   доказано тестом `test_report_translates_and_caches_in_report_texts`), но на
   данных копии главный блок за сутки 2026-09-15 пуст: нет не-одиночных сюжетов
   с публикацией именно в этот день и текстом для перевода, поэтому переводить
   было нечего. Это честное «нет данных за сутки», а не сбой; блок 7 приводит
   фактический ноль.
2. **Один существующий тест изменён** (`test_classify_prefilter_marks_heuristic_not_classified`):
   его логика противоречила новому требованию «предфильтр выключен по
   умолчанию». Тест сохранён, но проверяет режим с явным `--prefilter`.
3. **Обёртки не зарегистрированы в планировщике автоматически** — по требованию
   задания строки расписания приводит заказчик (в `docs/schedule.md`), установка
   в планировщике Hermes — его шаг.
4. **Аудит статический**: `tools/audit_writeback.py` ищет заданные шаблоны
   (copy поверх prod, `.restore`, `cp/mv` на БД, имена `*restore*`). Он не
   доказывает отсутствие произвольного внешнего отката — именно поэтому к нему
   добавлен рантайм-предохранитель в `db.py` и удалены лежалые снимки.
5. Живой прогон `synd-snapshot` в рамках этой работы не повторялся (канал
   разовый, бюджет 5 запросов/сутки) — вне задач ТЗ-6.
