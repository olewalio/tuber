# ТЗ-10: аварийное переключение на резервный источник без потери аккаунтов

Дата: 15.09.2026. Исполнитель: jCode (`--local`). Репозиторий: `/root/tuber-x`.
Коммит кода: `ТЗ-10: резерв включается по факту отказов сбора в том же прогоне`.

## 1. Что было (воспроизведение дефекта)

Замер заказчика 15.09.2026 на **копии** боевой базы: все инстансы Nitter заменены
мёртвым адресом (`http://127.0.0.1:9`), затем штатный `collect --tier C`:

```
1-й прогон:  аккаунтов: 2 ok=1 fail=1 ... x_ssr=1
   @cointelegraph  ОТКАЗ: исчерпаны попытки (3) (fail_streak=1, status=candidate)
   @justinsuntron  items=9 ...  <- пошёл через резерв
2-4 прогоны: x_ssr=2, ok=2
Другой замер (сразу после пометки инстанса нездоровым):
   аккаунтов: 2 ok=0 fail=2 x_ssr=0
   оба: ОТКАЗ: нет живых инстансов Nitter (cooldown/блок/потолок), fail_streak=1
```

Резерв работал, но включался с запаздыванием (до получаса), и первый аккаунт
каждого «слепого» окна терялся. Дефект в коде:

1. `nitter_broker._pick_instance` пропускал инстанс со свежей отметкой «нездоров»
   (моложе `HEALTH_TTL_SEC` = 600 с) — повторных фактических попыток не было;
2. `_run_job` при отсутствии живых инстансов ставил `NoLiveInstance` и выходил,
   НЕ увеличивая счётчик отказов;
3. `fail_streak` рос только в health-пробе и не чаще раза в `HEALTH_TTL_SEC`, а
   `all_degraded()` требовал `>= 3` по **каждому** инстансу — чтобы включить
   резерв, нужно ~3 цикла проб.

**Собственный контрольный замер ДО** (ревизия `5e4b1de`, реальный мёртвый адрес,
резерв подменён мок-транспортом, 2 аккаунта):

```
аккаунтов=2 ok=0 fail=2 x_ssr=0 резерв=0 потеряно=2
   @acct0  ОТКАЗ: нет живых инстансов Nitter (cooldown/блок/потолок)
   @acct1  ОТКАЗ: нет живых инстансов Nitter (cooldown/блок/потолок)
   all_degraded=False reserve_calls=0
```

## 2. Что сделано

### 2.1. Считаются фактические отказы сбора, а не только пробы (`nitter_broker.py`, `db.py`)

* Новый счётчик `instances.collect_fail_streak` (переживает перезапуск). Растёт
  на транспортном отказе (соединение отклонено/таймаут/DNS/обрыв чтения), на
  5xx и на `NoLiveInstance`; обнуляется успешным фидом (`HTTP 200`).
* Ограничение «не чаще раза в `HEALTH_TTL_SEC`» осталось только для health-проб:
  фактический отказ считается всегда. Попыткой запроса считается только реальный
  запрос ленты — ожидания лимитера её не расходуют (`job.attempts` инкрементится
  непосредственно перед запросом).
* 404 и пустая лента (0 item) отказом НЕ являются: счётчик не растёт, резерв не
  включается. Для этого введены типизированные ошибки: `NitterTransportError`,
  `NitterNotFound`, `EmptyFeedError` (все — наследники `NitterError`),
  `NoLiveInstance`.
* Свежая отметка «нездоров» больше не исключает инстанс в `_pick_instance`.
* Деградация (`all_degraded`) — сумма фактических отказов по всем инстансам
  `>= XSSR_DEGRADED_STREAK` (3): один прогон, где аккаунт исчерпал повторы, уже
  включает резерв. Health-пробы по-прежнему не чаще раза в TTL.

### 2.2. Переключение на резерв без потери аккаунтов (`collect.py`, `config.py`)

* Если Nitter отказал по аккаунту после штатных повторов, а инстансы
  деградировали — аккаунт добирается через `x_ssr` **в том же прогоне**.
* Nitter остаётся первым всегда; резерв — только после фактического отказа по
  конкретному аккаунту. Единичный сбой не переводит систему на резерв целиком:
  через резерв идёт только сломавшийся аккаунт.
* `NoLiveInstance` даёт право на резерв (инстансов нет вообще = деградация);
  `NitterTransportError` — право на резерв при деградации; 404/пустая лента —
  резерв не включают.
* Потолок `config.XSSR_MAX_PER_RUN` (по умолчанию 50) на прогон; пауза между
  запросами резерва `config.XSSR_MIN_INTERVAL_SEC` = 2.0 с (было 1.0).
* Правила ТЗ-4 по тексту резерва сохранены: `text_src=None`, текст Nitter не
  перезаписывается, метрики не выдумываются.

### 2.3. Наблюдаемость (`cli.py`, `health.py`, `channels.py`)

* Итоговая строка `collect` печатает: `аккаунтов_через_резерв`, `отказов_Nitter`,
  `потеряно` (цель 0), `потолок`, `причина`.
* `health.py`: проверка «резерв x_ssr активен дольше 6 ч» (`HEALTH_XSSR_ACTIVE_HOURS`)
  печатает `ALERT`; проверка «фактических отказов сбора Nitter за час больше
  порога» (`HEALTH_COLLECT_FAIL_PER_HOUR` = 20) — тоже `ALERT`. В норме — тишина.
* Момент включения резерва хранится в `instances(host='x.com').reserve_since`
  (ставится первым обращением к `x_ssr`, снимается первым успешным фидом Nitter).

### 2.4. Схема БД (`db.py`)

`SCHEMA_VERSION` 3 → 6: у `instances` добавлены `collect_fail_streak` и
`reserve_since`. Миграция идемпотентна, `_ensure_columns` не падает на урезанных
базах без нужной таблицы. Схема применяется **на копии**; боевая база приёмкой
не изменялась.

## 6. Ограничения и рекомендации

* Живой `x.com` в приёмке не дёргался: резерв подменён мок-транспортом (внешняя
  сеть и платный трафик запрещены). Nitter при этом настоящий — реальный
  мёртвый адрес; отказы воспроизводятся честно.
* `all_degraded` теперь считает СУММУ фактических отказов, а не «>= порога по
  каждому инстансу». Это сознательное изменение ради нулевых потерь: при 2
  инстансах один упавший аккаунт распределяет свои отказы между ними, и старое
  правило «по каждому» не срабатывало.
* Потолок резерва по умолчанию 50 обращений/прогон при паузе ≥ 2 с: даже при
  полном отказе Nitter прогон не выходит за измеренный темп x.com.
* Рекомендация на будущее: если Nitter будет лежать штатно, рассмотреть
  автоматическое письмо владельцу (сейчас только `ALERT` сторожа в Telegram) и
  отдельный счётчик `metrics_daily` для доли аккаунтов, добранных резервом.
