### Р2 + Р2-БИС — цикл дискавери и трёхступенчатый статус (`tuber_x/discover.py`, `registry.py`)
- Порядок рубрик по приоритету, по одному запросу за раз (Р2.1); вторая страница по
  курсору, не более 2 страниц на запрос (Р2.2).
- Извлечение кандидатов 4 видов с `found_via` (Р2.3): `author|orig|mention|link:<рубрика>`.
- Дедуп по `handle` (PK), рост `seen_count` и `distinct_sources` по ключу
  «вид:рубрика|наблюдатель» (Р2.4/Р2.6).
- Отбраковка на входе (Р2.5): невалидный хендл, служебные (`search`, `explore`, `i`,
  `home`, …), уже в `accounts`, стоп-лист `tuber_x/blocklist.py`.
- **Р2-БИС исполнен**: `candidate → provisional → active`.
  - `candidate → provisional`: пройдены пять порогов Р4.3, `cooccurrence_ge_2` НЕ применяется.
  - `active` по пути (а) `core_mentions`: ≥2 засчитанных упоминания (Р2-БИС.1: от `active`
    **и** от `provisional` с ≥10 постами и `ai_density ≥ 0.5`); самоупоминания не считаются,
    повторы одного автора — один раз, спам-хендлы и стоп-лист в граф не входят (Р2-БИС.3).
  - `active` по пути (б) `by_tenure`: ≥14 дней `provisional` при `ai_density ≥ 0.5` и
    отсутствии нарушений качества (Р2-БИС.2).
  - Фаза bootstrap (`count(active) < 20`): для **provisional → active** путь (а) закрыт,
    работает только (б); путь «кандидат → active по упоминаниям» открыт всегда — именно он
    разрывает замкнутый круг в фазе bootstrap (П8). Ограничители: ≤300 `provisional`
    одновременно, дневной потолок 50 `active` (Р3.3). Каждый промоушен пишется в `run_log`
    с `by=core_mentions|by=tenure` и фактическими числами (Р2-БИС.4).

### Р3 — скоринг очереди и тиры (`registry.py`)
`priority = distinct_sources + 3·(TIER-A источники) + 2·(рубрика приоритета 1)
+ 1·(найден среди авторов) − 2·(спам-шаблон)`. Верифицируются верхние `--max-verify`
(по умолчанию 30). Причины отказа `bad_handle/not_found/bot_pattern/duplicate_content`
пополняют стоп-лист (Р3.2). Тиры: A — `ai_density ≥ 0.7` и ≥1 пост/сутки (до 200 мест),
B — `ai_density ≥ 0.5` (до 1000), иначе C (Р3.4).

`heuristic` до появления классификатора ТЗ-3.

Простыми строками, без эмодзи.

## 3. Что не получилось и почему

1. **П4 с первой попытки провалился (0 постов).** Причина: первые RU-запросы были из
   3–4 токенов с AND (`новая модель ИИ релиз since:... lang:ru`), Nitter возвращал пусто.
   Замер на живом поиске показал, что 1–2 токена отдают 17–20 item, а 3–4 — ноль.
   Запросы сведены к двум токенам (`ИИ релиз`, `нейросеть модель`, …), П4 перезапущен:
   59 ru-кандидатов. Вывод: русский поиск в Nitter узкий по AND — подтверждает §12
   методологии («русский срез только через реестр»).
2. **П3 «в прогоне» дал 3 provisional, а не ≥5.** Порог П3 выполняется по состоянию БД
   (17 provisional с заполненными признаками). Причина малого числа в самом прогоне:
   верх очереди — высокочастотные новостные боты, у них `posts_per_day > 20` → отказ
   `posts_per_day_out_of_range` (18 из 24 отказов). Это ожидаемое поведение порога Р4.3.3.
3. **Бюджет.** Дневной бюджет (120) соблюдён. Ограничение «≤20 поисковых запросов за
   прогон» соблюдено в каждом прогоне (П1 — ровно 20, П4 — 6). Суммарно за приёмку ушло
   40 search-запросов, т.к. помимо двух приёмочных прогонов были 8 диагностических
   проб для разбора П4 (см. п.1) и повтор П4. Каждый запрос шёл с паузой ≥2 с через
   лимитер брокера.
4. **Тонкость интерпретации Р2-БИС.2.** Формулировка «пока `count(active) < 20`,
   переход `provisional → active` только по пути (б)» реализована буквально для
   `provisional → active`. При этом путь (а) для **кандидата** (candidate → active по
   2 упоминаниям provisional) оставлен открытым и в bootstrap — иначе П8 («разрыв
   замкнутого круга, путь а») был бы невозможен до появления 20 active, а Р2-БИС.1
   («упоминание provisional засчитывается») не имело бы смысла. Это зафиксировано как
   открытый вопрос (см. §5) и покрыто тестом `test_bootstrap_blocks_provisional_mention_promotion`.

## 4. Обратная совместимость

72 теста ТЗ-1 остались зелёными; изменены **два** теста, обоснованно:
`test_verify_account_rejects_without_core_backing` → `…_provisional_without_core_backing`
(это и был дефект: при пустом ядре отказ `cooccurrence_lt_2` заменён на `provisional`);
`test_daily_cap_keeps_candidate` → `…_keeps_out_of_active` (при исчерпанном потолке
прошедший пороги кандидат остаётся `provisional`, а не `candidate`). Логика под тесты
не подгонялась. `collect.py` теперь обходит и `provisional` (тир C) — иначе provisional
не наберёт 10 постов для графа упоминаний.

## 5. Открытые вопросы / рекомендации

1. **Р2-БИС.2**: нужна ли симметрия — закрывать путь (а) и для кандидатов в bootstrap?
   Текущее решение (открыт) выбрано ради П8 и Р2-БИС.1. Если ужесточать — П8 придётся
   тестировать на 20+ active.
2. **Русский срез**: поиск по русским запросам отдаёт устаревшее и узкое; продукту нужен
   русский срез через реестр (§7/§12 методологии), а не через `lang:ru`-поиск.
3. **Миграция статуса `candidate` в БД ТЗ-1**: аккаунт `cointelegraph` остался в статусе
   `candidate` (не был в очереди дискавери). Стоит решить, считать ли его очередью
   верификации автоматически.
4. **`ai_density` — эвристика** до ТЗ-3; пороги тира и tenure завязаны на неё. После
   классификатора пороги нужно перепроверить (поле перезаписывается с src='classifier').
5. **`distinct_sources`** для поискового дискавери считается по ключу «вид:рубрика|наблюдатель»;
   при переходе на поаккаунтный снежный ком (ТЗ-4) наблюдатель станет реальным аккаунтом —
   ключи совместимы.
