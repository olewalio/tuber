# ТЗ-12 — доставка суточной сводки владельцу и честность при неуспехе

Дата: 2026-09-15. Проект: Tuber-x (`/root/tuber-x`, ветка `master`).
Журнал прогона с доказательствами: `docs/acceptance-log-12.txt`.
Приёмка ТЗ-9 (затронутый инструмент): `docs/acceptance-log-9.txt`.

## 1. Что было сломано

Задание планировщика `Tuber-x: сводный отчёт` (job `a3a782010a06`, `no_agent`,
`0 7 * * *`) доставляло владельцу ровно то, что обёртка напечатала в stdout.
Обёртка `scripts/tuber_x_report.sh` печатала пустоту (весь вывод уходил в
`/root/.hermes/logs/tuber_x_report.log`), поэтому планировщик писал
`agent returned [SILENT] — skipping delivery`: отчёт существовал файлом на
сервере, но владелец не получал ничего. Требование ТЗ-4 («report — 1 раз в
сутки, утром, выдача владельцу») не выполнялось, при этом статус задания был
`ok`, а `last_delivery_error` пуст.

## 2. Что изменено

### 2.1. `scripts/tuber_x_report.sh` (обёртка; бизнес-логика не тронута)

Доставка (Р1.1). При успешной сборке в stdout идёт компактная сводка:

```
Tuber-x, сводка за 2026-09-15
Главное за сутки:
1. AI-стартап Flam привлёк $40 млн в раунде Series B во главе с QED Investors; Шах Рук Хан присоединился к раунду
   автор: @chandrarsrikant
   ссылка: https://x.com/chandrarsrikant/status/2099789614395556279
Сюжетов за сутки: 24. Постов в базе: 548. Отказы сбора: 1.6%. Квота Nitter: 927 запросов (2.58% от потолка). Кандидатов в реестре: 1407. Полный файл: /root/tuber-x/reports/2026-09-15.md
```

Лимит (Р1.2). Длина stdout ≤ 3500 знаков. При превышении отбрасываются ЦЕЛЫЕ
сюжеты (с пометкой «... ещё N сюжетов — в полном файле»); обрезка посреди
строки или посреди ссылки не делается никогда, длина строки «ссылка:»
проверяется регуляркой на полный URL.

Честность при неуспехе (Р1.3). Любой из случаев — CLI вернул непустой код,
файл отчёта за дату не создан, вывод не распознан как отчёт за эту дату —
печатает в stdout строку
`ALERT Tuber-x: отчёт за <дата> не собран: <причина>` и завершает работу кодом
0. Молчание при неуспехе невозможно.

Журнал (Р1.4). Полный вывод CLI, stderr, код возврата и режим по-прежнему идут
в `/root/.hermes/logs/tuber_x_report.log`; служебная строка
`=== ... report ===` пишется только туда.

Без перезаписи (Р1.5). Режим выбирается по факту: без аргумента и файла отчёта
за сегодня нет — обычный прогон (файл создаётся); без аргумента и файл уже есть
— прогон `--stdout-only` (сводка считается по текущей базе, файл не трогается);
с аргументом-датой — явный прогон за дату, файл перезаписывается.

Попутно закрыта ловушка, из-за которой «неуспех» выглядел успехом: `db.connect`
сам создаёт каталоги и пустую базу по пути из `TUBER_X_DB`. Обёртка теперь
проверяет базу ДО запуска CLI (файл существует, читается, содержит ядро схемы
`posts`/`accounts`/`stories`) и объявляет ALERT, если базы нет. Без этой
проверки прогон с недоступной базой печатал «нет данных за сутки» и нули —
бодрую пустую сводку вместо сигнала о поломке.

### 2.2. `tools/acceptance_tz9.py` (приёмочный инструмент ТЗ-9)

Список ожидаемых шимов больше не хардкодится. Источник истины — реестр
механизмов, блок `LAUNCHERS=(...)` в `scripts/install_hermes_cron.sh`, по
которому установщик создаёт файлы; из него выводится и число шимов (сейчас 11),
и ожидаемая команда каждого. Добавлены две проверки:

* [0] реестр разобран (иначе инструмент останавливается с объяснением, а не
  подставляет число);
* [12] реестр и каталог `scripts/tuber_x_*.sh` согласованы попарно: рецепт без
  шима и шим без рецепта — отдельные явные ошибки.

Пропавший шим теперь называется по имени («отсутствует: tuber_x_scores.sh») и
даёт FAIL. Dryrun-проверка расширена с трёх тиров на все шимы реестра.
Сообщения и итоговая строка содержат число из реестра, а не константу 10.

## 4. Что нашлось по дороге

1. **Обрыв блока сюжетов на сюжете «2.» и «7.».** Первая версия разбора главного
   блока останавливалась на строке, начинающейся с `2.`, и теряла все сюжеты,
   начиная со второго. Нашлось на синтетическом отчёте (в боевом за сутки был
   один сюжет, дефект не проявлялся). Исправлено: границей блока считается
   только строка без отступа.
2. **Пустая база вместо ошибки.** `db.connect` создаёт базу и каталоги молча,
   поэтому недоступная база давала «успешный» отчёт из «нет данных». Это
   отдельный класс дефекта того же рода, что и основной: неуспех выглядел
   благополучием. Закрыто проверкой базы до запуска.
3. **Перезапись утреннего отчёта.** Прогон 18:17 (до правки) перезаписал
   `reports/2026-09-15.md` свежим состоянием базы — файл в рабочем дереве
   отличался от закоммиченного. Так как ТЗ-12 запрещает перезапись при
   повторном прогоне за ту же дату, случайная перезапись отменена
   (`git checkout -- reports/2026-09-15.md`), файл снова соответствует
   утреннему отчёту; после правки повторные прогоны его не касаются.

## 5. Ограничения

1. **Доставка проверена через тик планировщика, а не `cronjob action=run`.**
   `cronjob action=run` выполняется в отдельном процессе и идёт запасным
   HTTP-путём (`tools/send_message_tool._send_to_platform`): у машины нет
   прямого egress к `api.telegram.org` (`Timed out`), а прокси окружения
   отвечает `407 Proxy Authentication Required`. Доставку владельцу делает
   живой адаптер шлюза, поэтому задание поставлено на ближайший тик
   (`cron.jobs.trigger_job`, выставляет `next_run_at = сейчас`), и его выполнил
   работающий шлюз: в журнале `delivered to telegram:<chat_id> via live adapter`.
   Расписание при этом не менялось и `next_run_at` пересчитан планировщиком на
   следующий штатный запуск 07:00. Штатный утренний запуск 07:00 идёт тем же
   путём (тик шлюза), что и проверенный.
2. **Сводка усечена содержательно, а не формально.** Показываются не «все
   сюжеты в пределах лимита», а до 5 из главного блока (как и требует Р1.1).
   Если один блок сюжета сам длиннее 3500 знаков (на живых данных это
   невозможно: перевод ограничен ~30 словами), сюжет не показывается вовсе —
   резать строку и ссылку запрещено.
3. **«Сюжетов за сутки» и «постов в базе» обёртка считает сама** (запрос
   только на чтение, окно суток — `report.day_bounds`, формат времени —
   `db.iso`), потому что отчёт этих чисел не печатает. Остальные цифры сводки
   разбираются из служебного блока отчёта; если формат блока изменится,
   сводка покажет `н/д`, а не выдуманное число.
4. **Тестов на обёртку не добавлено** (ТЗ-12 разрешает правки только в обёртке,
   приёмочном инструменте и документах), поэтому поведение сводки закреплено
   приёмочным журналом и разбором синтетических отчётов, а не `pytest`.
   Существующий тест `tests/test_tz6.py` по-прежнему требует, чтобы вывод CLI
   уходил в журнал (`>>"$LOG"`) — это сохранено.
5. **Сторож свежести отчёта** (`health.py`) проверяет файл, а не факт доставки;
   так как сводка теперь реально доставляется, расхождение «файл есть — сводки
   нет» закрыто на уровне задания, но сам сторож по-прежнему не знает о факте
   доставки (отдельный пункт техдолга, в ТЗ-12 не входил).
