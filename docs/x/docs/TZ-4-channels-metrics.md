## 2. Реализация

### 2.1 `tuber_x/channels.py` — единый роутер каналов
Обязан стать **единственным владельцем квоты всех каналов** (расширение роли `nitter_broker.py`
из ТЗ-1). Никакой другой модуль не делает сетевых запросов.

Для каждого канала — свой лимитер и своё состояние в БД:

| Канал | Темп по умолчанию | Жёсткие правила |
|-------|-------------------|-----------------|
| `nitter_rss`, `nitter_search` | 8 зап / 30 с на инстанс, cooldown на 429 | как в ТЗ-1 |
| `cdn_tweet` | 2 зап/с, пауза 0,35 с между запросами | при 429 — пауза 60 с, повторов не более 3 |
| `synd_timeline` | **бюджет на окно**: не более 5 запросов, затем пауза 20 мин | первым делом тратится на тир A |
| `x_ssr` | 1 зап/с | включается только когда `nitter_rss` деградировал (fail_streak ≥ 3 по всем инстансам) |

Все запросы (успех и отказ) пишутся в таблицу `requests` с полем `kind` = имя канала,
`host`, `status`, `latency_ms`, `items`.

### 2.2 `tuber_x/enrich.py` — обогащение постов
Схема работы:
1. Взять из `posts` посты без метрик (`metrics_at IS NULL`) с ограничением `LIMIT batch` (по умолчанию 400).
2. Отсортировать: сначала свежие (`published_at_utc DESC`), затем по аккаунтам тира A/B/C.
3. Для каждого ID — запрос в `cdn_tweet`, разбор полей.
4. Записать: `likes`, `replies`, `has_quote` (из `quoted_tweet`), `is_long` (наличие `note_tweet`),
   `lang`, `text` (**только если в базе пусто** — см. правило 6), `metrics_at`, `metrics_src='cdn'`.
5. Каждый замер метрик дополнительно писать в историю `post_metrics_history` (см. 3.2) —
   без неё невозможна скорость набора (лайков/час).
6. **Текст из CDN — только для заполнения пустого.** В `tweet-result` текст обрезан на ~280
   символах, поэтому ЗАПРЕЩЕНО перезаписывать им текст, полученный из Nitter
   (`UPDATE ... SET text=? WHERE text IS NULL OR length(text) < 40`). Если у поста `is_long=1`
   (есть `note_tweet`), а полного текста в базе нет — такой пост ставится в очередь на добор
   через Nitter, а не считается обработанным. Проверено 15.09.2026: один и тот же пост `@sama`
   — Nitter даёт 2 871 символ, CDN 280, oEmbed 344, SSR-страница поста 300.

Обязательные свойства:
- **идемпотентность**: повторный вызов не создаёт дублей, только обновляет `metrics_at`;
- **устойчивость**: 404 (удалённый пост) → `deleted_at` в `posts`, не ошибка прогона;
- **ретвиты не скорить**: при `is_retweet=1` метрики сохранять, но в скоринг не подавать
  (см. п. 7 замеров) — ставить `metrics_src='cdn_rt'` и исключать из агрегатов;
- **батч-пауза**: 0,35 с, при 429 — экспоненциальная пауза 60/120/240 с.

### 2.3 `tuber_x/channels.py::timeline_snapshot(handle)` — премиальный канал
Разбор `__NEXT_DATA__` из HTML: `json.loads` содержимого тега
`<script id="__NEXT_DATA__" type="application/json">…</script>` → `props.pageProps.timeline.entries[]`
→ `entry['content']['tweet']`.

Правила:
- **канал разовый, не регулярный:** не более 5 аккаунтов в сутки, только для разового уточнения
  по важнейшим аккаунтам. Проверено 15.09.2026 (probeF): после 15 минут полной тишины первый же
  запрос вернул 429, вся серия 30/30 — 429. То есть блок переживает 15 минут простоя и держится
  дольше (точное окно не найдено). В расписании этому каналу — отдельная задача не чаще 1 раза
  в сутки с бюджетом 5 запросов;
- первая запись — **закреплённый** пост, помечать `pinned=1` и не считать новинкой;
- ретвиты (`full_text` начинается с `RT @`) помечать `is_retweet=1`;
- если канал вернул 429 — не повторять в этом окне, писать в `run_log` и переключаться на Nitter;
- бюджет запросов хранить в `cursors`/`instances` (`requests_today`, `cooldown_until`).

## 4. Скоринг значимости на реальных метриках

Раньше (ТЗ-3) значимость считалась без метрик вовлечённости. Теперь доступны `likes` и `replies`
безлимитно через CDN. **Чего нет (проверено 15.09.2026, probeK):** счётчиков репостов, цитат,
закладок и просмотров в CDN-канале нет вообще (`retweet_count`, `quote_count`, `bookmark_count`,
`view_count` → отсутствуют). Репосты доступны только в ленточном канале, а он разовый (см. 2.3),
поэтому **в массовом скоринге репостов не будет** — и это надо честно писать в выдаче, а не
подменять догадками. Что даёт CDN помимо лайков: галочку верификации автора и автора цитаты —
их используем как слабые признаки.

**Возрастная нормализация (обязательно).** Абсолютные лайки несравнимы: пост возрастом 2 ч и 30 ч.
Считать скорость на фиксированном возрасте:

```
velocity_6h(post)  = likes_at_6h / 6
score_engage(post) = log10(1 + velocity_6h * 10 + replies_at_6h * 2)
```

**Распространение — строится на графе, а не на репостах.** Основной сигнал: число **независимых
аккаунтов реестра**, упомянувших или процитировавших пост (`mentions`, `quoted_tweet`,
`orig_handle`), с весом 1,5 за каждого. Если по конкретному посту случился разовый заход в ленточный
канал и там есть `retweet_count` — использовать как уточнение, помечая в базе `spread_src='synd'`,
иначе `spread_src='graph'`. Смешивать два источника в одном рейтинге без пометки запрещено.

**Слабый признак для аккаунта:** `verified=1` из CDN даёт +10% к весу аккаунта в графе, но **не
является** критерием допуска. Осторожно: у `@sama` и `@DarioAmodei` поле `verified=False`, у
`@OpenAI` — `True` с `verified_type`, то есть признак неоднородный (наследие/платная галочка) —
использовать только как добавку, никогда как фильтр.

**Первоисточник.** Как в ТЗ-3: разница во времени публикации между первым и вторым
независимым автором темы, в минутах; меньше — выше.

**Итог:** `score = 0,45*score_engage + 0,35*score_spread + 0,20*score_first`.
Коэффициенты — стартовые, пересмотр после 30 дней данных (обязательно зафиксировать
в METHODOLOGY.md, что это калибруемая часть).

**Запреты:** ретвиты и посты с `pinned=1` в агрегаты значимости не подавать; посты с
`metrics_src='cdn_rt'` — не подавать.

## 5-БИС. Размер реестра, тиры и конкуренция за квоту (замерено 15.09.2026)

**Продуктивность 12 крупных ИИ-аккаунтов** (`/tmp/xx_probeJ_rate.py`, живые ленты + 2 страницы
курсора на каждом, отказов 0):

| Показатель | Значение |
|---|---|
| постов за 24 ч суммарно на 12 аккаунтов | **30** |
| аккаунтов с ≥ 1 постом в сутки | **5 из 12** |
| простой с последнего поста: минимум / медиана / максимум | 6,3 ч / **31,9 ч** / 271 ч |
| самое плотное (в замере) | `@levelsio` — 17 постов за сутки |

Вывод для тиров: профиль ИИ-аккаунтов **низкопоточный**. Ленты в 20 постов хватает на 4–10 суток
для медианного аккаунта, поэтому:
* тир A (каждый час) — только тем, у кого ≥ 5 постов/сутки (в замере такие единицы);
* тир B (каждые 4 ч) — 1–5 постов/сутки;
* тир C (раз в сутки) — меньше 1 поста в сутки, то есть большинство реестра. Потерь нет: 20 постов
  покрывают 4+ дня такой ленты, и курсор доберёт остаток.

Практический вывод по размеру: реестр 1000–3000 аккаунтов при преимущественно тире C — это
1000–3000 запросов в сутки, то есть 12–35 запросов в минуту при равномерном размазывании.
Один инстанс держит 8 запросов за 30 с (16 в минуту), два — вдвое больше. Значит **реестр
упирается не в объём, а в конкуренцию за инстанс**.

**Риск, который надо закрыть кодом:** боевой демон CryptoGraph обходит 3181 аккаунт по тем же
двум инстансам и имеет собственный лимитер. Лимитер Tuber-x про чужой расход не знает — два
процесса сложатся и дадут 429-шторм, как это уже было 15.09 утром. Требование: брокер
Tuber-x обязан либо (а) закрепить за собой отдельный инстанс (Tuber-x — `jaydenha.uk`,
CryptoGraph — `kareem.one`) через конфиг, либо (б) брать квоту через общий файловый семафор
(`/run/tuber-x-nitter.lock` с записью времени запросов), который читает и демон CryptoGraph.
Вариант (а) проще и не требует правок в чужом проекте — принять его по умолчанию, (б) оставить
как шаг развития при росте реестра выше 3000.

## 6. Расписание (после реализации)

| Задача | Частота | Что делает |
|--------|---------|-----------|
| `collect` (Nitter, тиры A/B/C) | тир A — 1 ч, B — 4 ч, C — 24 ч | сбор постов |
| `enrich` | каждые 2 ч | догоняет метрики пачками по 400 |
| `synd_snapshot` (≤5 аккаунтов/цикл) | **1 раз в сутки** | разовое уточнение по репостам; канал разовый — бюджет исчерпывается мгновенно |
| `discover` (ТЗ-2) | 4 раза в сутки | рост реестра |
| `report` (ТЗ-3) | 1 раз в сутки, утро | выдача владельцу |
| `health` | каждые 30 мин, `no_agent` | сторож: свежесть, доля отказов, бюджет каналов |

Сторож (`health`) обязан алертить при: нет новых постов за 6 ч; доля отказов > 50% за час;
`cdn_tweet` 429 > 20 за час; исчерпан суточный бюджет ленточного канала (все 5 запросов — 429);
доля постов с полным текстом (`is_long=1 AND length(text) < 200`) > 10% — значит длинные посты
приходят обрезанными и выдача врёт по содержанию.

## 7. Питфоллы (проверено живьём — не повторять ошибок)

1. `syndication.twitter.com/…/timeline-profile` **без** заголовка `Referer` → 429 (probe7);
   с `Referer: https://platform.twitter.com/` → 200 (probe10). Referer обязателен.
2. Квота ленточного канала общая у `syndication.twitter.com` и `cdn.syndication.twimg.com` —
   переключение хоста **не** обходит 429 (probeC).
3. Эндпоинт `tweet-result` (одиночный пост) и эндпоинт `timeline-profile` — **разные квоты**.
   Обогащение метриками не тратит бюджет ленты.
4. Ретвиты приходят с `favorite_count=0` — не считать «нулевой популярностью» (probe11).
5. Первая запись ленты — закреплённый пост, он может быть старым (у `@OpenAI` закреплён пост
   от 3 сентября с 339 548 лайками) — не считать новинкой и не поднимать в топ по свежести.
6. `x.com/<handle>` кэшируется: три запроса подряд дали одинаковый набор ID (probe9-D),
   отставание до 45 ч. Годится только как дублёр.
7. Ответы CDN сжаты `gzip` — обязательна декомпрессия по заголовку `Content-Encoding`.
8. Кэш Nitter — 10 минут: чаще опрашивать бессмысленно.
9. Коды ответа `tweet-result` различать строго (probeH, живые пробы):
   `400` — ID вне диапазона/битой длины (несуществующий `9999999999999999999`);
   `404` — ID не найден (`0`, короткий номер);
   `200` + `__typename=Tombstone` — пост удалён или недоступен (в теле нет `created_at`);
   `200` + поля поста — норма. Ни `400`, ни `404`, ни `Tombstone` не повторять — это не сбой сети.
10. Метрики в `tweet-result` — кэшированные значения (могут отставать на часы), поэтому
    сравнение постов между собой корректно, а «точные лайки в реальном времени» — нет.
11. **Бэкфилл метрик работает задним числом (probeI, 15.09.2026):** 8 из 8 постов от 7–10 августа
    2026 (5+ недель давности) отдали лайки и ответы. Значит метрики можно подтянуть к любому
    ID, который у нас уже есть — в том числе к 152 постам, собранным ТЗ-1, и к историческим
    X-постам из соседних проектов. Отдельная команда `cli enrich --backfill-days N`.
