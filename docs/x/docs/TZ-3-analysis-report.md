# ТЗ-3 — Tuber-x: анализ, сюжеты и ежедневная выдача

Предусловие: ТЗ-1 и ТЗ-2 приняты. Работать в `/root/tuber-x`.

## Р1. Классификация постов (`classify.py`)

Р1.1. Тематическое решение принимает модель (DeepSeek), а не ключевые слова: ключевые
слова допускаются только как предфильтр для отсечения заведомо нерелевантного и обязаны
помечать пост `heuristic`, а не `classified`.

Р1.2. Для каждого поста получать: `is_ai` (0/1), `topic` (одна из 10 рубрик ТЗ-2 Р1.1),
`subtopic` (свободный, 1–3 слова), `claim_type` (одно из: `release`, `funding`,
`research`, `opinion`, `news`, `howto`, `incident`), `novelty` (0.0–1.0 — новое ли
это утверждение по сравнению с уже собранным за 7 дней), `lang`.

Р1.3. Батчи по 20 постов, ответ — строгий JSON (валидируется схемой; при невалидном
ответе — повтор один раз, затем пометка `failed` и повтор в следующем прогоне).

Р1.4. Кеш по `text_hash`: одинаковый текст не классифицируется дважды. Классифицируется
только то, что ещё не имеет записи в `classified`.

Р1.5. Учёт стоимости: перед прогоном проверять бюджет DeepSeek
(`/root/.hermes/scripts/deepseek_budget.py --status`). При исчерпании — не запускать,
писать причину. Дневной потолок классификации Tuber-x — 400 постов (по приоритету:
свежие, TIER-A, уникальные тексты).

Р1.6. Язык постов не переводится в БД; перевод делается только в отчёте, чтобы выдача
была на русском.

## Р2. Сюжеты (`stories.py`)

Р2.1. Кластеризация постов в сюжеты за окно 72 часа: simhash текста (64 бита) + правило
«тот же набор ключевых сущностей» (упоминания, ссылки, имена моделей/проектов, извлечённые
из текста регулярками и словарём).

Р2.2. Порог схожести — параметр (`SIMHASH_THRESHOLD`, по умолчанию 12 из 64 бит разницы);
значение фиксируется в `runs.note` при изменении.

Р2.3. Роли участников сюжета:

| Роль | Признак |
|---|---|
| `primary` | самый ранний пост сюжета (автор — first_mover сюжета) |
| `echo` | пересказ без ссылки на первоисточник |
| `amplifier` | ретвит/цитата с сохранением авторства |
| `extender` | добавляет новую сущность (новый факт, деталь, ссылку) |

Р2.4. Для каждого сюжета считать: `xconf` (число независимых авторов, не постов),
`first_mover` (хендл), `published_at` первого поста, `lead_time_min` (минуты от первого
поста до второго независимого автора), `topics`, `entities`, `is_new_entity` (есть ли
среди сущностей впервые встреченная в базе).

Р2.5. Сюжет, у которого `xconf = 1` и нет `extender`-ов, помечается `single` и в главный
блок отчёта не попадает (это одиночное мнение, а не событие) — исключение: рубрика
`funding` и `release` при наличии ссылки на первоисточник.

## Р3. Три оси и оценки (единая функция в `scores.py`)

Р3.1. Значимость поста. **Обновлено 15.09.2026 по ТЗ-4:** метрики вовлечённости ДОСТУПНЫ
(лайки и ответы из `cdn.syndication.twimg.com/tweet-result`, репосты — из ленты embed-API),
поэтому оценка строится на настоящих числах, а не только на графе. Снимки метрик копятся
в `post_metrics_history`; для оценки берётся снимок в возрасте ~6 часов — раньше цифры ещё
не устоялись, позже теряется разница между «выстрелило сразу» и «накрутилось за неделю».

```
engagement = likes + 2 × replies                     (снимок в возрасте 6 ч)
velocity   = engagement / 6                          (прирост в час)
spread     = xconf − 1                               (число независимых авторов, кроме первичного)
significance = (ln(1 + velocity) + 0.8 × ln(1 + spread)) / (1 + hours_since / 24)^1.8
```

Р3.1-бис. Если метрик за 6 часов нет (канал деградировал), оценка считается по прежней
графово-временной формуле `(xconf − 1)^0.8 / (hours_since + 2)^1.8`, пост помечается
`metrics_missing=1`, и в выводе прямо указывается, что оценка временная, а не по популярности.
Обе ветки обязаны быть проверяемы: тест подаёт пост без метрик и проверяет, что подмена
формулы и пометка происходят.

Р3.1-тер. Ретвиты в лентах приходят с нулевыми лайками (метрики принадлежат оригиналу),
поэтому ретвит никогда не оценивается как самостоятельный пост: он либо ведёт к оригинальному
`tweet_id`, либо учитывается только как признак распространения. Тест: фикстура с ретвитом
не должна давать ему нулевую значимость в рейтинге.

Р3.2. `first_mover_score` аккаунта — накопительно: доля сюжетов, где он `primary`,
от всех сюжетов, где он участвовал, с весом свежести (полураспад 30 дней).

Р3.3. `darks` — тёмные лошадки: аккаунты, у которых за 7 дней выросло число уникальных
сюжетов, но которые ни разу не попали в топ-20 по `significance`. Рост считается как
отношение текущей недели к предыдущей (минимум 5 сюжетов, чтобы не ловить шум).

Р3.4. Антинакрутка и мусор: из всех рейтингов исключаются сюжеты, где
`xconf ≥ 3`, но все авторы — аккаунты с `dup_ratio > 0.5` (один и тот же текст
разными хендлами); такие сюжеты помечаются `suspect` и попадают в служебный блок.

## Р4. Ежедневная выдача (`report.py`)

Р4.1. Отчёт печатается в stdout и сохраняется в `/root/tuber-x/reports/YYYY-MM-DD.md`.
Формат: пронумерованные блоки, простые строки, без эмодзи и без английского без перевода.

Р4.2. Блоки:

1. **Главное за сутки** — до 10 сюжетов с наибольшим `xconf`: описание на русском +
   кто первый + сколько независимых аккаунтов + время + ссылка `https://x.com/<handle>/status/<id>`.
2. **По темам** — таблица «рубрика: сюжетов сегодня / сюжетов за 7 дней / доля», только
   строки с ненулевыми значениями, отсортировано по сегодняшней доле.
3. **Деньги и запуски** — сюжеты с `claim_type` = `funding` (сумма раунда из текста,
   кто, ссылка) и `release` (что выпущено, чья модель/продукт).
4. **Новинки и инструменты** — рубрики «инструменты разработчика», «инфраструктура»,
   «вайб-кодинг»: что нового появилось у разработчиков.
5. **Русскоязычный срез** — отдельно: 5–10 позиций с `lang='ru'`.
6. **Тёмные лошадки и первые авторы** — по Р3.3 и топ-5 по `first_mover_score`.
7. **Служебный блок** — посты за сутки, дубли, доля валидных дат, отказы сбора,
   живые инстансы, расход квоты, кандидаты и рост реестра, `suspect`-сюжеты.

Р4.3. Если в блоке нет данных — писать `нет данных за сутки` (не пропускать блок молча
и не выдумывать содержимое).

Р4.4. Ни один пункт не может содержать пост без `published_at_utc` (исключение —
служебный блок со счётчиком).

## Р5. Сторож (`health.py`, no_agent, крон каждые 30 минут)

Проверки и пороги:

| Проверка | Порог | Действие |
|---|---|---|
| свежесть TIER-A | последний пост старше 3 ч | ALERT |
| свежесть всей базы | нет постов 6 ч | ALERT |
| доля отказов сбора | > 20% за прогон | ALERT |
| валидность дат за сутки | < 99% | ALERT |
| живые инстансы | 0 живых | ALERT |
| расход квоты | > 80% суточного потолка | ALERT |
| рост реестра | 0 новых `active` за 48 ч | WARN |
| подозрительное совпадение | `xconf ≥ 5` при всех авторах `dup_ratio > 0.5` | WARN |

Р5.1. В норме сторож молчит (пустой вывод = ничего не отправляется). При ALERT — одна
строка на проблему, по-русски, без эмодзи.

Р5.2. Дополнительно `cli health --json` — машинный вывод для внешних панелей.

## Р6. Тесты

1. `test_simhash_cluster` — одинаковые/почти одинаковые тексты в один сюжет, разные — в разные.
2. `test_roles` — первичный, эхо, усилитель, расширяющий определяются верно.
3. `test_xconf` — `xconf` считает независимых авторов, а не посты (10 постов 2 авторов = 2).
4. `test_significance` — формула на 3 эталонных значениях.
5. `test_suspect_excluded` — сюжет с одинаковыми текстами у 5 хендлов уходит в `suspect`.
6. `test_report_blocks` — все 7 блоков присутствуют; при пустых данных печатается `нет данных за сутки`.
7. `test_report_no_missing_date` — пост без даты не попадает в содержательные блоки.
8. `test_health_silent` — в норме вывод пустой; при нарушении порога — одна строка.
9. `test_classify_cache` — повторный запуск не отправляет уже классифицированные тексты (счётчик вызовов модели = 0).
