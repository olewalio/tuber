# Tuber-x — методология (v1, 15.09.2026)

Третий элемент стека: `tuber-os` (YouTube) + `tuber-telegram` (Telegram) + **`tuber-x` (X)**.

## 1. Что это

Ежедневный сбор и анализ того, что происходит в ИИ-тренде на X, и **накопительный реестр
аккаунтов**, которые этот тренд создают: вайб-кодинг, инвестиции в новые ИИ-проекты,
ИИ-приложения и релизы, новинки инструментов, инфраструктура, регулирование, скандалы.

Две части механизма:

1. **Реестр аккаунтов** — кто пишет про ИИ-тренд: проверенные источники, их тиры,
   тематический профиль, поведенческий отпечаток (ритм, доля ссылок, доля ретвитов,
   тематическая плотность), статус (candidate / active / dead / blocked).
2. **Ежедневная выдача** — что происходит сейчас: сюжеты по числу независимых
   аккаунтов, тематический срез, деньги и запуски, новинки, русскоязычный срез,
   тёмные лошадки и первые авторы.

Проект независимый. Логика `crypto-graph` (X-сбор для крипто-новостей) копированием
НЕ переносится: она решает другую задачу (крипто-лента) и работает без разбора
аккаунтов. Совпадение цифр с ней не является критерием приёмки. Общее — только
транспорт (Nitter), и он выносится в отдельный брокер (раздел 4).

## 2. Главный технический факт: метрик вовлечённости нет вообще

Замер 15.09.2026, `src/views/rss.nimf` + живой разбор RSS: элемент `<item>` содержит
только `title`, `dc:creator`, `description` (текст, медиа, цитата, опрос),
`pubDate`, `guid`, `link`. **Ни лайков, ни ретвитов, ни просмотров, ни подписчиков,
ни даты регистрации, ни верификации.** HTML профиля, где были счётчики, отдаёт 403.

Следствия, определяющие всю конструкцию:

1. Ранжирование «значимости» по популярности НЕВОЗМОЖНО. Признак популярности,
   который заказчик ожидает увидеть, физически отсутствует.
2. Вместо популярности работают три доступных сигнала: **граф** (кто кого упоминает,
   цитирует, репостит), **время** (кто раньше сказал, как быстро разошлось),
   **текст** (тема, новизна, повтор).
3. Любой скоринг обязан быть честно помечен как «без метрик вовлечённости», а не
   выдавать выдуманный «рейтинг популярности».

Проверено также: `f=users` (поиск людей) в RSS запрещён на уровне кода
(`Only Tweet searches are allowed for RSS feeds`) — значит «поиск аккаунтов»
существует только косвенно, через твит-поиск.

## 3. Три оси вместо «популярности»

| Ось | Что считаем | Как измеряем |
|---|---|---|
| Распространение | сколько **независимых** аккаунтов сказали то же самое | xconf — число разных авторов в сюжете; динамика xconf/час против 7-дневной базы |
| Первоисточник | кто сказал раньше всех и насколько раньше | first_mover сюжета; lead_time = время до второго независимого автора |
| Новизна | что впервые появилось в нашей базе | доля сущностей/проектов, встреченных впервые; связка с раундами и релизами |

Нормировка значимости поста (единственная доступная форма без метрик —
адаптация открытой gravity-формулы Hacker News, первоисточник: комментарий pg,
`news.ycombinator.com/item?id=1781013`):

```
значимость = (xconf − 1)^0.8 / (часы_с_публикации + 2)^1.8
```

Адаптация помечена как адаптация: коэффициенты 0.8/1.8 взяты из HN, для X
не откалиброваны и подлежат пересмотру после первых 30 дней данных.

Оценка аккаунта собирается из наблюдаемых величин (не из популярности):

| Признак | Как считается | Рабочий диапазон «живой автор» |
|---|---|---|
| Регулярность | CV интервалов между постами (σ/μ) | 0.3–2.0 (CV < 0.15 — автомат) |
| Продуктивность | постов/сутки | 0.2–20 (нитка > 20/сутки — новостной провод) |
| Ссылочность | доля постов с внешней ссылкой | 0.05–0.5 (у спам-бота > 0.8 однотипных) |
| Авторство | доля оригиналов против ретвитов/ответов | ретвитов < 0.7, иначе это усилитель, а не автор |
| Тематическая плотность | доля постов про ИИ по классификатору | ≥ 0.5 |
| Повтор | доля постов-дублей (simhash) | > 0.3 дублей — копипаста |
| Первоисточниковость | как часто аккаунт оказывается first_mover сюжета | накопительно, отдельный рейтинг |

## 4. Транспорт и брокер: почему это отдельный слой

Замер 15.09.2026. Публичный доступ к X с сервера закрыт (x.com → 403 с 26.08.2026).
Единственный бесплатный канал — Nitter RSS. Из 8 инстансов статус-панели
`status.d420.de` реально отдают RSS **два**:

```
nitter.kareem.one    200, items=20  (живой)
nitter.jaydenha.uk   200, items=20  (живой)
nitter.miningtcup.me 400 | nitter.netbub.com 200/заглушка | nitter.meowing.monster 200/заглушка
shitter.thepixora.com 400 | nitter.cz 200/заглушка | nitter.privacyredirect.com 200/заглушка
nitter.tiekoetter.com 200/заглушка | xcancel.com 451 (юридический takedown)
```

Замеренные свойства канала:

- **Лимит:** ~8 запросов / 30 с на инстанс (429 примерно на 7–9-м подряд), после
  перегруза — блок на десятки секунд, дальше 429 держится и на 3 запросах/мин проходит.
- **Кеш:** инстанс кеширует RSS на 10 минут — опрос одного и того же адреса чаще
  бессмыслен.
- **Лимит глубины:** лента отдаёт ровно 20 постов (`count: 20` в `src/api.nim`), параметра
  `?count=` нет.
- **Курсор ЕСТЬ и работает** (проверено мной 15.09.2026 на обоих инстансах, для ленты
  и для поиска): заголовок ответа **`min-id`** (в нижнем регистре) отдаёт курсор;
  запрос `?cursor=<min-id>` возвращает следующую страницу в прошлое.
  Замер: лента `@cointelegraph` — 3 страницы = 59 уникальных постов (20+20+19,
  окно уходит назад по времени), поиск `AI agents` — 2 страницы = 40 уникальных постов.
  Вывод: **бэкфилл после простоя выполним**, потери восстановимы.

Оба факта — что лимит общий и что наш существующий демон `cryptograph-daemon` уже
долбит `kareem.one` реестром 3181 аккаунта и живёт в 429-шторме — означают: если
Tuber-x просто «добавит свой сборщик», он отберёт канал у CryptoGraph и оба встанут.

Поэтому первый компонент проекта — **брокер доступа** (`nitter_broker.py`): один
процесс-владелец квоты, через который ходят все (и Tuber-x, и CryptoGraph):

1. пул инстансов из конфига, проверка здоровья «отдал ≥ 15 item» (HTTP 200 без данных
   не считается живым — это ловушка Anubis/заглушек);
2. общий лимитер на инстанс с окном и cooldown (по умолчанию 6 зап/60 с — ниже
   замеренного предела: лучше недобрать, чем словить блок);
3. учёт расхода по каждому инстансу за сутки и жёсткий потолок (80% ёмкости);
4. приоритеты: сторож → TIER-A обход → дискавери → бэкфилл;
5. при 429 — cooldown инстанса и переключение на второй; при отсутствии живых —
   пауза и алерт, а не долбление;
6. журнал каждого запроса (инстанс, вид, статус, items) — основа сторожей.

Эксплуатационное правило: **частота сбора не должна превышать пропускную способность
канала.** Это правило уже нарушено в CryptoGraph (3181 аккаунт × обход 3 ч 08 мин
при суточной ёмкости 23 040 запросов на инстанс) — перевод CryptoGraph на брокер
и снижение его частоты до нормы входит в эту же работу.

## 5. Окно и полнота

Потеря постов зависит от периода обхода T и потока аккаунта P:

```
получено = min(20, P·T);  потери = max(0, P·T − 20)/(P·T)
```

Замерено на исторических данных (реестр 3181, средний поток 0.31 поста/сутки):

| Период обхода | Теряют | Доля потерь |
|---|---|---|
| 1 час | аккаунты с потоком > 480/сутки | ~0% |
| 6 часов | > 80/сутки | 0–1% |
| 24 часа | > 20/сутки | 10–20% (новостные проводы теряют до 37%) |
| 20 суток (простой) | > 1/сутки | ~95% |

Отсюда окно и тиры: **TIER-A** (эталонные первоисточники, до 200 аккаунтов) — каждый
час; **TIER-B** (ядро, до 1000) — каждые 3–4 часа; **TIER-C** (широкий слой) — раз в
сутки. Цена простоя измерена на практике: 27.08–14.09.2026 CryptoGraph не собирал X —
потеряно ~96% постов периода.

Критерий полноты (единственный честный на 20-окне): **повторный обход сразу после
первого обязан дать 0 новых id.** Если даёт — мы не успеваем за потоком и нужно
учащать обход, а не увеличивать окно.

## 6. Реестр: как растёт и чем защищён от мусора

Расширение — снежный ком по графу упоминаний: тематический поиск → из найденных постов
берём авторов, упоминания, источники ретвитов → кандидаты → валидация → приём.
Замер выхода: один запрос даёт 20 постов и **33–40 разных хендлов** кандидатов;
20 запросов в сутки — ~700 кандидатов в сутки, то есть прирост реестра ограничен
не поиском, а фильтром качества.

Обязательный конвейер приёма (все пороги — жёсткие):

1. хендл по `^[A-Za-z0-9_]{1,15}$` (мусорный хендл `layerzero_core\` уже дал 3643 ошибки подряд в CryptoGraph);
2. проверка «инстанс отдал ≥ 15 постов» — аккаунт существует и читается;
3. тематическая плотность: ≥ 25% постов про ИИ по классификатору;
4. социальное доказательство: хендл встречается у ≥ 2 разных аккаунтов доверенного ядра (co-occurrence), а не в одном посте;
5. отбраковка автоматов: CV интервалов < 0.15, доля ссылок > 0.7, доля дублей > 0.3, доля ретвитов > 0.8;
6. дневной потолок прироста (по умолчанию 50 аккаунтов/сутки) — одна шумная ночь не должна утроить реестр;
7. каждому приёму — запись «откуда пришёл» (запрос, аккаунт-источник упоминания), чтобы решения были проверяемы.

Замер риска без фильтров: 30–60% мусора при наивном «все, кого упомянули» — спам-боты
специально набивают упоминания, чтобы попадать в парсеры.

## 7. Ежедневная выдача

Каждая позиция: **описание на русском + кто сказал первым + сколько независимых
аккаунтов + когда + ссылка**. Английский без перевода в выдаче считается браком.

1. **Главное за сутки** — сюжеты, набравшие больше всего независимых авторов за 24 часа.
2. **По темам** — срез по таксономии с динамикой: сегодня против 7-дневной базы,
   видно, куда смещается интерес.
3. **Деньги и запуски** — раунды, новые проекты, запуски продуктов: сумма, кто, ссылка.
4. **Новинки и релизы** — модели, инструменты, вайб-кодинг, инфраструктура.
5. **Русскоязычный срез** — отдельно от мирового (замер: тематический поиск по русским
   запросам отдаёт посты 3–4-дневной давности, поэтому русский срез строится на
   реестре, а не на поиске).
6. **Тёмные лошадки и первые авторы** — аккаунты, растущие в графе упоминаний, и те,
   кто стабильно говорит раньше остальных.
7. **Служебный блок** — состояние реестра и канала: принято/отклонено кандидатов,
   покрытие, живые инстансы, доля отказов, свежесть.

## 9. Схема данных (контур)

`accounts` (реестр) · `posts` (посты) · `classified` (тема/новизна/тип утверждения) ·
`stories` + `story_members` (сюжеты = кластеры дублей, роль primary/echo/amplifier) ·
`candidates` (очередь дискавери с причиной находки) · `cursors` (курсор min-id по
аккаунту и запросу — страховка от потери при простое) · `instances` + `requests`
(здоровье канала и расход) · `runs` + `run_log` + `metrics_daily` (журнал и панель
качества). Поля и инварианты — в ТЗ-1.

Дата публикации: `published_at` берётся из `pubDate`, проверяется (пустое и
`1970-%` отбраковывается) и при необходимости восстанавливается из snowflake-id
(`guid`). Причина — замер: 97.5% X-записей в `crypto_graph.db` имеют пустую или
битую дату, любая аналитика по дням на таких данных недостоверна.

## 10. Ресурс и бюджет запросов

Ёмкость канала (замер): 8 зап/30 с = 960 зап/ч = **23 040 зап/сутки на инстанс**,
два живых инстанса — 46 080. Рабочий потолок 80%, то есть ~37 000 запросов/сутки.

| Трек | Что делает | Расход в сутки |
|---|---|---|
| A. TIER-A обход (200 аккаунтов, каждый час) | первоисточники | 4 800 |
| B. TIER-B обход (1000 аккаунтов, каждые 3 ч) | ядро | 8 000 |
| C. TIER-C обход (до 1500, раз в сутки) | широкий слой | 1 500 |
| D. Дискавери (24 запроса + пагинация до 3 страниц) | рост реестра | ~100 |
| E. Сторожа и health | живучесть канала | ~150 |
| F. Бэкфилл после простоя | восстановление | разово, до 1 000 запросов за прогон |

Итого ~14 500 запросов/сутки = 31% ёмкости — остальное запас на сбои, повторы и
CryptoGraph (после перевода на брокер). Потолок не поднимать без проверки расхода:
переподписка даёт 429-шторм и тихие пропуски, а не больше данных.

Что не берём: платный X API, платные прокси, `f=media` (отдаёт старое), `f=users`
(запрещён кодом), любые «популярностные» метрики (их нет в канале).

## 12. Известные питфоллы (перенесены в реализацию)

- HTTP 200 без данных (Anubis и заглушки) — проверять по `<item>`, а не по коду ответа.
- Заголовок курсора — `min-id` в нижнем регистре; `Min-Id` из документации не приходит (проверено).
- 429 не снимается мгновенно: в перегруженном режиме блок держится минуты; cooldown 30 с недостаточен.
- Кеш 10 минут: опрос чаще — пустая трата квоты.
- Поиск по русским запросам отдаёт устаревшее — русский срез только через реестр.
- Поисковая выдача узкая по времени (20 постов ≈ минута потока) — поиск это сэмплер, не сборщик.
- Ретвит в RSS выглядит как пост исходного автора (`dc:creator` — автор оригинала), а не владелец ленты; владельца определять по полю `RT by @...` в заголовке.
- «Значимость» без метрик вовлечённости обязана быть помечена как графово-временная оценка.
- Лимит канала общий с CryptoGraph — сначала брокер, потом рост.

## 13. ТЗ-4: каналы, метрики и скоринг (дополнение 15.09.2026)

**Метрики вовлечённости доступны.** CDN `cdn.syndication.twimg.com/tweet-result`
отдаёт лайки (`favorite_count`) и ответы (`conversation_count`) безлимитно; квота
общая с ленточным каналом только у ленты, одиночный `tweet-result` её не тратит.
Чего в CDN НЕТ вообще: репостов, числа цитат, закладок, просмотров. Поэтому
массовый скоринг репостов не использует, и в выдаче это написано честно, а не
подменено догадками.

**Возрастная нормализация.** Абсолютные лайки несравнимы между постом 2 ч и 30 ч.
Считается скорость на фиксированном возрасте 6 ч:

```
velocity_6h        = likes_at_6h / 6
score_engage       = log10(1 + velocity_6h * 10 + replies_at_6h * 2)
```

Замер в окне ±1,5 ч от 6 ч — точный (`velocity_estimated=0`); иначе линейная
переоценка по ближайшему замеру с пометкой `velocity_estimated=1`. Возраст и
число независимых авторов берутся из `post_metrics_history`.

**Ось 1. Вовлечённость** — `score_engage` выше.

**Ось 2. Распространение** — по ГРАФУ упоминаний, не по репостам: число
независимых аккаунтов реестра, упомянувших/процитировавших пост, с весом 1,5
за каждого; галочка верификации автора даёт +10% к весу и НЕ является фильтром.
Если по посту был разовый заход в ленточный канал и там есть `retweet_count`,
используется он, а пост помечается `spread_src='synd'`; смешивать два источника
в одном рейтинге без пометки запрещено.

**Ось 3. Первоисточник** — `score_first` по времени до второго независимого
автора темы (минуты), меньше — выше. Без сюжетов ТЗ-3 тема приближается
пересечением сущностей (общие ссылки/упоминания за 72 ч) — это приближение.

**Итог:** `score = 0,45*score_engage + 0,35*score_spread + 0,20*score_first`.

> **Веса — калибруемая часть.** Значения 0,45/0,35/0,20 — стартовые, задаются
> в `config.SCORE_W_*`; пересмотр — после 30 дней накопленных данных. Изменение
> весов не меняет структуру осей, только их вклад.

**Запреты (агрегаты значимости):** ретвиты, посты с `pinned=1`, посты с
`metrics_src='cdn_rt'` не подаются. Первая запись ленты — закреплённый пост,
он может быть старым и не является новинкой.

**Ленточный канал (`synd_timeline`) — разовый.** Блок переживает 15 минут
тишины, поэтому канал стоит отдельной задачей не чаще 1 раза в сутки с бюджетом
5 запросов; регулярного опроса нет.

**Текст из CDN обрезан** (~280 символов). Он пишется в базу ТОЛЬКО для
заполнения пустого места; полный текст Nitter (например, 2871 символ у `@sama`)
перезаписывать запрещено — это уничтожило бы данные.

## 14. ТЗ-3: анализ, сюжеты и ежедневная выдача (дополнение 15.09.2026)

**Роль ТЗ-3.** ТЗ-1/ТЗ-2 дали сбор и реестр, ТЗ-4 — честные метрики. ТЗ-3
добавляет смысловой слой: классификацию через модель, кластеризацию постов в
сюжеты и ежедневную выдачу. Никаких новых обращений к Nitter слой не делает:
он читает базу и (в классификации/переводе) ходит только в DeepSeek.

**Классификация — только модель.** Тематическое решение принимает DeepSeek
(`deepseek-v4-flash`, `thinking:{"type":"disabled"}`). Ключевые слова работают
исключительно предфильтром: пост без единого ИИ-признака помечается `heuristic`
с пустой темой и НЕ называется классифицированным. Ответ модели — строгий JSON
(`{"items":[...]}`), проверяется схемой: `idx`, `is_ai`, `topic` (одна из 10
рубрик), `subtopic` по-русски, `claim_type` из фиксированного набора,
`novelty` 0..1, `lang`. При невалидном ответе — один повтор с ненулевой
температурой и прямой правкой (при t=0 повтор бессмыслен); если и он не прошёл —
статус `failed` и повтор в следующем прогоне.

**Кэш и деньги.** Результат кладётся в `classified` по `text_hash`: одинаковый
текст не оплачивается дважды, повторный прогон даёт 0 вызовов модели. Перед
прогоном проверяется внешний бюджет DeepSeek и флаг останова; дневной потолок
Tuber-x — 400 постов, приоритет «свежие → TIER-A → уникальные тексты». Стоимость
пишется в `classify_daily` и в общий журнал `/root/.hermes/logs/deepseek_usage.jsonl`.

**Сюжеты.** Окно 72 часа; два поста попадают в один сюжет, если их 64-битный
simhash отличается не более чем на `SIMHASH_THRESHOLD` (12 бит) ИЛИ совпадает
набор ключевых сущностей (упоминания, домены ссылок, имена моделей/проектов из
словаря), ИЛИ совпадают минимум две «ядерные» сущности (модель/проект/упоминание).
`xconf` — число независимых АВТОРОВ (не постов). Роли: `primary` (самый ранний),
`amplifier` (ретвит/цитата/ссылка на первоисточник), `extender` (приносит новую
сущность), `echo` (пересказ). Одиночное мнение (`xconf=1` без extender) не идёт
в главный блок, кроме `funding`/`release` со ссылкой на первоисточник.

**Значимость (Р3.1).** При свежих метриках (снимок ≤ 24 ч):

```
engagement   = likes_at_6h + 2 * replies_at_6h
velocity     = engagement / 6
spread       = xconf - 1
significance = (ln(1+velocity) + 0.8*ln(1+spread)) / (1 + hours_since/24)^1.8
```

Если метрик нет или они старше 24 ч, включается графово-временная ветка
`(xconf-1)^0.8 / (hours_since+2)^1.8`, пост помечается `metrics_missing=1`, и
выдача прямо говорит, что оценка временная. Ретвиты не оцениваются как
самостоятельные посты, а посты с измеренным нулём лайков не подаются в топ
(иначе «нулевые» ретвиты всплывали бы наверх).

**`first_mover_score`** — доля сюжетов, где аккаунт `primary`, от всех сюжетов,
где он участвовал, с весом свежести (полураспад 30 дней). **`darks`** — рост
числа уникальных сюжетов за неделю против предыдущей (минимум 5 сюжетов) у
аккаунтов, ни разу не попавших в топ-20 по значимости. **`suspect`** — сюжеты,
где `xconf ≥ 3`, но все авторы имеют `dup_ratio > 0.5`: они исключаются из всех
рейтингов и уходят в служебный блок.

**Выдача.** Семь блоков, русский язык, без эмодзи; пустой блок — «нет данных за
сутки». Перевод делается ТОЛЬКО в отчёте и кэшируется в `report_texts`; в базу
постов язык не переводится. Ни один содержательный пункт не выводится без
автора, ссылки `https://x.com/<handle>/status/<id>` и проверенной даты.

**Сторож.** Пороговые проверки Р5 (свежесть TIER-A 3 ч, свежесть базы 6 ч,
отказы > 20%, валидность дат < 99%, 0 живых инстансов, расход квоты > 80% —
ALERT; рост реестра и подозрительные совпадения — WARN). В норме вывод пустой.

## 15. ТЗ-10: аварийный резерв включается по факту отказов сбора (дополнение 15.09.2026)

**Дефект (замер заказчика 15.09.2026 на копии боевой базы).** Все инстансы Nitter
заменены мёртвым адресом, затем штатный `collect`. Резерв `x_ssr` включался с
запаздыванием, и первый аккаунт каждого «слепого» окна терялся (до получаса
простоя, аккаунты уходят в `fail_streak`). Причина — в коде, а не в источнике:
`_pick_instance` пропускал инстанс со свежей отметкой «нездоров» (моложе
`HEALTH_TTL_SEC` = 600 с), поэтому повторных фактических попыток не было;
`NoLiveInstance` не увеличивал счётчик отказов; `fail_streak` рос только в
health-пробе и не чаще раза в TTL, а включение резерва зависело от пробы.

**Что изменено.**

1. **Считаются фактические отказы сбора, а не только пробы.** Транспортный отказ
   (соединение отклонено/таймаут/DNS/обрыв чтения), 5xx и `NoLiveInstance`
   увеличивают `instances.collect_fail_streak` (переживает перезапуск процесса).
   Успешное получение фида (`HTTP 200`) обнуляет счётчик этого инстанса. 404 и
   пустая лента отказом НЕ считаются. Ограничение «не чаще раза в
   `HEALTH_TTL_SEC`» осталось только для health-проб; на подсчёт фактических
   отказов оно не распространяется. Попыткой запроса считается только реальный
   запрос ленты: ожидания лимитера её не расходуют.
2. **Свежая отметка «нездоров» больше не исключает инстанс** в `_pick_instance`:
   фактическая попытка делается всегда, пропуск — только по cooldown/блокировке/
   суточному потолку. Health-проба по-прежнему не чаще одного раза в TTL.
3. **Резерв в том же прогоне.** Если Nitter отказал по аккаунту (после штатных
   повторных попыток) и инстансы деградировали, аккаунт добирается через `x_ssr`
   в этом же прогоне. Nitter всегда остаётся первым, резерв — только после
   фактического отказа по конкретному аккаунту. Теперь деградация считается по
   СУММЕ фактических отказов по всем инстансам (`XSSR_DEGRADED_STREAK` = 3), а не
   «≥ 3 по каждому»: один прогон, где аккаунт исчерпал повторы, уже включает
   резерв. Единичный отказ не переводит систему на резерв целиком — через резерв
   идёт только сломавшийся аккаунт, остальные собираются через Nitter.
4. **Типизированные ошибки.** `NitterTransportError` (право на резерв),
   `NoLiveInstance` (право на резерв), `NitterNotFound` и `EmptyFeedError` (резерв
   НЕ включают) — причина отказа доносится до коллектора.
5. **Потолок и темп резерва.** Новый параметр `config.XSSR_MAX_PER_RUN` (по
   умолчанию 50) ограничивает число обращений к резерву за прогон; пауза между
   запросами резерва — `XSSR_MIN_INTERVAL_SEC` ≥ 2 с (замер: x.com держит ~2,05 с
   на запрос). Текст из резерва подчиняется правилам ТЗ-4: текст Nitter не
   перезаписывается, метрики не выдумываются.

**Новые параметры конфига.**

| параметр | значение | смысл |
|---|---|---|
| `XSSR_MAX_PER_RUN` | 50 | потолок обращений к резерву за один прогон сбора |
| `XSSR_MIN_INTERVAL_SEC` | 2.0 | пауза между запросами резерва (было 1.0) |
| `HEALTH_XSSR_ACTIVE_HOURS` | 6 | резерв активен дольше — ALERT «Nitter лежит долго» |
| `HEALTH_COLLECT_FAIL_PER_HOUR` | 20 | фактических отказов сбора Nitter за час больше — ALERT |

**Схема БД.** `SCHEMA_VERSION` 3 → 6: у таблицы `instances` появились
`collect_fail_streak` и `reserve_since` (момент включения резерва). Миграция
идемпотентна; `reserve_since` снимается первым успешным фидом Nitter.

**Наблюдаемость.** Итоговая строка `collect` печатает: сколько аккаунтов ушло
через резерв, сколько было фактических отказов Nitter, сколько аккаунтов
потеряно (цель — 0) и причину переключения. Сторож печатает `ALERT`, если резерв
активен дольше 6 ч или фактических отказов сбора за час больше порога; в норме
молчит.

**Замер ДО/ПОСЛЕ (копия боевой базы, реальный мёртвый адрес `http://127.0.0.1:9`,
резерв подменён мок-транспортом — живой x.com запрещён условиями ТЗ).**
ДО (ревизия до ТЗ-10): `аккаунтов=2 ok=0 fail=2 x_ssr=0 резерв=0 потеряно=2` —
оба аккаунта потеряны. ПОСЛЕ: `аккаунтов=2 ok=2 fail=0 x_ssr=2 резерв=2
отказов_Nitter=6 потеряно=0` — оба собраны через резерв в том же прогоне.

## ТЗ-18. Приём кандидатов X из внешних фидов

**Источник.** Два проекта-экспортёра пишут один JSONL (`kind`, `handle`,
`mentions`, `videos[]`, `ai_hint`, `first_seen`, `last_seen`, `source`,
`sources[]`, `examples[]`, `exported_at`):
`/root/tuber-os/data/exchange/external_candidates.jsonl` (описания YouTube) и
`/root/tuber-telegram/data/exchange/external_candidates.jsonl` (посты Telegram).
Отсутствие файла — не ошибка (`feeds_missing`).

**Команда.** `python -m tuber_x.cli import_candidates --feed <путь> [--feed ...]
[--limit N] [--dry]`. Берутся только строки `kind="x"`. Чужой `kind` —
`skipped_kinds`, битая строка — `bad_lines`, импорт продолжается. Ошибка (код 2)
только на пустом фиде или фиде, где все строки битые. Сети нет: команда только
наполняет очередь, верификация не запускается.

**Фильтры** (с разбивкой в `skipped_filter`): нормализация хендла
(`bad_handle`), служебные хендлы (`service_handle`), стоп-лист (`blocklist`),
уже в реестре (`already_registered`), бот-шаблон (`bot`), новостник-гигант
(`news_giant`, `config.NEWS_GIANTS`), порог упоминаний
(`below_mention_threshold`). Порог берётся из `VERIFY_MIN_MENTIONS` конфига
фильтра проекта и не меняется.

**Слияние** по `handle`: `seen_count += mentions`; `distinct_sources` = длина
объединённого списка источников (учитываются `sources[]` и `source`); минимум
`first_seen_at`, максимум `last_seen_at`; `found_via` и `feed_source` дополняются
без дублей (`yt_desc:tuber-os`, `tg_posts:tuber-telegram`); `ai_hint` = OR;
`priority` — существующей `registry.candidate_priority`. Существующие
`validated`, `reject_reason`, `verified_at`, `llm_checked` не меняются никогда;
новые кандидаты создаются с `validated=NULL`. Ни один кандидат не регистрируется
в `accounts` сам по себе.

**Схема.** `SCHEMA_VERSION` 6 → 7: в `candidates` добавлены
`ai_hint INTEGER DEFAULT 0` и `feed_source TEXT`. Миграция аддитивная
(`ALTER TABLE ADD COLUMN`), безопасна на живой базе.

**Сводка.** В суточную сводку ТЗ-12 добавлена строка о притоке: сколько пришло
из описаний YouTube, сколько из постов Telegram, сколько всего в очереди и за
сколько суток очередь закроется при текущем бюджете
(`ceil(очередь / DISCOVERY_MAX_VERIFY_DEFAULT)` при
`DISCOVERY_DAILY_BUDGET` запросах/сутки).
