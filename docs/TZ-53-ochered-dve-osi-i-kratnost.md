## Факты

1. Таблица `score`: 605 648 строк. Схема (PRAGMA): `content_id, computed_at, significance, branch,
   engagement, velocity, spread, first_mover, decay, freshness, xconf, anomaly, metrics_missing,
   metrics_at, metrics_age_hours, axes_json, parts_json, story_id, platform, external_id`.
2. `branch` заполнена у **5 216** строк из 605 648 (0,86 %): `graph` 3 297, `popularity` 1 919,
   NULL — 600 432 (99,1 %). То есть деление «нашлось по норме своего автора» против «нашлось по
   абсолютной величине» в базе фактически отсутствует.
3. `branch` пишет только путь X: `tuber/platforms/x/scores.py:150` (`"graph" if missing else "popularity"`).
   Ещё два писателя score: Telegram `tuber/platforms/telegram/store.py:864` (колонки score через
   представление `scores`) и YouTube `tuber/platforms/youtube/store.py:1321` (`save_score` →
   `storage.upsert_score`) — оба ветку не ставят. **Проверь сам, какие поля передаёт каждый писатель,
   и приведи в отчёте точный список.**
4. `axes_json` уже несёт относительные оси: у X это `er`, `eng_channel` (вовлечённость к норме канала),
   `eng_global`, `wsrc`, `dup_penalty`, `fr`, `topic_weight`, `age_days`.
5. Кратность (во сколько раз материал выше нормы) сейчас считается **на лету при выдаче**, в базе не
   хранится: `tuber/analysis/report.py:1113` `_norm_map` (медиана по автору + число материалов),
   X — медиана лайков автора (`report.py:1433`, порог `VIRAL_X_MIN_AUTHOR_MEDIAN`), Telegram —
   `source_baseline.median_views` (`report.py:1288`), YouTube — медиана просмотров канала за окно
   (`report.py:1570`, `_norm_map`). Из-за этого готовую находку невозможно перепроверить: неизвестно,
   по какой норме и какой выборкой она получена.

## Что сделать

1. **Хранить основу находки.** Добавить в `score` колонки (идемпотентная миграция в `tuber/core/schema.py`,
   образец — `backfill_metric_schedule_status`):
   - `norm_value REAL` — сама норма (медиана автора/канала или значение базовой таблицы);
   - `norm_sample INTEGER` — сколько материалов легло в норму;
   - `norm_window_hours INTEGER` — окно, по которому норма считалась;
   - `norm_kind TEXT` — откуда норма: `author_median` / `channel_median` / `baseline_table`;
   - `lift REAL` — кратность: величина материала ÷ норма;
   - `lift_at TEXT` — время величины, по которой кратность посчитана (момент снимка, не время расчёта).
2. **Заполнять эти поля для всех трёх площадок** (X, Telegram, YouTube) тем же расчётом, что и выдача:
   - пороги и минимумы брать из существующих констант (`VIRAL_X_MIN_AUTHOR_MEDIAN`, минимум материалов
     для медианы канала YouTube, Telegram — `source_baseline`), **не выдумывать новые**;
   - если выборки для нормы не хватает — `norm_value`/`lift` = NULL, `norm_kind` = причина отсутствия
     (`no_norm_sample`), и материал считается только по абсолютной оси. Пустое поле обязано отличаться
     от «нормы нет» явным значением.
3. **Заполнить `branch` для всех трёх площадок**: `local`, если материал найден по кратности к норме
   (норма есть и кратность посчитана), `popular`, если нормы нет и материал оценивается абсолютной
   величиной. Существующие значения `graph`/`popularity` у X не переименовывать и не терять — опиши в
   отчёте, как они соотносятся с новыми (`local` = `graph`?), и предложи способ свести без потери истории.
4. **`significance` не менять.** Работа добавленная: рейтинг остаётся как есть, новые поля только
   объясняют находку.
5. **Замер до/после** (сначала копия, потом боевая):
   - сколько строк имеют `lift IS NOT NULL` и `norm_value IS NOT NULL` по каждой площадке до и после;
   - распределение `branch` по площадкам до и после;

     ручной сверкой одной строки с прямым запросом к `metric_snapshot` (показать оба числа).
6. **Тест**: расчёт кратности и `norm_kind` на подготовленных данных (нормы хватает; нормы не хватает;
   площадка Telegram; площадка YouTube). Существующий набор тестов зелёный, число пройденных — в отчёте.
