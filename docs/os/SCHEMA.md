# Tuber_OS — схема данных (этап 3, 10.09.2026)

Проектирование под три вопроса, которые механизм обязан отвечать каждый день:
**что растёт**, **почему растёт** (SEO-разбор), **о чём это** (темы и русское описание).

## 1. Инварианты

1. **Время — целым числом.** Все моменты (`published_at`, `captured_at`, `first_seen`) —
   unixtime в секундах. Строки с датами ломаются на сравнениях: проверено на живых данных,
   `"2026-09-10T00:30:00Z" > "2026-09-10 06:00:00"` даёт True вместо False.
2. **Замер хранит своё приращение.** Дельта и интервал считаются в момент записи замера
   и лежат в той же строке. Пересчёт задним числом должен быть возможен, но не обязателен.
3. **Ненаблюдаемое не хранится.** Полей под CTR и удержание чужого видео в схеме нет —
   их нельзя получить. Пустое место честнее нуля, который потом кто-то просуммирует.
4. **Оценка без базы — NULL, не ноль.** Outlier не считается, пока у канала меньше
   5 замеренных видео: вместо выдуманного множителя пишем NULL.
5. **Один формат для одного поля.** Теги — только JSON-массив, обложка — только
   проверенный URL, тема — только из закрытого списка.
6. **Каждая запись замера уникальна.** Индекс `(video_id, bucket, captured_at)`
   не даёт записать два замера в один слот и исказить скорость.

### 2.4 Медианы для outlier — расчёт на лету

Отдельной таблицы нет. Медианы для outlier считаются на лету в
`tuber/report.py` (`_outlier_map`) по ключу `(канал, формат)`: шортсы и полные
видео считаются раздельно, иначе медиана канала смешивает разные единицы
измерения. Выборка берётся из последних замеров, отдельный кэш не нужен.
Решение принято 13.09.2026: таблица `channel_baseline` удалена из схемы — в
боевой базе она была пуста и не читалась ни одним модулем.

## 3. Расчёт скорости: как именно

Для пары замеров одного видео:

```
interval = captured_at₂ − captured_at₁          (секунды)
delta    = views₂ − views₁
views_per_day  = delta / (interval / 86400)
views_per_hour = delta / (interval / 3600)
```

Защита от мусора:
- `interval < 600` секунд — замер не считается парным (слишком близко, шум);
- `interval < 3600` секунд (`MIN_INTERVAL_FOR_SPEED_SECONDS`) — дельта честная и
  сохраняется, но `views_per_day`/`views_per_hour` = NULL, `interval_quality='short'`:
  экстраполяция с 6-12 минут — это шум выборки, а не тренд;
- `interval >= 3600` — скорость считается, `interval_quality='ok'`;
- первый замер видео — `interval_quality='first'`, дельты NULL;
- в отчёт («Что растёт» и производные блоки) попадают только замеры `ok`;
- `delta < 0` — сигнал аномалии (чистка счётчиков или накрутка): писать, но помечать;
- видео моложе 1 часа — скорость считать, но в отчёт не выводить (слишком шумно);
- окно «за 10 дней» = сумма дельт по всем парам, попавшим в окно, делённая на
  фактическое покрытие окна. Это устойчивее, чем «последний замер минус первый»:
  если один замер пропущен, покрытие честно уменьшается.

## 4. Расчёт outlier

```
baseline = медиана просмотров по последним N видео канала (N >= 5, окно 90 дней)
outlier  = views видео / baseline
```

Медиана, а не среднее: один вирусный ролик сдвигает среднее и глушит все
последующие оценки канала. Порог значимости — 3x (индустриальный стандарт).
При выборке меньше 5 видео — NULL.

### 5.1 Как считается расход

Учёт ведётся по журналу `quota_log`: каждая запись хранит ключ, время, число вызовов и units.
Дневная граница — **полночь по Калифорнии** (`America/Los_Angeles`), потому что именно по этому
поясу Google обнуляет квоту; в UTC это 07:00 летом и 08:00 зимой. Предохранитель останавливает
работу на пороге «лимит минус запас» (8 000 из 10 000 units), оставляя запас на завершение
текущего прогона.

Лимит 10 000 units выдаётся **проекту Google Cloud**, а не отдельному ключу. Пока привязка
«ключ → проект» не заполнена, расход считается на ключ: для одного проекта это может
занизить счётчик во столько раз, сколько ключей в нём. Заполнение привязки переводит учёт
на проект без изменения кода.

Остаток квоты — запас на расширение пула и на дни с высокой активностью.
Замеры почти бесплатны — именно поэтому частые замеры свежих видео возможны.
Замеренный общий расход по всем ключам — около 9,5 тыс. units в сутки, то есть близко
к лимиту проекта: если все ключи лежат в одном проекте Google Cloud, дни высокой
активности упираются в потолок (см. раздел 5.1).
