### 1.3 capture_snapshots.py (212 строк) — снапшоты метрик и viral_score

1) Механика. Отбор: videos.first_seen за 14 дней И (нет снапшота за сегодня
ИЛИ published_at за последние 2 дня) (23-45). Шаг 1 — батчами по 50
videos.list part=statistics и UPDATE метрик в videos (48-76). Шаг 2 —
повторная выборка уже обновлённых значений (172) и расчёт viral_score
(86-158), запись строки в snapshots (182-195).

Формула v2: vpd = views / дней с публикации; rel = min(log10(1 + views/subs), 3);
freshness = max(0.3, 1 - days/14); like_ratio, comment_ratio; engagement =
min(1 + 10*like_ratio + 100*comment_ratio, 6.0); growth_bonus (см. ниже);
ГЕЙТ: views >= 5000 И vpd >= 100, иначе score = 0 (112-148).
Строка при этом пишется всегда, даже с score=0.

2) Поля/метрики: view_count, like_count, comment_count, views_per_day,
viral_score, like_ratio, comment_ratio, growth_bonus, freshness,
engagement_bonus, captured_at (184-194).

3) РОСТ — единственное место, где динамика вообще считается, и считается
плохо:
- Берётся views_per_day ПРЕДЫДУЩЕГО снапшота по ORDER BY captured_at DESC
  (129-137) и growth_bonus = vpd_now / max(0.1, vpd_prev) - 1, зажатый в
  [-0.5, +2.0] (140-141).
- Это НЕ дельта между замерами и не скорость прироста. views_per_day — это
  кумулятивное среднее (все просмотры / весь возраст видео), поэтому
  отношение средних ≠ рост за интервал.
- Интервал между замерами в знаменателе не учитывается: если замер пропущен
  (цикл упал), знаменатель не меняется, а числитель уже вырос — метрика
  искажается.
- Дельта просмотров/лайков/комментариев между снапшотами НЕ хранится: в схеме
  нет колонок delta_views/delta_likes/delta_comments (sqlite3 .schema
  snapshots), код их не считает. Вывести их можно только SQL-диффом вручную.
- Рост комментариев/лайков отдельно не считается нигде.
- Практический результат: growth_bonus отрицательный в 18347 снапшотах из
  22442 (82%), положительный в 1924, нулевой в 2171 — метрика систематически
  штрафует почти все видео (эффект затухания кумулятивного среднего).
- В дайджест рост не выводится вообще (publish_digest.py:140-155 показывает
  только абсолютные просмотры, лайки, тип, возраст).
- Нет velocity первых часов/суток: снапшоты снимаются максимум 2 раза в сутки
  (крон 10:00/19:00), распределение — 1413-1500 снапшотов в день на 2081
  видео, у 513 видео ровно 15 снапшотов.

4) SEO-поля: не собирает ничего SEO-специфичного; на входе — уже собранные
поля из videos (в снапшот попадают только метрики, но не title/description/
tags).

5) Дефекты:
- Гейт MIN_VIEWS/MIN_VPD обнуляет score, но не отсекает видео от дальнейшей
  обработки: 11 видео с просмотрами < 5000 лежат в videos, из них часть
  попадает в выборки.
- freshness = max(0.3, 1 - days/14) при days >= 10 уже упирается в пол 0.3 —
  фактически константа для большинства старых видео.
- subscriber_count берётся из ТЕКУЩЕГО состояния канала (29-34), а не на
  момент публикации видео → rel искажён для каналов, выросших после релиза.
- Комментарии по ошибкам пишутся в stderr и теряются (197-199): при сбое
  видео просто выпадает из снапшота без отметки в БД.
- CUTOFF/окна зашиты константами (18-20), в конфиг не вынесены.

## 3. vision_describe.py: как именно разбираются обложки

Что вызывает: POST http://localhost:8601/vision (vision_describe.py:29, 71-88)
с телом {"image": <URL maxres-обложки>, "prompt": PROMPT}. PROMPT (32-35):
«Опиши обложку видео: что на ней изображено, есть ли текст (прочитай его),
какие эмоции, о чём видео по обложке. Максимум 3 предложения по-русски».

Сервис: /root/dsh-integrations/vision_bridge.py, процесс
«python3 /root/dsh-integrations/vision_bridge.py --server --port 8601»
(pid 1715501).

Модель и цепочка (vision_bridge.py:96-174):
1) Основная — deepseek-v4-flash-vision-exp через api.deepseek.com с ключом из
   /root/.hermes/.env (DEEPSEEK_VISION, 41, 107-136), max_tokens=1200.
   Ответ API приходит с полем model=«deepseek-flash».
2) Фолбэк при ошибке/429 — анонимный OVHcloud AI Endpoints
   (oai.endpoints.kepler.ai.cloud.ovh.net) с ротацией по 5 моделям
   (58-64): Qwen2.5-VL-72B-Instruct, Qwen3.5-397B-A17B,
   Mistral-Small-3.2-24B-Instruct-2506, Qwen3.6-27B, Qwen3.5-9B; лимит
   ~2 req/min/IP/модель, 429 → сразу следующая модель (161-164).
Фактические модели в БД (video_vision.model): deepseek-v4-flash-vision-exp 23,
Qwen2.5-VL-72B-Instruct 1, Mistral-Small-3.2-24B-Instruct-2506 1 — то есть
95% вызовов ушло через платный DeepSeek, фолбэк почти не задействован.

Что извлекается: один абзац русского текста (описание содержимого обложки +
прочитанный текст + эмоции + вывод о теме видео). В таблицу сохраняются
video_id, description, model, created_at (129-132). Объём в БД — от 275 до
575 знаков на видео. Структурированных полей нет; текст на обложке не
выделяется в отдельное поле; в make_digest.py:190-192 описание подмешивается
в промпт перевода.

Стоимость вызова (замер вживую 10.09.2026, обложка loCU36T8orQ,
maxresdefault.jpg 80 303 байта, прайс deepseek-v4-flash из
usage_pricing.py:504-512: вход 0.14 / выход 0.28 / кэш 0.0028 за 1M):
- вызов 1: prompt_tokens 656 (из них 512 из кэша), completion_tokens 1200
  (из них reasoning 1148), латентность 11.1 с → $0.000358. Бюджет max_tokens
  выбран полностью — выход обрезан на границе лимита.
- вызов 2: prompt_tokens 656 (512 кэш), completion_tokens 585 (reasoning 411),
  латентность 4.3 с, длина ответа 534 знака → $0.000185.
Итого порядок: $0.0002-0.0004 за обложку, в среднем ~$0.00027. Лимит 8
обложек за цикл × 2 цикла/сутки ≈ $0.004/сутки ≈ $0.13/месяц.
Важно: 60-95% оплачиваемых выходных токенов уходит в скрытый reasoning, а не
в текст описания; при первом замере описание было обрезано лимитом.
Отдельной записи для модели -vision-exp в usage_pricing.py нет (grep -i vision
даёт только строку документации 954) — стоимость нигде не учитывается:
ни vision_bridge.py, ни vision_describe.py не вызывают ds_usage.

Дополнительно: 404 по maxres (у многих видео его нет) обрабатывается как
полноценная ошибка — 3 ретрая внутри vision_describe (73-88) с паузами 5 и
10 с, затем повторный вызов на original-качество (126-127); функция
fetch_thumbnail (56-68), которая должна была проверять картинку заранее, не
вызывается. В логе — «vision_fail ... /maxresdefault.jpg».
