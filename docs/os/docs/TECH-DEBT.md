### D-14. Индекс виральности: ось просмотров без окна и среднее по наличным осям

**Открыт:** 16.09.2026.

**Суть.** Композитный индекс (`tuber/viral.py`) собирается по осям, которые у
видео реально есть. Две несогласованности зафиксированы осознанно, чтобы не
менять формулу на глаз:

1. Ось просмотров использует готовый `outlier_score`, который
   `tuber/report.py::_outlier_map` считает к медиане канала за ВСЮ историю, а
   лайки/комментарии/упаковка нормируются на окно `VIRAL_CHANNEL_WINDOW_DAYS`
   (90 дней). Базы сравнения у осей разные.
2. Индекс — среднее геометрическое только по НАЛИЧНЫМ осям. Видео с двумя осями
   (`views` и `packaging`) может получить больший индекс, чем более виральное
   видео с четырьмя осями, потому что отсутствующие оси не разбавляют среднее.

**Почему не чиним сейчас.** Индекс вводится впервые, отчёт только начинает
накапливать нарезку по осям; менять формулу раньше, чем видно её поведение на
неделях данных, — значит чинить по догадке, а не по факту.

**Что сделать.** Пересчитать ось просмотров по окну 90 дней (единая база);
посчитать вариант со средним по всем четырём осям (отсутствующая = 1) и сравнить
топы; принять решение по результатам замера, затем обновить эту запись.

**Маркер:** `# TODO(debt-D-14)` в `tuber/viral.py`.

### D-11. Счётчик квоты падал на подключении без row_factory

**Закрыт:** 15.09.2026.

**Суть.** `YouTubeClient.spent_today()` и `search_calls_today()` читали значение
запроса по имени колонки (`row["u"]`, `row["n"]`), причём `int(...)` стоял ВНЕ
`try/except`. На подключении без `row_factory = sqlite3.Row` (обычный
`sqlite3.connect()`) строка — это `tuple`, и `row["u"]` поднимал
`TypeError: tuple indices must be integers or slices, not str`, который улетал
наружу и РОНЯЛ сбор. При этом докстрока обещала обратное: «сбой чтения учёта не
останавливает работу, пишем warning и считаем 0».

**Чем закрыт.** Значение читается ПОЗИЦИОННО (`row[0]`), а возврат перенесён
внутрь `try`: теперь любой сбой чтения (включая нечисловое значение) даёт
`log.warning` + 0 при любой форме подключения. Тот же приём применён к
`candidates._quota_total()` (та же ошибка `int(row["u"])` вне `try`).
Поведение при сбое прежнее. Маркер `TODO(debt-D-11)` оставлен у мест правок в
`tuber/yt.py` и `tuber/candidates.py` (по требованию ТЗ-19 приёмки).

**Покрыто:** `tests/test_quota_search.py`, `tests/test_candidates.py` — чтение
значения счётчика на подключении без `row_factory` и что сбор при этом не падает.

### D-10. Учёт квоты должен считаться на проект, а не на ключ

**Закрыт:** 15.09.2026.

**Суть.** YouTube Data API v3 даёт 10 000 units в сутки на **проект** Google Cloud, а не на
ключ, и отдельно ограничивает **100 вызовов `search.list` в сутки на проект**. Учёт расхода
по проекту был готов, но привязка ключей к проектам в боевом `yt_keys.json` не заполнена,
поэтому действовал режим «на ключ»: два ключа одного проекта могли вместе выйти за проектный
лимит (по units — вдвое, по поиску — кратно числу ключей). Историческая справка (проверена
`git grep` по коммиту-предку `fdc4186`): до появления учёта расхода `QUOTA_LIMIT_PER_KEY =
10000` и `QUOTA_SAFETY_RESERVE = 2000` были только объявлены и нигде не читались, защита шла
по ошибке API `403 quotaExceeded`.

**Замеры (боевая `data/tuber.db`, только чтение):**

- 13.09.2026: расход за сутки по ключам ≈ **9 520 units**, каждый ключ по отдельности далёк
  от 10 000.
- 15.09.2026 (сутки квоты 14.09 по Pacific Time): расход **9 578 units**, из них
  `search.list` — **8 100 units = 81 вызов** (85% расхода). По ключам поисковых вызовов:
  `<key-id-1>` — 28, `<key-id-4>` — 26, `<key-id-3>` — 14, `<key-id-2>` — 13.

**Чем закрыт (части A, B, C ТЗ-16):**

1. **Привязка ключей к проектам.** В боевом `/root/.hermes/data/yt_keys.json` проставлен
   проект `<gcp-project-number>` у двух ключей — `<key-id-1>` и `<key-id-2>`; перед правкой сделана
   резервная копия `yt_keys.json.bak-20260915-225733`. **Без привязки остались четыре ключа:**
   `<key-id-3>`, `<key-id-4>`, `<key-id-5>`, `<key-id-6>` — их проекты без обращения к
   консоли Google Cloud (страница ключей API) не восстановить, выдумывать нельзя. Для них
   поведение прежнее: и units, и поиск считаются **по ключу**.
2. **Units по проекту** (было готово): `QUOTA_LIMIT_PER_PROJECT = 10000`, порог остановки
   `10 000 − QUOTA_SAFETY_RESERVE (2 000) = 8 000` units; считается в одном месте —
   `YouTubeClient.quota_stop_threshold`.
3. **Вызовы поиска по проекту** (новое): `QUOTA_SEARCH_LIMIT_PER_PROJECT = 100` и
   `QUOTA_SEARCH_RESERVE = 15`; порог `100 − 15 = 85` считается рядом —
   `YouTubeClient.search_stop_threshold`. Перед отправкой `search.list` считается число
   попыток (`quota_log.endpoint = 'search'`, сутки Pacific Time): для ключа с проектом —
   сумма по всем ключам проекта, для ключа без проекта — по ключу. На пороге вызов **не
   отправляется и units не тратятся**, поднимается событие вида
   `search quota guard: проект <gcp-project-number>: 85/100 (лимит 100, резерв 15)`.
4. **Прогон не падает:** `expand` и `collect` ловят событие и продолжают бесплатными
   механизмами (разбор имён, упоминания, обход плейлистов). Причина пропуска поисков попадает
   в итог прогона (`search_guard` в `collect`, `search_guard_reason` в `expand`).

**Что защищено теперь (по проекту):** units (10 000/сутки) и вызовы поиска (100/сутки) — для
двух связанных ключей; для четырёх несвязанных — по ключу, как раньше.

**Честная оговорка.** Предохранитель по вызовам поиска — вторая линия защиты, а не замена
units-порога. Поиск стоит 100 units, поэтому при проектном учёте units-порог 8 000
срабатывает около 80-го поиска раньше, чем 85-й по счётчику вызовов. Отдельный счётчик нужен
потому, что (а) он считает именно то, что ограничивает Google (число вызовов), и не зависит
от цены поиска, (б) он защищает случай, когда units считаются по ключу, а поиск должен
считаться по проекту. На 15.09.2026 у связанного проекта расход далеко ниже обоих порогов
(41 поиск, ≈ 4 800 units за сутки).

**Когда пересматривать:** после привязки оставшихся четырёх ключей к проектам — счётчики
переключатся на проект автоматически. Если появятся проекты с несколькими ключами и поиском
чаще 85/сутки, сверить с реальным лимитом Google.

**Покрыто:** `tests/test_quota_search.py` — (a) два ключа одного проекта делят счётчик
(60 + 25 = 85 → поиск блокируется, вызов не уходит, квота не тратится); (b) счётчики разных
проектов независимы; (c) ключ без проекта считается по ключу; (d) ниже порога поиск проходит;
ровно 85 — блок; не-поисковый эндпоинт предохранитель не трогает; `expand`/`collect` ловят
событие и не падают. `tests/test_quota_project.py` — сумма units по двум ключам одного проекта
и старый формат файла.

Арифметика ёмкости (допущения: не больше `EXPAND_MAX_CHANNEL_SEARCHES_PER_RUN = 2` поисков
каналов за прогон; каждая фраза проходит не больше двух кругов, правило `runs < 2`): одна фраза
даёт до 2 поисков, весь пул — до 879 × 2 = 1758 поисков, значит прогонов хватает примерно на
1758 / 2 = **879**. Двойка поисков на фразу и двойка фраз на прогон сокращаются, поэтому ёмкость
численно равна размеру пула. Один прогон тратит на поиск каналов до 200 units (2 фразы × 100) —
2% суточного лимита ПРОЕКТА (10 000 units). Если ключи разложены по разным проектам, на каждый
ключ приходится свой лимит 10 000 units. Повтор полезен:
2 повторных поиска 13.09 12:45 дали 4 новых канала-кандидата за 200 units, поэтому очередь нельзя
застревать на четырёх фразах.

Числа 1545 (и выведенное из одного круга «≈760») из прошлых замеров на снимке 13.09 13:18 не
воспроизводятся: база дрейфует (находки `term_mining` приходят каждый прогон), поэтому цифры выше
даны с датой и временем снимка. Формула ёмкости — 879 × 2 / 2 = 879 прогонов; прежняя запись
«≈760» противоречила тут же написанному правилу двух кругов и опиралась на неверную арифметику.

**Короткие фразы и маркеры плейлистов (ТЗ-34):** миграция ТЗ-33 (`db._migrate_drop_dead_queries`)
ошибочно закрыла как «непригодные» рабочие двухбуквенные фразы `ai`, `ии`, `ml` и 728 маркеров
обхода плейлистов `playlist:*`/`playlists:*` (`source='playlist'`). Правило исправлено: фраза
годится при не меньше двух знаках, если состоит только из букв (латиница/кириллица) и разделяющих
пробелов — годятся `ии`, `аи`, `ai`, `ml`; НЕ годятся один знак, цифры (`3d`), `:`, `/`, строки без
букв. Служебные ключи обхода под закрытие больше не подпадают (условие `source <> 'playlist'`), а
миграция-исправление `db._migrate_restore_usable_queries` вернула все 731 ошибочно закрытые строки
(728 маркеров + 3 фразы) в `accepted` с очищенной причиной. Строки не удалялись и не удаляются:
обход плейлистов работает по ним как раньше, а `ai`/`ии`/`ml` теперь входят в пул (879 = 876 + 3).
Окончательно закрытых новым правилом строк среди `accepted/new` нет: единственные непригодные

`'не ИИ-запрос'` и не трогаются.

### D-03. Признак «≥2 ИИ-видео» пропускал корпоративные каналы
