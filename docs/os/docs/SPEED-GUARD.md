# Предохранитель расчёта скорости (этап 10)

## Проблема

`views_per_day` считался как дельта просмотров, делённая на интервал и
умноженная на сутки. На коротком интервале это даёт абсурд:

| интервал | множитель экстраполяции | пример |
|---|---|---|
| 748 с (12,5 мин) | ×115,5 | 4583 просмотра → «33 959 в сутки» |
| 383 с (6,4 мин) | ×225,6 | 1094 просмотра → «21 201 в сутки» |

Экстраполяция с двенадцати минут — это шум случайной выборки, а не тренд.
В отчёт такие цифры попадать не должны: они выглядят как факт, но фактом не
являются.

## Решение

1. `config.MIN_INTERVAL_FOR_SPED_SECONDS` (по умолчанию **3600** с, читается из
   окружения). Скорость считается только если между замерами прошёл час.
2. `db.insert_snapshot` пишет колонку `snapshots.interval_quality`:
   - `first` — первый замер видео, дельты считать не от чего;
   - `short` — интервал меньше порога: дельты просмотров сохраняются (они
     честные), но `views_per_day` / `views_per_hour` = **NULL**;
   - `ok` — интервал достаточный, скорость посчитана.
3. `db.migrate_interval_quality` идемпотентно пересчитывает старые замеры.
   У существующей БД колонка добавляется, и миграция прогоняется один раз
   автоматически при `init_db`; вручную — `python3 -m tuber migrate-speed`.
4. `report.build_report` берёт в «Что растёт» только `interval_quality='ok'`,
   показывает в шапке разбивку замеров и честно сообщает, когда пригодных
   замеров нет (без нулей вместо данных).

Дельты просмотров не обнуляются на коротком интервале: сама дельта честная,
шумной является только производная «скорость».
