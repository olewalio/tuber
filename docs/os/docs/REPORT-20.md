## Часть A. Обёртки заданий

Обе обёртки — по образцу `tuber-telegram/scripts/cron_collect.sh`: запускают
команду через venv-питон Hermes (`/usr/local/lib/hermes-agent/venv/bin/python3`,
`timeout 900`), пишут вывод в `logs/bridge-*.log`, тихие при норме и **всегда
завершаются кодом 0** (аномалия — не «сбой задания»). Одна понятная строка в
stdout печатается только при аномалии:

- итог не-JSON/пусто;
- `error`/`errors` непусто;
- фид не найден или пуст;
- ни одного канала не разрешено при непустом фиде (признак разрыва формата);
- экспорт записал 0 строк.

Идемпотентность: повторный импорт при том же фиде даёт `new=0`, и это **норма**
(тишина), если часть каналов уже известна (`known>0`). Строка печатается только
когда не разрешён **ни один** канал.

Тестовые хуки без сети: `TU_EXPORT_TEST_JSON`, `TU_IMPORT_TEST_JSON`, `*_CRON_LOG`,
`TU_IMPORT_FED`, `TU_CRON_DB`, `TU_EXPORT_OUT`, `TU_IMPORT_LIMIT`.

**Важная деталь:** у `candidates-import` в CLI потолок `--limit` по умолчанию 50, а
фид моста содержит 87 видео. Поэтому обёртка явно передаёт `--limit 300` (перекрывает
`TU_IMPORT_LIMIT`), иначе за один ночной прогон разбиралась бы только часть фида.

## Часть B. Установщик и единый источник расписания

`scripts/install_hermes_cron.sh`:

- блок `JOBS=(...)` — единственный источник истины (новые задания моста + действующие
  `tuber_daily.sh`, `tuber_snapshots.sh`);
- создаёт **настоящие файлы-шимы** в `/root/.hermes/scripts/` (не симлинки: планировщик
  разыменовывает путь и отклоняет ссылку наружу), внутри — `exec` обёртки;
- идемпотентен, посторонние файлы не трогает;
- `--dry-run` / `HERMES_INSTALL_DRYRUN=1` — только печать;
- печатает таблицу «шим | расписание | что делает» для регистрации владельцем.
- Задания в планировщике **регистрирует владелец**; установщик их не создаёт и в
  crontab не пишет.

## Часть C. Тест синхронизации

`tests/test_schedule_sync.py` парсит блок `JOBS` установщика и сверяет его с
фактическими заданиями проекта в `/root/.hermes/cron/jobs.json` по паре «имя
скрипта-шима + расписание». Отбор заданий проекта: префикс `tuber_os_*` плюс
исторические `tuber_daily.sh`, `tuber_snapshots.sh`. Отсутствие `jobs.json` — `skip`
с причиной. Синтетическая проверка ловит случай «то же задание, другое время». Пути
переопределяются `TUBER_OS_INSTALLER` и `TUBER_OS_HERMES_JOBS_JSON`.

## Рекомендации

1. Потолки `--limit` (300/1000) подобраны под текущий размер фида. При росте фида
   выше потолка импорт растянется на несколько ночей — поднять `*_IMPORT_LIMIT`.
2. Держать блок `JOBS` единственным источником: любое изменение расписания — сначала
   в установщике, потом у владельца; тест поймает расхождение.
3. При добавлении новых заданий моста обновлять сразу три места: обёртку, блок
   `JOBS`/`LAUNCHERS` установщика и `docs/SCHEDULE.md`.
