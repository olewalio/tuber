## Часть 1. Дыры сбора

### 1.1 Форварды — честный результат: из `t.me/s` их взять нельзя

Что сделано: в `collect.py` выделен `extract_forwards(msg)`, счётчик пишется в
`posts.forwards` при вставке/обновлении; в `scoring.py` — команда `forwards`
(бэкфилл по страницам каналов).

Что показал бэкфилл (полный, на копии, 400 с):

| Метрика | Значение |
|---|---|
| каналов просканировано | 421 |
| страниц скачано | 418 |
| постов увидено | 6 927 |
| **форварды заполнены** | **0** |
| осталось NULL | 9 235 (все посты) |
| ошибок сети | 3 |

Причина (проверена на живой разметке `t.me/s/durov`, `/chatgptv`, `/techsparks`,
`/deepl…` и др.): публичное веб-превью **не содержит счётчика форвардов**. В
футере сообщения есть только `tgme_widget_message_views` (просмотры) и
`tgme_widget_message_forwarded_from[_name]` (признак, что сама публикация —
пересылка, т.е. это `is_forward`/`fwd_from`, а не число форвардов).

Найденный и устранённый ложный путь: наивный парс «любого класса со словом
forward» даёт ложные форварды из имени канала-источника — «Forwarded from
**42** секунды» давало `forwards=42` (зафиксирован как баг до коммита). Теперь
классы `*forwarded_from*` отсекаются по подстроке токена.

Вывод (долг **D-01**): реальные форварды даёт только Telethon/MTProto
(`Message.forwards`), см. DESIGN §4.1 — это отдельная работа с учётом квоты.

### 1.2 Базы каналов (`channel_baselines`)

| Метрика | Значение |
|---|---|
| каналов с постами в окне | 412 |
| попало в базы (≥5 постов) | 391 |
| из них авторских по данным | 383 |

### 1.3 Признак агрегатора данными (правило, не ручная разметка)

Правило (описано здесь и в `channel_baselines`): пост считается **перепостом**,
если тот же `text_hash` встречается в **другом** канале в пределах **±48 ч**.
`dup_ratio` = доля таких постов среди постов с текстом. Если у канала ≥5 постов с
текстом и `dup_ratio ≥ 0.5` → `is_author = 0` (агрегатор); иначе `is_author = 1`
(автор). Меньше 5 постов с текстом → `is_author = NULL` («неизвестно», а не 0:
нельзя выдавать незнание за агрегатор).

| `channels.is_author` | было | стало |
|---|---|---|
| NULL (неизвестно) | — | 760 |
| 0 (агрегатор) | 995 | **2** |
| 1 (автор) | 0 | **383** |

Агрегаторы по данным: `@ankitavasthi` (14/14 постов — дубли), `@apnipathshalaup`
(13/14). Это **не ручная разметка**: точный `text_hash` ловит только копии
«символ-в-символ». Почти-дубли (синонимы, перестановки) требуют simhash —
долг **D-06**. Поэтому 2 агрегатора — заниженная оценка, а не истина.

## Часть 2. Скоринг (таблица `scores` создана)

Формула из `docs/DESIGN.md:173/232`:

```
Significance = Fr × Wsrc × Xconf × Eng × (1 − DupPenalty) × TopicWeight × decay
decay = 0.5 ** (age_days / half_life_days)
```

* `er = reactions/views`; при `views = 0` или реакциях NULL → NULL (не считаем).
* `eng_channel = er / медиана_ER_канала`, `eng_global = er / общая_медиана_ER`;
  `Eng = √(eng_channel × eng_global)` (две базы, как требует ТЗ; **D-08**).
* `xconf` = число независимых каналов с тем же `text_hash` (**D-05**, без simhash).
* `wsrc = 1 / (1 + число перепостов того же текста)`.
* `dup_penalty = 1 − 1/xconf`.
* `fr = 1.0` — DESIGN не определяет `Fr` однозначно, не выдумываем (**D-02**).
* `topic_weight = 1.0` — нужен классификатор тем, этап 2 (**D-03**).
* `half_life_days = 30` — вынесено в `config/scoring.json`, указано в отчёте.

Числа прогона: посчитано строк `scores` = 9 235; со значимостью = 7 471 (у 1 764
постов `views` пусто/0); общая медиана ER = **0.98 %** (внешний ориентир ТЗ ≈2.3 %
— это среднее по Telegram, наша медиана по ИИ-нише ниже).

Распределение значимости: `[0,0.25)` 1 651 · `[0.25,0.5)` 1 346 · `[0.5,1)` 2 027
· `[1,2)` 1 619 · `[2,5)` 673 · `[5,10)` 100 · `≥10` 55. Ненулевых — 7 471.

### 2.2 Антинакрутка

`ER > 50 %` → `scores.anomaly = 1`, пост **исключается** из честного рейтинга и
показывается отдельным блоком (не прячем). Замер ТЗ был 9 постов; на выросшей
базе (9 235) — **13**. Примеры: `@vistehno` (views=1, react=49, ER=4900 %),
`@dailyprompts` (1/7, 700 %), `@claudecodich` (серия постов ER 95–114 %),
`@chatgptv` (245/242, 98.8 %).

### 2.3 Фильтры

Из рейтинга исключены: `is_ad = 1`, каналы `status='flooded'` и `flood_until` в
будущем. Выборка после фильтров: 9 138 постов / 420 каналов; честный рейтинг
(без аномалий): 9 125 / 420.

### 2.4 Реклама — долг, а не расширение ключевых слов

Keyword-эвристика сборщика (`erid`/`реклам`/`промокод`) владельцем отвергнута.
Полноценный семантический классификатор в эту задачу не влез; ключевые слова НЕ
расширялись. Нужно: DeepSeek-классификатор + файл промпта `prompts/is_ad.md` +
кэш по `text_hash` — долг **D-04** (отдельный раздел, см. TECH-DEBT).

### 2.5 Выдача (построена с нуля)

Каталог `reports/` был пуст; постера/дайджеста в расписании нет. Сделана выдача
`scoring.py report` → `reports/significance-YYYY-MM-DD.md`: топ-15 по значимости
(канал, дата, просмотры, реакции, ER, значимость, `t.me/<handle>/<id>`),
отдельный блок аномалий, число постов и каналов в выборке, топ-15 «до» по числу
упоминаний.

Уточнение: `mentions` в проекте — это фильтр **отбора каналов** при разведке
(`bridge_common.py`, `min_mentions`), а не ранжирование выдачи. Готового рейтинга
не существовало. Для «до» взято число упоминаний = `xconf` (в скольких каналах
тот же текст) — ближайший смысловой эквивалент.
