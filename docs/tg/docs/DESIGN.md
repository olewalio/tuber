### 3.5. Инцидент квоты (реальный, из этого прогона)

Массовый резолв хендлов через MTProto (`get_entity` + `GetFullChannelRequest`) на 73 канала дал **FloodWait 35 416 с (9.8 ч)** на 31 канале; снимается в **06:32 МСК 15.09.2026**, состояние записано в `flood_state.json`. 41 канал успел зарезолвиться до блокировки.

Причина: `ResolveUsername` для **неподписанных** каналов — квотируемая операция. Это второй подтверждённый случай: ранее `GetHistory` на неподписанных давал эскалацию 600 с → 21 000 с.

**Следствия для дизайна (жёсткие):**
- Никакого массового резолва. Максимум **20 резолвов за прогон**, пауза 3–5 с, результат кэшируется в БД навсегда.
- Приоритет у `t.me/s` (HTTP, без аккаунтной квоты) — он же даёт текст, дату, просмотры.
- MTProto — только для **подписанных** каналов (их чтение квотой почти не ограничено), для истории и `fwd_from`.
- `flood_until` в таблице каналов/аккаунтов; при активном флуде аккаунт не трогать до полного спада (правило уже зафиксировано в скилле).

## 4. Интернет-ресёрч: методы, лимиты, методология (с источниками)

### 4.1. Способы сбора

| Способ | Что даёт | Лимит | Риск |
|---|---|---|---|
| Telethon / MTProto (user) | Полная история, метаданные (views, forwards, reactions), медиа, **`fwd_from` → первоисточник** | `420 FLOOD_WAIT_X`; GetHistory ≈ **30 с на 10 запросов → sleep 1 с** | Средний (квота аккаунта) |
| `t.me/s` | ~20 постов/страница, пагинация `?before=<id>`; текст, дата, просмотры, реакции | Заголовков лимита нет; троттлинг по IP при объёме | Низкий (IP, не аккаунт) |
| Bot API | Только новые апдейты, ≤100/24 ч; историю **не отдаёт** | 20 msg/мин в группе, ~30 msg/с broadcast | Низкий |
| RSSHub | RSS по `t.me/s` с fallback на MTProto | Зависит от инстанса | Низкий |
| TGStat API | Stat/Search/Callback, публикации, форварды | Квота по запросам/каналам; FREE — только свои ≤2 канала | Нет (легально, платно) |
| telemetr.io | 1.8 млн каналов, метрики, reach | Free: 1000 req/мес, 5 каналов, 7 дней | Нет (от $25/мес) |

Ссылки: Telethon (bot-vs-mtproto, flood limits) — docs.telethon.dev; `?before=` — apify/bestscraperapi; getUpdates ≤100/24 ч — core.telegram.org/bots/faq; RSSHub `channel.ts` — github.com/DIYgod/RSSHub; TGStat — api.tgstat.ru/docs; telemetr — api.tlmtr.io/docs.

**Рекомендация ресёрча:** Telethon для чтения публичных каналов + `t.me/s` как резерв, не тратящий MTProto-квоту; для истории — takeout-сессия; инкрементально по `min_id`, а не полный re-scan.

### 4.2. Признаки перепечатки/агрегатора (для отбора первоисточников)

Ссылка на другой канал внутри текста, «via @channel», «(с) @channel», `post_author`, сохранённое тело при изменённом заголовке, метка «Переслано от…», отсутствие собственного медиа. Первоисточник — минимальный `published_at` в кластере + отсутствие признаков перепечатки.

### 4.3. Таксономия ИИ-тематики (10 тем + атрибуты)

`model_release`, `agents`, `vibe_coding`, `devtools`, `infra_hardware`, `funding`, `regulation`, `research`, `use_case`, `risk_scandal`.
Атрибуты: `source_type` (primary / secondary / tertiary / discussion), `claim_type`, `entity_tier`, `novelty`.
Проблема текущего классификатора Datapine: `ai_trends` съедает 68% потока (1935 из 2824 за смену) — релизы тонут в мелочи. Новый парсер обязан разнести релизы/девтулзы/железо по своим темам.

### 4.4. Скоринг значимости

- HN: `score = (P−1)/(T+2)^1.8` (гравитация), плюс штрафы и бусты.
- Reddit: log-hot; Techmeme: кластеризация + редакционная пирамида; Google News: MinHash+PLSI+covisitation (Das, 2007).
- Композит для нас: `Significance = Fr × Wsrc × Xconf × Eng × (1 − DupPenalty) × TopicWeight`, где `Eng` нормируется на медиану источника (иначе крупный канал всегда №1), `Xconf` — число независимых источников (считать **после** дедупа).

### 4.5. Дедуп

Точный (URL/ID) → нечёткий (SimHash Charikar 2002, MinHash+LSH Broder 1997) → эмбеддинги + cosine → кластеризация в сюжеты (Union-Find / BERTopic).

### 4.6. Метрики качества и приёмка

На **gold-сете 200–300 материалов** (ручная разметка, 2 аннотатора, Cohen's κ ≥ 0.7): recall/precision/F1 классификации, dup-rate и recall дедупа, latency/свежесть, enrichment coverage (дата+метрика+живая ссылка) ≥ 0.95, ошибки/uptime. Без эталона метрики — самообман.

### 4.7. Типовые провалы

Мусор из агрегаторов; эхо-эффект одного сюжета; потеря первоисточника; устаревание; перегрузка потока; мёртвые ссылки.

## 5. Проблемы, найденные при аудите (что чинить обязательно)

1. **Квота аккаунта** — массовый резолв убивает сборщик на часы (§3.5). Нужен предохранитель и кэш.
2. **Нет пагинации в t.me/s-сборщике** (24 ч окно) — история не добирается; при пропуске прогона посты теряются навсегда.
3. **Дедуп только внутри одного пайплайна** (`cryptostream/dedup.py`, окно 4 ч) — для 100+ каналов ИИ нужен кросс-канальный дедуп с кластеризацией.
4. **Классификатор перекошен** (68% в `ai_trends`) — не различает релиз/тулзу/мнение.
5. **Нет различения первоисточник/перепечатка** в автоматике (только ручная таблица кросс-постов в Headliners).
6. **Нет метрик качества** ни у одного парсера: полнота, dup-rate, точность классификации не измеряются — «не работает»/«работает» определяется на глаз.
7. **VR не считается** — отбор источников идёт по подписчикам (крупные агрегаторы вытесняют авторские каналы с VR 40–52%).
8. **Веб-превью закрыто у 17 каналов** — их нельзя читать через `t.me/s`; нужен путь через MTProto-подписку или отказ от них.

## 6. Проект системы (новый контур, отдельный от старых)

Каталог: `/root/tuber-telegram/` (БД SQLite + WAL, код отдельными модулями; правки — только через jCode по ТЗ).
Схема БД уже создана (`scripts/init_db.py`): `channels`, `posts`, `classified`, `stories`, `story_members`,
`account_state`, `runs`, `run_log`, `metrics_daily`.

### Слой 1. Реестр каналов (Discovery)
- Источники наполнения: сид-список (наш `UNIVERSE.csv`, 95 живых), MTProto `SearchRequest` + `GetChannelRecommendationsRequest` порциями, веб-каталоги через FlareSolverr.
- Верификация канала: `t.me/s` (жив/мёртв, дата, частота, язык, VR) → запись в реестр с полями `handle, title, subs, subs_at, last_post_at, posts_7d, avg_views, vr, lang, topic_guess, status, flood_until, source_type, first_seen`.
- Регламент: ≤20 новых резолвов за прогон, пауза 3–5 с, кэш навсегда, при `flood_until` — стоп до спада.

### Слой 2. Сбор (Collector)
- Основной канал: `t.me/s` c пагинацией `?before=<id>` до `min_id` из БД (инкрементально, без потерь), пауза 0.5–1 с, backoff на 403/429, дедлайн прогона.
- Второй канал (для подписанных каналов): Telethon `iter_messages(min_id=..., reverse=True)` со sleep 1 с — даёт `fwd_from`, реакции, медиа.
- Запись: `posts(post_id, channel_id, date_utc, text, views, forwards, reactions, media, links, fwd_from_channel, raw_html_hash)`; upsert, обновление просмотров на 24/72 ч.

### Слой 3. Нормализация
- Снятие рекламных блоков и маркировки (ERID/«реклама»), извлечение ссылок, хэштегов, упоминаний @; канонизация URL (срез utm).
- Вычисление `is_forward`, `has_own_media`, `mentions_channels` → признаки для слоя «первоисточник».

### Слой 4. Классификация (DeepSeek)
- Промпт-файл `prompts/classify.md`: 10 тем + `source_type` + `claim_type` + `entity_tier` + `novelty` + `is_ai_related` + `lang`.
- Батчи по 8 постов, `thinking: disabled` (иначе reasoning съедает бюджет), кэш ответов по хэшу текста, ретраи.
- Отдельный проход «это ИИ?» для пограничных IT-каналов.

### Слой 5. Дедуп и сюжеты
- Канон URL → SimHash (шинглы k=4 слова) → MinHash/LSH при объёме; порог зафиксировать на gold-сете.
- Кластеризация Union-Find в «сюжеты»; в кластере выбирается первоисточник (min `published_at` + авторские признаки), остальные — эхо.

### Слой 6. Скоринг и отбор
- `Significance = Fr × Wsrc × Xconf × Eng × (1 − DupPenalty) × TopicWeight`; `Wsrc` — по типу источника (авторский/первоисточник выше агрегатора), `Eng` — нормировка на медиану канала, `TopicWeight` — важность темы (релизы/агенты выше мемов).
- Антинакрутка: VR > 80% при малых абсолютных просмотрах → флаг, из честных метрик исключать.

### Слой 7. Выдача
- Дайджест в Telegram (только Bot API, `parse_mode=HTML`) по расписанию; формат: тема → заголовок → суть 2–3 строки по-русски → источник-первоисточник (кликабельная ссылка).
- БД-API для запросов («что нового по вайб-кодингу за неделю», «все релизы моделей за месяц»).
- Обязательно: ссылки строить только из реальных `t.me/<user>/<id>` — не из внутренних ID (известный провал: URL из hex-хэша).

### Предохранители (по опыту инцидентов)
`flood_until` на аккаунт и канал; ≤20 резолвов/прогон; ≤50 MTProto-вызовов/прогон; sleep 1 с на GetHistory, 3–5 с на резолв; дедлайн прогона; backoff на 403/429 у `t.me/s`; WAL + ежедневный бэкап БД; watchdog по свежести данных; никаких правок боевого кода без ТЗ и независимой приёмки.

## 7. Критерии приёмки (свои, не «0 расхождений со старым»)

| Метрика | Порог |
|---|---|
| Полнота (recall) на gold-сете | ≥ 0.85 |
| Точность классификации темы (F1) | ≥ 0.85 |
| Dup-rate выдаваемого потока | ≤ 0.05 |
| Recall дедупа (доля схлопнутых дублей) | ≥ 0.90 |
| Свежесть: пост в выдаче от публикации | ≤ 2 ч (p90) |
| Enrichment coverage (дата+метрика+живая ссылка) | ≥ 0.95 |
| Uptime сборщика | ≥ 0.98 |
| Ошибки на 1000 постов | ≤ 5 |
| Инциденты квоты Telegram | 0 (флуд-инцидент = провал прогона) |

Gold-сет: 200–300 материалов, ручная разметка двумя аннотаторами, κ ≥ 0.7.

## 8. План работ

1. **Этап 1 (каркас + сбор).** Каталог проекта, схема БД, реестр (импорт 95 живых из `UNIVERSE.csv`), сборщик `t.me/s` с пагинацией и инкрементом, предохранители квоты, лог прогонов. Приёмка: 3 суток сбора без пропусков, 0 инцидентов квоты.
2. **Этап 2 (нормализация + классификация).** Очистка рекламы, признаки первоисточника, DeepSeek-классификатор по 10 темам, кэш.
3. **Этап 3 (дедуп + сюжеты + скоринг).** SimHash/MinHash, кластеры, формула значимости, антинакрутка.
4. **Этап 4 (выдача + метрики).** Дайджест в канал, gold-сет, панель метрик, недельный разбор ошибок.

Первый шаг — этап 1; код пишется заново (по правилу: механику берём, логику старых контуров не копируем), через jCode с ТЗ и независимой приёмкой.
