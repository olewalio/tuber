## 1. Дефект и почему он блокирующий

TEMP-триггеры адаптеров X и YouTube писали в ядро **квалифицированным** именем:

```sql
CREATE TEMP TRIGGER posts_ins INSTEAD OF INSERT ON posts BEGIN
  INSERT INTO main.content(platform, external_id, …) VALUES(…);
END
```

SQLite ≤ 3.45.1 запрещает квалифицированный DML в теле триггера безусловно:

```
sqlite3.OperationalError: qualified table names are not allowed on
INSERT, UPDATE, and DELETE statements within triggers
```

Ошибка возникает уже на `CREATE TRIGGER`, то есть на **первом** соединении:
`store.connect()` падает и больше ничего не делает. Воспроизведено:

| Интерпретатор | SQLite | Установка слоя совместимости |
|---|---|---|
| `/usr/bin/python3` (системный) | 3.45.1 | `OperationalError` (падало) |
| `/usr/local/lib/hermes-agent/venv/bin/python3` | 3.53.1 | ОК |

Замеры запрета (минимальные воспроизводимые опыты) на 3.45.1: отклоняются
`main.`, `"main"`, `[main]`, имя привязанной схемы, и это не зависит от того,
создан триггер в `TEMP` или в `main`. Запрет снят только в новых SQLite; на
3.45.1 обойти квалификацию нельзя.

## 2. Что оказалось не так просто: шесть конфликтующих имён

Наивное «убрать `main.`» ломается на именах, которые совпадают у legacy-таблицы и
таблицы ядра:

| Платформа | Конфликтующие имена |
|---|---|
| X | `run_log`, `blocklist`, `metrics_daily`, `classify_daily` |
| YouTube | `llm_usage`, `thumbnail_vision` |

Причина: TEMP-триггер разрешает НЕквалифицированное имя сначала в `TEMP`-схеме,
и только потом в `main`. Если представление совместимости названо так же, как
таблица ядра, запись из триггера попадает обратно в представление:

* `INSERT INTO <имя>` → разрешается в TEMP-представление → рекурсия;
* при `recursive_triggers=OFF` (по умолчанию) это **тихая потеря записи** —
  проверено: `INSERT` «успешен», строк в ядре 0.

То есть убрать квалификацию во всех шести случаях нельзя без изменения того,
куда разрешается имя.

### 2.1. Решение

Для конфликтующих имён представление совместимости создаётся **под своим
именем**, и TEMP-схема больше не затеняет ядро:

| Legacy-имя | TEMP-представление |
|---|---|
| `run_log` | `x_run_log` |
| `blocklist` | `x_blocklist` |
| `metrics_daily` | `x_metrics_daily` |
| `classify_daily` | `x_classify_daily` |
| `llm_usage` | `yt_llm_usage` |
| `thumbnail_vision` | `yt_thumbnail_vision` |

Тогда DML в триггере идёт без квалификации и разрешается в ядро. Чтобы
legacy-код по-прежнему видел привычные имена, `tuber.core.sqlcompat.
CompatConnection` на лету переписывает в исполняемом SQL **имя таблицы** в
позициях `FROM` / `INTO` / `JOIN` / `UPDATE` / `TABLE` и внутри
`PRAGMA table_info(...)`. Строковые литералы и комментарии сохраняются дословно,
`main.<имя>` не трогается (прямая работа с ядром). Примеры:

```
SELECT msg FROM run_log            -> SELECT msg FROM x_run_log
INSERT INTO blocklist (…)          -> INSERT INTO x_blocklist (…)
PRAGMA table_info(metrics_daily)   -> PRAGMA table_info(x_metrics_daily)
SELECT 'FROM run_log' FROM main.run_log   -> без изменений
```

Трансляция включается **только после установки слоя** (иначе его же DDL
переписал бы сам себя) и **выключена во время миграции схемы ядра** (там имена
означают таблицы ядра). Реализация — `tuber/core/sqlcompat.py`; подключение —
`_RetryConnection` (X) и `_CompatConnection` (YouTube) через
`core.db.connect(factory=…)`.

Попутно найден второй источник того же запрета: `INSERT OR REPLACE INTO
temp.x_last_insert` внутри триггеров `runs_ins`/`stories_ins`. Он тоже
де-квалифицирован (`x_last_insert` — TEMP-таблица, разрешение корректно).

### 2.2. Почему это «слой совместимости», а не правка логики платформ

Ни один файл платформ (`collect.py`, `report.py`, `thumbs.py`, …) не изменён:
плоский SQL legacy-кода работает как раньше. Всё сосредоточено в
`tuber/core/sqlcompat.py` и `tuber/platforms/*/store.py`.

## 3. Ранний явный отказ и диагностика (задача 2)

* `sqlcompat.MIN_SQLITE_VERSION = (3, 24, 0)`; `ensure_supported_sqlite()`
  вызывается в начале `store.connect()` обеих платформ и падает понятным
  `RuntimeError` с версией SQLite, путём к интерпретатору, версией Python и
  подсказкой (вместо сырого `OperationalError`).
* Любой `OperationalError` при установке слоя оборачивается
  `compat_install_error(...)`: версия, интерпретатор, исходная ошибка, подсказка
  про venv и `tuber doctor`.
* Добавлена подкоманда `python3 -m tuber doctor`:

```
tuber doctor
  Python:      3.12.3
  исполняемый: /usr/bin/python3
  SQLite:      3.45.1 (минимум для адаптеров: 3.24.0)
  платформа:   Linux-…
  база:        (не задана; укажите --db PATH или TUBER_DB)
```

`python3 -m tuber schema --target …` тоже печатает строку с интерпретатором и
SQLite.

## 4. Приёмка: равенство на двух интерпретаторах (задача 3)

Полный журнал — `docs/acceptance-log-tz3c.txt`. Кратко:

| Проверка | system (3.45.1) | venv (3.53.1) | Расхождение |
|---|---|---|---|
| `parity` (44 правила, os+x+tg) | «расхождений нет», rc 0 | то же, вывод **бит-в-бит** | 0 |
| `yt report --days 10` | 423 строки, 20 с, rc 1* | 423 строки, 17 с, rc 1* | **0 строк**, md5 `debddc9d…` совпал |
| `x report --date 2026-09-15 --stdout-only --no-model` | 62 строки, rc 0 | 62 строки, rc 0 | **0 строк**, md5 `10a9b2fb…` совпал |
| `EXPLAIN QUERY PLAN` (6 YT + 4 X запросов) | планы совпали, `MATERIALIZE: none` | то же | отличается только строка версии SQLite |

\* rc 1 — предупреждение «индекс виральности не посчитан» на копии данных;
одинаково на обоих интерпретаторах, к дефекту отношения не имеет.

**Находка приёмки.** `/tmp/unified5.db` патологически медленный на
`tuber yt report` (>10 мин, стек — `report._viral_candidate_rows`). Это
**воспроизводится на базовой ревизии** (`9c6fe8f`, worktree): `report --days 1`
убит по таймауту 300 с. Значит это свойство копии/данных, а не регрессия ТЗ-3c.
Для отчётной части единая база пересобрана из замороженных `/tmp/v-*.db`
(`tuber migrate`, 54 с) — на ней отчёт укладывается в 17–20 с. Копия не
чинилась (это данные, не код).

## 5. Тесты (задача 4)

| Набор | Собрано | Результат |
|---|---|---|
| до ТЗ-3c | 908 | 907 passed + 1 xfailed |
| после ТЗ-3c | **922** | **921 passed + 1 xfailed** |

Новый `tests/core/test_tz3c_sqlite_compat.py` (14 тестов):

* `connect()` + запись конфликтующих таблиц **в подпроцессе** под
  `/usr/bin/python3` и под `sys.executable` (skip с явной причиной, если
  системного интерпретатора нет) — тест ловит именно дефект: на старом коде
  подпроцесс падал бы на `CREATE TRIGGER`;
* отсутствие `main.`/`temp.` в тексте `CREATE TEMP VIEW`/`CREATE TEMP TRIGGER`
  и отсутствие квалифицированного DML-таргета в триггерах;
* `sqlcompat.sqlite_info()` и вывод `tuber doctor` (версия SQLite + путь к
  интерпретатору); понятная ошибка на старом SQLite (подмена версии);
* трансляция legacy-имён (позиции таблиц, `PRAGMA`, неприкосновенность строк и
  `main.X`), переименование конфликтующих представлений;
* обёртка с `PATH=/usr/bin:/bin` исполняет явно заданный интерпретатор.

Сеть не используется.

**Тест ловит именно дефект.** На базовой ревизии `9c6fe8f` (отдельное дерево,
`git archive`) под `/usr/bin/python3` и X-, и YouTube-`connect()` падают с
`OperationalError: qualified table names are not allowed … within triggers`;
на текущей ревизии оба успешны. Значит subprocess-тест проверяет ровно дефект,
а не окружение (подробности — `docs/acceptance-log-tz3c.txt` §8).

## 6. Обёртки расписания (задача 5)

`scripts/x/*.sh` (9 обёрток) и `scripts/acceptance_tz1.sh` больше не зовут
`python3` по имени, а берут интерпретатор ЯВНО:

```bash
TUBER_PYTHON="${TUBER_PYTHON:-/usr/local/lib/hermes-agent/venv/bin/python3}"
if [ ! -x "$TUBER_PYTHON" ]; then
  echo "ошибка: интерпретатор контура не найден: $TUBER_PYTHON" >&2
  exit 4
fi
```

Проверено: при `PATH=/usr/bin:/bin` обёртка исполняет venv-python (3.53.1), а не
системный (3.45.1); фолбэка на PATH нет — при отсутствии интерпретатора явный
отказ с кодом 4. В заглушке `scripts/install_hermes_cron.sh` — TODO о
закреплении интерпретатора при реализации единого расписания (ТЗ-5).

## 8. Остаток и рекомендации

* **Закрыто:** совместимость с SQLite 3.45.1 (D-32), явный отказ, диагностика,
  закрепление интерпретатора в обёртках X.
* **Остаток (зафиксирован в D-32):** на соединении адаптера неквалифицированное
  имя любой из шести конфликтующих таблиц означает legacy-форму и
  транслируется в представление. Код, которому нужна таблица ядра на таком
  соединении, обязан писать `main.<имя>`. Сейчас таких мест нет, ограничение
  закреплено тестами.
* **Рекомендация (ТЗ-5):** в едином расписании Hermes вызывать интерпретатор из
  переменной с полным путём (образец — inline-блок в `scripts/x/*.sh`), а не по
  PATH; заглушка `install_hermes_cron.sh` уже помечена.
* **Рекомендация по данным:** `/tmp/unified5.db` пересобрать (или не
  использовать для отчётов) — на нём `yt report` патологически медленный и на
  базовой ревизии. Это данные/копия, не код.
* Открытые долги, не относящиеся к ТЗ-3c, не трогались: D-14..D-20, D-28,
  D-29, D-30, D-31.
